# Keyboard window switching

Two shortcuts, one rule behind both: **after the keyboard moves focus, the
pointer goes with it.**

| | Hyprland (APEX Desktop) | labwc (APEX Floating) | niri (APEX Scrolling) |
|---|---|---|---|
| `SUPER`+arrow | moves focus, cursor warps into the window | moves the window to that edge, cursor warps with it | moves focus along the scroll |
| `ALT`+`Tab` | APEX Shell switcher | labwc's thumbnail switcher, all desktops | niri's recent-windows switcher |
| `ALT`+`SHIFT`+`Tab` | the same, backwards | the same, backwards | the same, backwards |

## Why the pointer has to move

Both the Hyprland and labwc sessions put focus under the pointer
(`follow_mouse = 1`, `<followMouse>yes</followMouse>`). That is deliberate —
focus never depends on a click landing in the right place — but it means a
focus change the *keyboard* made only lasts until the mouse is touched. Press
`SUPER`+`Left`, take your hand off the keyboard, nudge the mouse, and focus
snaps back to whatever the pointer was still sitting on.

So the compositor carries the pointer to the middle of the window that just
gained focus:

* **Hyprland** — `cursor { no_warps = false }` in `apex/input-defaults.lua`.
  It is Hyprland's default today; it is written down anyway, so a future
  release cannot change APEX's behaviour by changing its own mind.
* **labwc** — `<action name="WarpCursor" to="window"/>` after every
  `MoveToEdge` and `SnapToEdge`, generated by `/usr/libexec/apex-labwc-keybinds`.
  labwc has no directional-*focus* action at all (`Focus` takes no arguments),
  so `SUPER`+arrow moves the window; the warp is what stops the move handing
  focus to whatever it uncovered.
* **niri** — nothing to do. niri does not focus-follow-mouse unless asked, so
  nothing takes the focus back.

`tests/test-apex-hypr-focus.sh` asserts the *consequence* on a real nested
Hyprland — the pointer ends up inside the newly focused window, and the window
is still focused after the pointer is nudged — rather than asserting that a
config file contains a line. It then tears the session down and runs the whole
thing again with `no_warps = true`, where those assertions **must** fail, so
the suite cannot pass by agreeing with whatever the configuration happens to
say. In that control the pointer is left at 480,540 while the focused window
starts at x=962, and a one-pixel nudge hands focus straight back: Andre's
report, reproduced on demand.

| apex-shell | `tests/run-window-switcher-test.sh` | real `ALT` and `TAB` keys reach the switcher — stepping, wrapping, backwards, `ESCAPE`, commit, and a window that has left the screen |
| apex-shell | `tests/run-switcher-activate-test.sh` | committing focuses the selected window, puts the pointer inside it, holds focus through a nudge, and switches workspace for a window on another one |

One thing no headless suite can press: a real `ALT` held down and let go.
`wtype`'s virtual keyboard is accepted by Hyprland 0.56.2 and then reported
with `active keymap: error`, and no binding fires from it; niri behaves the
same way; only wlroots compositors take it. So the release binding is asserted
as *registered* (`release: true` in `hyprctl binds`) and confirmed for real by
a person holding `ALT`.

## The Alt-Tab switcher

`apex shell switcher next | prev | commit | cancel`

Hold `ALT`, tap `Tab` to step through every window on every workspace
most-recently-used first, release `ALT` to switch to the highlighted one.
`ESCAPE` (or `ALT`+`ESCAPE`) cancels and leaves focus where it was. A single
tap-and-release is therefore an ordinary "go back to the last window" swap.

The window list is **wlr-foreign-toplevel-management**, which is the same
protocol the app dock uses: every toplevel the compositor has, regardless of
workspace or output, with no compositor-specific IPC involved.

### How the hold-and-release works, and why it is not a keyboard grab

The obvious implementation gives the switcher surface exclusive keyboard focus
so it can watch for the `ALT` release. That cannot be right here: taking
keyboard focus takes it *away from the window the switcher is about to
activate*, which is the exact defect the rest of this document is about.

So the shell's overlay never asks for the keyboard. The **compositor** reports
the release:

* Hyprland — a bind with `release = true` (`bindr`) on `Alt_L` and `Alt_R`,
  and `transparent = true` so applications still see the release themselves.

It fires on *every* `ALT` release for as long as the machine is on, not only
while the switcher is open. That is why the keybind names
`/usr/libexec/apex-switcher` rather than `apex shell switcher` directly: with
nothing open, the helper does one `[ -e ]` on a flag file under
`XDG_RUNTIME_DIR` and exits, and the shell is never contacted.

`ALT`+`Return` commits as well, and it is not decoration. The release binding
is the one part of this that no headless test can press — a synthetic keyboard
(`wtype`, virtual-keyboard-v1) is accepted by Hyprland 0.56.2 and then reported
with `active keymap: error`, and no binding fires from it. `ALT`+`Return` is an
ordinary press binding, so if the release semantics ever change the switcher
still has a keyboard way to commit rather than becoming a thing you can open
and not close.

### Why the other two sessions keep their own

Both were measured rather than assumed, on 2026-09-20.

**labwc** has `onRelease="yes"`, and labwc-config(5) says what it is for: "the
action should fire when the modifier is used **without** another key". Holding
`ALT`, tapping `Tab` — which fires the `A-Tab` binding — and releasing `ALT`
fires an `Alt_L onRelease` binding zero times; pressing and releasing `ALT` with
no `Tab` fires it. That is the documented design, and it makes a shell-drawn
hold-and-release switcher impossible there. labwc's own switcher does the same
job properly, so the Floating session keeps it — with
`<action name="NextWindow" workspace="all"/>`, which is the whole of "all
windows including other workspaces" for that session.

**niri** 26.04 ships `recent-windows`: hold-and-release, MRU ordering, live
previews. It has no key-release binding for the shell's switcher to borrow
either, so the Scrolling session keeps niri's — and APEX Shell writes the two
binds into `ApexShellKeybinds.kdl` rather than inheriting them, for the same
reason `cursor { no_warps = false }` is written into the Hyprland seed when it
too is upstream's default: this is APEX's `ALT`+`Tab`, not something a later
release can change its mind about.

So `ALT`+`Tab` looks different in each session, and that is a decision rather
than an oversight: two of the three compositors already do this well, and
replacing a working native switcher with a worse shell-drawn one for the sake
of a matching look would be the wrong trade.

### Rebinding

`ALT`+`Tab` is **not** in the Keybinds page. The shell's keybind model has no
way to express a key *release*, so rebinding the opening shortcut there would
move `next` and leave the commit on `ALT` — a switcher you can open and cannot
close. Until the model grows a release, the combination is fixed in
`apex/keybindings.lua` and `rc.xml`.
