# The shell is accessible on the new image — 8 windows on the bus, no shim

Measured on katana 2026-09-22, on the image built that night
(`apex-44c9a5cb…`, digest `sha256:06ba23c3…`), in a real Hyprland session
started the way `katana-qualification-20260919.md` §4 documents.

## The result

```
applications on the AT-SPI bus: 4
  :1.0    polkit-mate-authentication   ChildCount=0
  :1.2    xdg-desktop-portal-gtk       ChildCount=0
  :1.34   polkit-mate-authentication   ChildCount=0
  :1.35   quickshell                   ChildCount=8
```

**Eight.** P2-003 has said for rounds that "on a real machine a screen reader
still gets ONE node from the shell". It now gets a tree.

That number is not new — round 30 measured exactly 8 by interposing
`QGuiApplication::exec()` with an `LD_PRELOAD` shim that reinstalled QtQuick's
accessibility factory. The shim "is test-only and ships nowhere". **The same 8
now appears with no shim**, from the shipped binary, because
`quickshell-git 0.3.1^860.gitc6a5160` carries upstream commit `916a0dd`
("launch: avoid creating multiple QApplications").

## The positive control, and why it is load-bearing

`soffice` published `ChildCount=2` in the first run of this probe, while
quickshell published 0. So the bus, the registry and the probe were all working
at the moment quickshell answered zero — the zero was about quickshell, not
about the instrument. LibreOffice was only on the machine at all because it had
been installed hours earlier for P1-038.

## A REAL FINDING: the bridge must be on BEFORE the shell starts

The first measurement on this same image, same binary, same session, read
**`quickshell ChildCount=0`** — and it would have been reported as "the fix does
not work" if it had been trusted.

The difference is startup order:

| | `toolkit-accessibility` at quickshell start | result |
|---|---|---|
| first run | `false` (turned on afterwards) | **0** |
| second run | `true` | **8** |

Qt decides whether to publish when the application object is built. Turning the
bridge on later does not retrofit it. So on a machine where
`org.gnome.desktop.interface toolkit-accessibility` is false at login — which is
the **default** — the shell ships an empty tree no matter which quickshell is
installed.

**This is the next thing P2-003 needs, and it is APEX's to fix, not upstream's.**
Either the session sets `QT_LINUX_ACCESSIBILITY_ALWAYS_ON=1` for the shell, or
the image ships the gsetting on. Neither is done today: quickshell's environment
on this machine carried no accessibility variable at all.

## What this closes and what it does not

- **Closes:** "a screen reader gets one node", the runtime half P2-003 has been
  blocked on, and it closes it without the shim.
- **Does not close:** whether the *content* is good — names, roles, focus order.
  `ChildCount=8` says eight windows are on the bus, not that a blind user can
  drive the shell. The lock screen's password field, which
  `check-lockscreen-a11y.sh` asserts at source level and could never reach at
  runtime, is now reachable and worth measuring properly.
- **Does not close:** Orca at the greeter, which is a different session.

# CORRECTION 2026-09-22 — the startup-order claim above is WRONG

A peer session ran the controlled experiment. **Walk 1 = 0, walk 2 = 8**, on
the same still-running process. Landed as `4739e21b`.

So `org.a11y.Status` is the gate, **the gsetting is not**, and **a late enable
does retrofit**. This sentence in the section above is false and is withdrawn:

> *"Qt decides whether to publish when the application object is built. Turning
> the bridge on later does not retrofit it."*

What my own run actually showed was weaker than what I wrote: I changed **two**
variables between the 0 and the 8 — I set the gsetting *and* restarted
quickshell — so a restart alone produces the identical pattern. Self-consistent
is not controlled. I said so when the peer first challenged it; the experiment
has now settled it against me.

## Why the test I proposed could not have worked

I suggested "set the flag alone, not the gsetting". That is impossible through
that interface: **setting `org.a11y.Status.ScreenReaderEnabled` writes the
gsetting back into dconf**, measured twice, including on a profile with no
database at all. The decisive run had to hold the gsetting down *physically* —
`at-spi-bus-launcher` under `GSETTINGS_BACKEND=memory` — so dconf could not
move. The tree then appeared with the database keeping its sha256 **and** its
mtime, and `gsettings get` still answering false.

**The coupling is one-way.** Putting the flag back down leaves
`toolkit-accessibility` and `IsEnabled` true, so any run that stops there leaves
accessibility switched on for everything that starts next.

## Two more corrections to the reasoning, not the result

- **My `mtime` argument has a hole.** `dconf dump /` prints *system defaults*,
  so an empty profile still dumps the APEX dark-mode keys. A dump is never
  evidence that a user set anything. That weakens the argument I used about the
  03:51:08 database, not the readings themselves.
- **The 8 is now explained rather than observed.** Four surfaces per output, and
  both landed runs had two outputs. Adding a second headless output took one
  process from 4 frames to 8. So "8" was never a property of the fix; it is a
  property of the desk.

## What actually remains for P2-003, which is bigger than the gate

**Every frame the shell publishes is empty** — no name, no description, no
`Action` interface. The bridge is no longer what stands between a blind user and
this shell. **The missing markup is.**

That reframes the row entirely. `ChildCount=8` was never the finish line, and
the section above was right to say so for a weaker reason than the real one.
It is shell-side work in apex-shell, and it is unowned.

Also recorded by that round, worth keeping: `org.a11y.Bus` cannot be
dbus-activated on a private session bus on this image (`Permission denied`, and
**no AVC is logged**, so "no denial" must not be read as "not SELinux" — this
repository already has that trap written down); and Qt attempts `Embed` exactly
**once**, logging the registry failure in the same second as the write and never
retrying.
