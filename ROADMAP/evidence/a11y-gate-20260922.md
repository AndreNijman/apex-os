## The verdict, from the table that was written before the run

| walk 1 | walk 2 | conclusion |
|---|---|---|
| **0** | **8** | **`org.a11y.Status` is the gate; the gsetting is not. A late enable DOES retrofit.** |

**Where those two numbers were read, stated before anyone quotes them.** The
**0** is every walk taken with the gate off — at the greeter (§1), and twice on
`apex-shell` in the isolated rig (§3, §4). The **8** is the `apex-shell` tree
with the gate flipped at runtime and two outputs present (§4): four frames per
output, which is exactly the eight both landed runs measured on two-output
sessions. The greeter's own walk 2 stops at the application node with no
children for a cause measured in §2 — its VT is inactive and its compositor has
no outputs — so the tree size there says nothing about the gate, only the
application's presence on the bus does.

`katana-a11y-20260922.md`'s line — *"Qt decides whether to publish when the
application object is built. Turning the bridge on later does not retrofit it"*
— **is struck.** It is the file that is wrong, and only in that sentence; its
headline of eight nodes with no shim is confirmed here for a third time and is
now explained.

The stronger half is that the gsetting was not merely "not set by me" but
**provably unmoved**: run K flipped the bus property against an
`at-spi-bus-launcher` started with `GSETTINGS_BACKEND=memory`, so the dconf
database physically could not change, and it did not — same sha256, same mtime,
`gsettings get` still `false` — while the shell went from publishing nothing to
publishing a tree.

## 5. A defect in the interface the brief told me to use: the write is a latch

**Setting `org.a11y.Status.ScreenReaderEnabled` over D-Bus writes the gsettings
back into dconf.** Measured twice:

| | before the write | after the write |
|---|---|---|
| greeter, `/var/lib/greetd/.config/dconf/user` | sha `af3a30ec…`, mtime 03:40:18.782, `toolkit-accessibility=false` | rewritten at **04:15:54.692** with `screen-reader-enabled=true` **and** `toolkit-accessibility=true` |
| isolated profile | **no dconf database at all** | database **created** at **04:21:03.420** |

So the brief's step 4 — "set `ScreenReaderEnabled` alone … and specifically not
the gsetting" — **cannot be done through this interface**. `at-spi-bus-launcher`
couples them. Run K is the way around it.

**And the coupling is one-way.** Setting `ScreenReaderEnabled` back to `false`
leaves `toolkit-accessibility` **`true`** and therefore `IsEnabled` **`true`**:

```
IsEnabled                    : b true
ScreenReaderEnabled          : b false
toolkit-accessibility        : true
```

A run that "puts the flag back" and stops there has left accessibility **on**
for every process that starts afterwards. Restoring needs an explicit
`gsettings set … false`, which is what §7 did.

### What that does to `katana-final-qual-20260922.md` §5

That file's counter-example rests on `andre` having had **no dconf database at
all** until 03:51:08, inferred from the database's **mtime**. The latch above
says their own `ScreenReaderEnabled` write at ~03:48:5x would itself have
created that database, and a later mtime cannot distinguish "created 03:51:08"
from "created ~03:48:5x and rewritten at 03:51:08". Their §5 **conclusion is the
one this run confirms**, but that particular argument for it does not hold. It
is not the file that is wrong; it is one line of its reasoning.

A trap that sits right next to this, found while checking the above rather than
asserting it: **`dconf dump /` prints the system defaults too.** On a profile
with no database at all it still prints

```
[org/gnome/desktop/interface]
color-scheme='prefer-dark'
gtk-theme='Adwaita'
```

because APEX seeds those in `/etc/dconf/db/local.d` as defaults, not locks. So a
dump cannot be read as "the user has set these". `strings` on the isolated
profile's 432-byte database shows what is actually in it: `screen-reader-enabled`
and `toolkit-accessibility`, **and nothing else** — which is the sharper form of
the point above. In that run the D-Bus property write was the *only* thing that
created a user database; a shell start does not.

## 6. Three more things this run found

- **`org.a11y.Bus` cannot be D-Bus-activated on a private session bus on this
  image.** `Activated service 'org.a11y.Bus' failed: Failed to execute program
  org.a11y.Bus: Permission denied` — and **no AVC is logged**, so "no denial"
  will read as "not SELinux" to whoever hits it next. The service file carries
  both `Exec=/usr/libexec/at-spi-bus-launcher` (label `gnome_atspi_exec_t`) and
  `SystemdService=at-spi-dbus-bus.service`; the systemd route works, the `Exec=`
  route does not. Any harness that stands up a private a11y bus —
  `tests/lib/atspi.sh` is the one in this repo — has to start the launcher
  itself rather than letting dbus activate it.
- **Qt attempts `Embed` exactly once.** With the gate flipped on and no registry
  running, quickshell logged, in the same second as the write:
  `qt.accessibility.atspi: Error in contacting registry:
  "org.freedesktop.DBus.Error.NameHasNoOwner" "Could not activate remote peer
  'org.a11y.atspi.Registry': unit failed"` — direct evidence that a running
  process reacts to the property — and then **never retried**, not when the
  registry appeared and not when the flag was toggled again. A CI probe that
  enables accessibility before the registry is up will measure an empty bus
  around a healthy shell.
- **The residue the brief warned about is real and was reproduced.** After
  `ScreenReaderEnabled` went back to `false` at the greeter, `--count` still
  answers **1**: Qt does not unregister. It clears when the greeter next starts.

### One thing I broke and put back, stated plainly

At 04:22:47 a `pkill -x -u 1000 -f "quickshell -c /usr/share/apex-shell"` aimed
at my own isolated shell also killed **session 89's** shell, pid 12634: the two
command lines are byte-identical, so the pattern could not tell them apart.

were untouched; only the bar died.

It was restored at 04:24 as `restore-s89-shell.service`, pid **17584**, and
`hyprctl layers` shows quickshell layer surfaces back on **both** outputs
(1920x40 bars at `0,0` and `1920,0`, plus the edge surfaces). Two honest
differences from the original: the new process sits in `app.slice` rather than

`exec("…")` and `hl.dsp.exec("…")` alike. Worth knowing before anyone writes a
script against `hyprctl dispatch` on this image.

## 8. What this settles, and what it does not

**Settles.** The runtime gate is `org.a11y.Status` on the session bus. A late
enable retrofits a running process, including adding surfaces to a tree already
published. The gsetting is one *writer* of that gate — `at-spi-bus-launcher`
mirrors it into `IsEnabled` — and is not itself the gate.

**Does not settle.** Whether APEX should ship the gsetting on, or set
`QT_LINUX_ACCESSIBILITY_ALWAYS_ON` for the shell, is a product question this
does not answer: a screen reader does not need either, because Orca sets
`ScreenReaderEnabled` itself, but an auditor or a CI probe that is not a screen
reader still sees an empty bus. `katana-final-qual` already makes that point and
this run supports it.

**Also not settled, and it is the next real P2-003 task.** Every frame this run
saw is **empty** — `name=`, `desc=`, no `Action` interface, nothing beneath it.
The bar publishes surfaces and no controls, which is exactly what
`katana-final-qual` §4.1 reported on labwc. The gate is no longer the thing
standing between a blind user and the shell; the missing markup is.
