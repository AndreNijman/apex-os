# L-003 — the PCR 7 binding, measured in a real boot

Unit `luks-boot` (which also owns L-002), round 39, 2026-09-21.
Branch `task/luks-boot`. Host: katana, `/var/lab/scratch/luks-boot/`.
Predecessor record: `L-003-enrolment-20260920.md` (unit `luks-enroll`), which
built the shipped script and measured its behaviour host-side.

## What this round adds

The `luks-pcr7` guest scenario landed on 2026-09-21 as `b9844c8e` (merge
`34132080`) and **had never been run**. It now runs, and it is green:

```
== boot-v2 VM harness: 26 passed, 0 failed ==
EXIT_CODE=0            START 17:33:40 +08:00   END 17:36:31 +08:00
```

Three guest boots, each a real OVMF firmware boot with Secure Boot enforcing
and a software TPM, against a root staged from katana's own live APEX install
(`apex-stage-root`, kernel `7.2.6-cachyos1.fc43.x86_64`).

This is the first time the **shipped** `/usr/libexec/apex-luks-enroll` has been
run inside a real boot against a **live** PCR 7 — every earlier measurement was
host-side, against a Secure Boot state read from a fixture or a PCR 7 value
chosen by the test.

## Boot A — enrol, live, against this boot's own measurement

```
enroll-interpreter=/usr/bin/env present
enroll-interpreter-arg=bash present
tpm-device=present
secure-boot-byte=1
pcr7-pre-enroll=69E722B3756359AAE507D8D886174B6267C663001E6A96D448D4DB85F71B8F21
pcr11=8C975D9D1551BCD6F7DE4CA6D63D418748949FB780306288AED5EA6AA97AA3AE
enroll-exit=0
enroll-out: tpm2: enrolled binding=pcr7 pcrs=7 bank=sha256 \
            hash=91cd90cbef3cb73ad31775fbe69cb36f6112937d1b44634970b5a6b6eece3a39 pin=no
passphrase-after-enrol=SUCCESS
recovery-key=vjfvhjng-…-hgtfvguu   (71 bytes on disk)
```

PCR 7 was a real firmware measurement **before** the script ran, so this is not
systemd's "PCR policy effectively unenforced" trap with a good-looking hash on
top of an unextended register — the distinction `L-003-enrolment-20260920.md`
established host-side, now satisfied by a real boot rather than by a fixture.

`passphrase-after-enrol=SUCCESS` is new this round. Enrolment rewrites the
LUKS2 header, and "where safe" is not satisfied by an unlock that works if it
cost the user the way in they already had. It is proved in the same boot,
against the same volume, with `cryptsetup open --test-passphrase`.

### Which gate refused signed-pcr11, and why that is the interesting part

`probe_signed_pcr11` refuses in order: Secure Boot off, no `StubInfo` efivar,
no readable signing key, PCR 11 unmeasured. The scenario as written asserted
the **second**. What actually fires is the **third**:

```
not using signed-pcr11: the boot did not publish a PCR signing key
                        at /run/systemd/tpm2-pcr-public-key.pem
```

Gates one and two passing is itself a measurement: this guest booted with
Secure Boot enforcing **and** genuinely came up through sd-stub. So the only
thing standing between this lab and a signed-PCR-11 enrolment is building the
UKI with `--pcr-key` — the `luks-pcr7-signed` variant `luks-enroll-2.md`
proposed, whose precondition is now measured instead of assumed. The absence
of the other two refusals is asserted too, so the day either starts firing, the
scenario says so rather than passing quietly.

## Boot B — the binding reproduces across a TPM power cycle

A fresh `swtpm` process (`--flags startup-clear` zeroes every PCR) and a
**different** UKI, same varstore template and signing cert:

```
pcr7=69E722B3756359AAE507D8D886174B6267C663001E6A96D448D4DB85F71B8F21   (identical to boot A)
pcr11=E98E6270DBA8A38C6067C7924D94AE514C6FF394537C68C682D66B2E2F6F64DB  (differs from boot A)
pcr0=52172DA4DAC5EC8A415750924C91B796BB5EF26749D122655C41FD6DB1C12AD8
pcr-signature=<absent>
tpm-unlock=SUCCESS
plaintext-marker=written
```

The firmware re-extended PCR 7 to the same value on its own, so "reproducible"
is true across TPM sessions rather than only within one. PCR 11 moved while
PCR 7 held and the volume still unlocked — the slot really is bound to PCR 7,
not to whatever this particular UKI measures. No signature was present or
needed: this is a by-value binding, not a PolicyAuthorize one.

## Boot C — the firmware changes, the slot refuses, the user still gets in

A dbx revocation update (`DBXUpdate-20260630.x64.bin`) applied to a fresh
varstore with `virt-fw-vars --add-dbx`:

```
pcr7=C4681679813FF36D46DB3E7C191950D88F11DEDEC902BFBFE1137BF3629550D6   (moved)
pcr0=52172DA4DAC5EC8A415750924C91B796BB5EF26749D122655C41FD6DB1C12AD8   (unchanged)
cryptsetup: TPM policy does not match current system state.
tpm-unlock=REFUSED
recovery-unlock=SUCCESS
recovery-marker=found
```

PCR 7 moved and PCR 0 did not, which is what a dbx update should do. The TPM
slot refused — the binding working, not a fault. The recovery key then opened
the volume **in the same boot**, and `recovery-marker=found` says the plaintext
behind it is the same data, not merely that a mapper appeared.

That completes L-003's acceptance clause "recovery path validated" as a
measurement: the machine auto-unlocks, it stops auto-unlocking when the Secure
Boot policy changes, and the user is not locked out when it does.

## Three defects this run found, all in the lab, none in the shipped product

The scenario had never been executed, and none of these were visible without
executing it.

**1. `#!/usr/bin/env bash` made the shipped script unrunnable in an initramfs.**
The first boot reported `have-apex-luks-enroll=yes` and `enroll-exit=127`, with
`failed to run command '/usr/libexec/apex-luks-enroll': No such file or
directory`. Both lines were true: `execve()` returns ENOENT for a missing
**shebang interpreter**, and a real APEX initramfs carries `bash` but not
`env` (`lsinitrd`, kernel 7.2.6). Fixing only `env` would have bought one more
failed boot — the same derivation shows `dirname` (used on `$RECOVERY_OUT`
before anything is enrolled), `wc` (the key's length check) and `head` (the
failure report) are equally absent. All four are now bundled, and `ldd` runs
per bundled binary rather than for `systemd-cryptenroll` alone.

The command list was derived rather than eyeballed: every token in command
position in the shipped script that names a real executable, intersected with
the `usr/bin`+`usr/sbin` inventory of a real initramfs. **That inventory has a
trap of its own**: `lsinitrd` prints symlinks as `usr/bin/awk -> gawk`, so an
inventory built from the last field loses every symlinked name and reports
`awk` and the whole `tpm2_*` family as absent when they are present.

This is **not** a shipped defect. `apex-install` runs the helper inside a
`podman run --privileged … "$IMAGE" /usr/libexec/apex-luks-enroll` container
with full coreutils, never in an initramfs. It would become one the day
enrolment is moved into a dracut module.

**2. The scenario aborted after boot A by copying a file onto itself.**
`cp "$ser" "$WORK/serial-pcr7-a.log"` where `vm_boot --serial` had already
written that exact path: `cp` exits non-zero with "are the same file", and the
file runs `set -euo pipefail`. Boots B and C — the reproduction and the whole
recovery arm — never ran. All three copies removed.

**3. A trailing newline made a correct recovery key read as a wrong one.**
Boot C's recovery unlock failed with `Failed to activate with key file … (Key
data incorrect?)`. The key data was correct; the file was 72 bytes where a
recovery key is 71. `cryptsetup --key-file <regular file>` uses every byte as
the passphrase, and the scenario captured the key off the serial log and
rewrote it with `printf '%s\n'`.

Confirmed host-side rather than reasoned, on katana against that same volume
over a read-only loop device:

| key file | result |
|---|---|
| 72 bytes, trailing `\n` | **REFUSED** |
| same key, piped without the newline | **OPENS** |

Nothing shipped is affected: `apex-luks-enroll` writes the key through
`tr -d '[:space:]'` and `apex-install` re-strips with `tr -d '\r\n'` before
piping to `--test-passphrase`. `luks-pcr7` is the only scenario that recovers
the key from a guest's **serial log** rather than from the file the script
wrote, which is why it alone had this. The length is now asserted host-side at
capture time, so a regression costs a line of output instead of a four-minute
guest boot and a failure that reads like a broken recovery slot.

### An assertion that inspected nothing

`have-apex-luks-enroll=yes` was an `-x` test. It examined the file and said
nothing about whether the kernel could run it, which is exactly how a `127`
came to sit one line under a `yes`. The hook now reads the shebang in pure
shell — a probe for missing commands must not itself need one — and reports
whether the interpreter is present; the scenario fails on `MISSING`.

## What is still NOT shown

- **No installer-produced disk was used here.** The guest boots a UKI this lab
  built and signed. A disk `apex-install` writes boots GRUB + shim, so it has
  no sd-stub; the PCR 7 binding does not need one, but that combination has not
  been run end to end.
- **The installer has never called the real script in a test.** Production
  `apex-install` does (`installer/apex-install:2189`), but every installer
  suite substitutes a recovery-key-only stand-in via `APEX_LUKS_ENROLL_LOCAL`.
- **No silicon.** Every TPM here is swtpm. Neither machine's TPM was cleared or
  touched, and no real disk was encrypted.
- **signed-pcr11 remains untaken**, for the reason measured in boot A.

## A cosmetic defect worth recording

The bundled python3 prints `Could not find platform independent libraries
<prefix>` on every invocation — five or more times into the shipped script's
**stderr**, the stream its contract reserves for prose shown to a person. Every
parse returned the right answer, so this is noise rather than breakage, but it
is noise in a user-facing stream and it comes from the lab's bundle, not from
the image.

## Reproducing

```
ssh katana
cd /var/lab/scratch/luks-boot/apex-os && git checkout task/luks-boot
systemd-run --user --collect --unit=luks-pcr7 /var/lab/scratch/luks-boot/run.sh
```

`run.sh` wraps `podman run --rm --device /dev/kvm -v /var/lab/scratch/luks-boot:/work:z
localhost/apex-bootlab -c '… run-scenarios --work /work/out luks-pcr7'` and
appends a literal `EXIT_CODE=` line, so a later reader can tell a finished run
from a truncated one. It runs as a **systemd user unit**, not `nohup &`: a
backgrounded podman is SIGTERMed when an agent's process tree is torn down, and
still exits 0.
