## What was actually new

### 1. APEX picked the signed policy for itself

Every previous measurement of the signed PCR 11 binding in this tree was a
policy the **lab** enrolled, host-side, with a `systemd-cryptenroll` command
line the test chose (`luks-tpm`). That can show a signed token unseals. It
cannot show which binding the shipped `/usr/libexec/apex-luks-enroll` would
**choose**, because it never runs it.

`serial-pcr7s-a.log`, from the real shipped script running in a dracut
pre-mount hook inside a Secure-Boot-enforcing guest:

```
APEX-BOOTLAB: secure-boot-byte=1
APEX-BOOTLAB: pcr11=7ABDFF81ADEB57F15DEDDAE2F81747AB6459D8FF51B5C45BC2CEF07AF071C537
APEX-BOOTLAB: enroll-exit=0
APEX-BOOTLAB: enroll-out: tpm2: enrolled binding=signed-pcr11 pcrs=11 bank=sha256 hash=… pin=no
APEX-BOOTLAB: passphrase-after-enrol=SUCCESS
```

and **not one** of `probe_signed_pcr11`'s four refusals appeared on stderr. The
scenario asserts that absence on the shared prefix `not using signed-pcr11`, so
a gate added to the probe later is covered without anybody remembering to edit
the assertion.

`binding=` is not a string the script remembers writing. `tpm2_report` derives
it from the SHAPE of the LUKS2 token read back with
`cryptsetup luksDump --dump-json-metadata`: a token carrying `tpm2_pubkey_pcrs`
is a signed policy, a token carrying `tpm2-pcrs` alone is a value policy. The
same function refuses a token that binds no PCRs at all and refuses a zero
policy hash — the trap systemd 258.10's `--tpm2-device=auto` with no PCR
argument walks straight into.

### 2. The reason signed-pcr11 outranks pcr7, finally justified by APEX's own token

The shipped table puts `signed-pcr11` above `pcr7` on one claim: it **survives a
kernel update**, where a value-bound policy meets the user at the one moment
they cannot get a shell. Boot B tests exactly that. A different UKI, signed by
the same PCR key, different `.cmdline` — which sd-stub measures into PCR 11
precisely as it would a new `.linux`:

```
serial-pcr7s-a.log  pcr11=7ABDFF81ADEB57F15DEDDAE2F81747AB6459D8FF51B5C45BC2CEF07AF071C537
serial-pcr7s-b.log  pcr11=DD9A93720200654A53C03E57B8AAA79736BAC91D54E2FE1B02C3CFAED39F7545
                    pcr-signature=/run/systemd/tpm2-pcr-signature.json
                    tpm-unlock=SUCCESS
                    plaintext-marker=written
```

**PCR 11 moved, and the volume still unsealed.** A value-bound policy would have
refused. The scenario compares the two values FIRST and only makes the claim
when they differ, because two identical measurements would make boot B a second
copy of boot A and prove nothing.

### 3. Recovery is not optional, and was proved in the same boot

`passphrase-after-enrol=SUCCESS` is `cryptsetup open --test-passphrase` against
the same volume, after the enrolment rewrote its header. A recovery key was
generated and captured at 71 bytes with no trailing newline — checked host-side
at capture time, because `cryptsetup --key-file <regular file>` uses every byte
of the file as the passphrase and one `\n` turns a correct key into a wrong one.

### 4. The refusal arm (`4029965f`)

Boot B on its own has two explanations: the signature satisfied a
PolicyAuthorize, or the policy constrains nothing and would unseal for anybody.
`tpm2_report` rules the second out by inspection. Boot C rules it out by
measurement — a UKI whose PCR policy is signed by the **foreign** key, with
`--pcrpkey` left as the REAL public key so the refusal is isolated to the
signature rather than to key identity. It asserts a signature **was** published
before asserting the refusal, because "the signature did not verify" and "no
signature was offered" read identically otherwise, then recovers with boot A's
key in that same refused boot and reads back the plaintext marker boot B wrote.

`serial-pcr7s-c.log`, measured:

```
APEX-BOOTLAB: pcr-signature=/run/systemd/tpm2-pcr-signature.json
APEX-BOOTLAB: tpm-unlock=REFUSED
APEX-BOOTLAB: recovery-unlock=SUCCESS
APEX-BOOTLAB: recovery-marker=found
```

with `tpm-unlock=SUCCESS` asserted ABSENT. Refused by the TPM, opened with the
recovery key, same plaintext — in one boot, so the two are joined rather than
left as separate green checks that never met.

## What this does NOT close

L-003 stays **partial**. The integration gap is unchanged and is not something
this scenario can reach:

- No test has ever run the real `apex-luks-enroll` through `apex-install`.
  Every installer suite stands it in with an `APEX_LUKS_ENROLL_LOCAL`
  recovery-only stub.
- No **installer-produced** disk has been TPM-auto-unlocked. `apex-install`
  writes GRUB + shim, not a UKI, so there is no sd-stub on it, no PCR 11
  measurement, and nothing for `probe_signed_pcr11` to bind to. Both of this
  scenario's bindings are therefore forward-looking with respect to the disk
  APEX ships today — which is exactly why `luks-pcr7` (the pcr7 fallthrough)
  and `luks-pcr7-signed` (the sd-boot future) both exist.

That pair is what would take L-003 to `done`.
