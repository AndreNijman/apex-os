# L-003 — the production LUKS enrolment path

2026-09-20. Unit `luks-enroll`, branch `task/luks-enroll` off `roadmap/v2.2`
@ `303221d5`. Nothing here was run on a real encrypted disk: every volume in
this record is a loopback image file inside the boot-lab container on katana,
and every TPM is a software TPM on a TCP port. **Katana's TPM was not cleared
and not touched.** The L16 was used only to edit and commit.

Versions, from the lab image: systemd 258.10-1.fc43, cryptsetup 2.8.7,
tpm2-tools 5.7, swtpm, podman on katana (20 cores, Fedora 43 base).

## 1. What was built

| path | what it is |
| --- | --- |
| `files/system/libexec/apex-luks-enroll` | **new.** The shipped path. `Containerfile.base` installs it at `/usr/libexec/apex-luks-enroll` |
| `Containerfile.base` | the COPY, plus four build-time assertions (§6) |

The lab script was **not** promoted by copying. It hardcodes a signed PCR 11
policy, which works there because the lab always builds a UKI for sd-stub to
measure into PCR 11. A shipped machine may or may not have one, so which
binding is right is a question for the running system: `policy_select` is a
best-first table (`signed-pcr11`, then `pcr7`), each entry probing for itself
and recording why it was passed over.

## 2. The interface

```
/usr/libexec/apex-luks-enroll --device <dev> --recovery-out <path>
```

stdout is machine lines, `key: value`. stderr is prose for a person. Exit 0
whenever the recovery key is enrolled — a declined TPM slot is **not** a failed
install. `--check` alone uses exit 2 for "there is a TPM slot and it is unsafe".

It does not format, partition or create anything: the volume must already be
LUKS2 and the caller must already hold a key for it.

## 3. What a machine gets

| case | key slots | machine line | what the user is told |
| --- | --- | --- | --- |
| Secure Boot ON, TPM, no sd-stub | passphrase + recovery + TPM2 on PCR 7 | `tpm2: enrolled binding=pcr7 pcrs=7 bank=sha256 hash=<64 hex> pin=no` | it unlocks itself; it will ask for the recovery key after a Secure Boot key change or a TPM clear, and that is the binding working |
| Secure Boot OFF | passphrase + recovery | `tpm2: declined reason=secure-boot-off` | that Secure Boot is off, why a TPM slot there would provide nothing, the command to re-run after enabling it, and that `--with-pin` is the other route |
| no TPM | passphrase + recovery | `tpm2: declined reason=no-tpm2-device` | that neither `/dev/tpmrm0` nor `/dev/tpm0` exists, to look for "PTT", "fTPM" or "Security Device" in the firmware setup, and the command to re-run |

Also reachable and **tested**: `setup-mode` (SecureBoot reads 1 but the
firmware has no platform key), `pcr-uninitialised` (Secure Boot claims on but
PCR 7 was never extended — the slot is created and then removed again), and
`tpm2-enrolment-failed` (exercised incidentally by the `enroll-no-tpm` control
arm). Reachable and **untested**: `not-uefi`, `no-secureboot-variable`. Present
but unreachable while `probe_pcr7` succeeds for every Secure-Boot-on machine:
`no-usable-policy`.

## 4. Measured in the lab — the findings

1. **A bare `systemd-cryptenroll --tpm2-device=<dev>` with no PCR selection**
   prints `New TPM2 token enrolled as key slot 1`, **exits 0**, and writes:
   `tpm2-pcrs: []`, **no `tpm2-pcr-bank` field at all**, `tpm2-policy-hash:
   0000…0000` (64 zeros). Sealed to the TPM storage key and nothing else. This
   reproduces L-001's silicon finding in the lab, so it is now a property of
   systemd 258.10 rather than of one machine.
2. **`--tpm2-pcrs=7` against a PCR 7 that is still 64 zeros produces a
   PERFECTLY GOOD-LOOKING NON-ZERO POLICY HASH** (`8b5682d81b29435d…`) while
   printing `PCR policy effectively unenforced!` on stderr. **The policy-hash
   assertion cannot catch this case.** Both checks are needed. With PCR 7
   extended the warning is absent and the hash is `51a6f4a83e15f72f…`.
3. **`--tpm2-pcrs=7:sha256` parses.** Plain `7` is used and the bank is
   asserted from the token instead.
4. **`systemd-cryptenroll --unlock-tpm2-device=<dev>` succeeds only on a real
   unseal.** After `tpm2_pcrextend 7` it answers *"TPM policy does not match
   current system state. Either system has been tempered with or policy
   out-of-date: Operation not permitted"*. So the security property is testable
   with no guest and no device-mapper.
5. **`cryptsetup open --test-passphrase --key-file` needs no device-mapper**, so
   every recovery-key check runs unprivileged in the container.
6. **The TPM2 PIN env var is `NEWPIN`**, not `NEWPASSWORD` — read out of the
   binary's strings. Without it, `--tpm2-with-pin=yes` PROMPTS, and the harness
   sat on that prompt for seven minutes with fifteen green lines above it before
   it was killed by hand. Every invocation in the scenarios now has stdin on
   `/dev/null`; a test that can block becomes a CI timeout somebody reads as
   flakiness.
7. **tpm2-tools falls back to `/dev/tpmrm0` when `TPM2TOOLS_TCTI` is unset**, so
   the lockout-property read has to be pointed at the same TPM being enrolled —
   the symptom was `--with-pin` reporting "would not report its lockout
   properties" for a part that reports them fine. And **tpm2-tools 5.7 prints
   `TPM2_PT_MAX_AUTH_FAIL: 0x3` on ONE line**; the older `raw:`-on-the-next-line
   parser read that as `unknown`.
8. **podman drops CAP_MKNOD**, so the lab cannot `mknod` a TPM device node. A
   **symlink to `/dev/null`** satisfies `-c`, needs no capability, and cannot be
   mistaken for a TPM by anything that opens it. Without it, the present-node
   arm of the no-TPM check could not run at all.
9. **LUKS2 token field names are mixed and both spellings are real**:
   `tpm2-pcrs`, `tpm2-pcr-bank`, `tpm2-policy-hash`, `tpm2-blob`,
   `tpm2-primary-alg` hyphenated; `tpm2_srk`, `tpm2_pubkey`,
   `tpm2_pubkey_pcrs` underscored. Read off a live `cryptsetup luksDump
   --dump-json-metadata`, not guessed.
10. **`tpm2-tools` reaches the image only as a dependency of `clevis`**
    (`rpm -q --whatrequires tpm2-tools` → `clevis-21-12.fc43.x86_64`) and is
    pinned by no line in `Containerfile.core`. The build asserts
    `test -x /usr/bin/tpm2_getcap` with a comment saying what to do when that
    chain breaks: add it to core explicitly, do not delete the assertion.
11. **The PCR 11 denial of service does not go away with a UKI.**
    `tpm2_pcrextend 11` works from plain root and `tpm2_pcrreset 11` answers
    `bad locality` (measured on katana 2026-09-19), so any root process can deny
    every PCR-11-bound unlock until the next reboot. After sd-stub has extended
    PCR 11 an attacker can no longer *choose* the value, which narrows it; the
    denial remains.

## 5. The scenarios

`files/scripts/boot-v2/run-scenarios`, in `ALL` so a default run cannot skip
them. They boot no guest: what they have to prove is what a LUKS2 header ends
up holding, and a header is the same object however it was written.

```
== boot-v2 VM harness: 75 passed, 0 failed ==
```

- **`enroll-sb-on`** — Secure Boot fixture on, PCR 7 pre-extended to a value no
  firmware would produce. Asserts the exact binding line, `pin=no`, a policy
  hash that is a real 32-byte digest, that `--check` accepts the volume, that
  the TPM2 slot **unseals**, that it **refuses** once PCR 7 moves, that the
  recovery key opens the volume and a mutated one does not, that `--with-pin`
  sets a PIN and prints this part's lockout numbers, and that the script SAID
  why it passed over `signed-pcr11`. Plus the branch the policy hash cannot
  catch: a second software TPM whose PCR 7 was never extended must be refused
  as `pcr-uninitialised` **and the slot removed again**.
- **`enroll-sb-off`** — exit 0, `declined reason=secure-boot-off`, tokens
  exactly `systemd-recovery`, the prose says Secure Boot is off in those words
  and says what to change and where and names the recovery file, `--check`
  independently reports `tpm2: absent`, the recovery key works and a mutated one
  does not. Plus the setup-mode arm: `SecureBoot=1` with `SetupMode=1` is still
  refused.
- **`enroll-no-tpm`** — `declined reason=no-tpm2-device`, the prose names PTT
  and fTPM, the recovery key works. Both fixture controls: the with-node and
  without-node roots really differ, and a **present** node does *not* decline as
  `no-tpm2-device`.
- **`enroll-bare-policy`** — the negative control. A volume is enrolled
  **without** the production script, the bare way; the control is verified
  known-bad (`pcrs=[] hash=<64 zeros>`) rather than assumed; `--check` must exit
  **2** and explain itself and offer a way forward. Then the other arm on the
  same gate — `--check` accepts a good volume — and the repair path: running the
  production script over the bad token replaces it rather than stacking a second
  one beside it.

Mutated-key control on every recovery check: the first character is changed to
**another modhex character** (`c`→`b`, else →`c`). `z` is not in systemd's
modhex alphabet, so a `z` mutant would be refused for being malformed and would
leave "a wrong key is refused" untested while looking green.

## 6. The build-time and per-PR assertions, and their controls

`Containerfile.base` refuses to build an image whose
`/usr/libexec/apex-luks-enroll`:

- binds PCR 0 on an executable line,
- names a TPM2 device on an executable line with no PCR selection beside it,
- runs a boot-path command (`bootctl install`, `bootupctl`, `grub2-install`,
  `efibootmgr -c/-B/-o`).

apply errexit to an inverted command, which is how 46 refusals in this tree

## 8. The disagreement — signed PCR 11 still needs Secure Boot

The orchestrator's mid-round updates said a signed PCR 11 policy "does not
require Secure Boot to be enabled". The implementation does not follow that
clause, and the reason is measurement rather than preference.

A signed policy is a TPM2 `PolicyAuthorize` over a `PolicyPCR` digest for PCR
11. The **unsealing side** supplies the signature; it ships in the UKI's
`.pcrsig` section, on the ESP, and is therefore public. The TPM then requires
PCR 11 to hold the signed value V. PCR 11 starts at zero on every boot, and
`tpm2_pcrextend 11` succeeds from plain root while `tpm2_pcrreset 11` answers
`bad locality` — measured on katana, 2026-09-19. Every digest that composes V is
public too: hashes of the UKI's own sections and of systemd's phase strings. So
an attacker who can boot **any** kernel extends PCR 11 to V from their own
userspace, presents the public signature, and unseals. Nothing in that chain
needs APEX's private PCR key, and **building our own kernel does not change it**
— the attacker does not need our kernel, only our PCR value, which is computable
from files they can read.

Two independent records in this repository already say the same thing:

- `ROADMAP/evidence/L-001-katana-tpm-20260919.md` §3.1 — systemd itself calls a
  policy bound to an unextended register "effectively unenforced", *"because
  anyone can extend it to anything"*.
- `files/scripts/boot-v2/apex-luks-enroll`'s own header, written when the lab
  path was built: *"What stops an attacker substituting their own UKI is Secure
  Boot enforcing."*

Signed PCR 11's advantage over PCR 7 is real, large, and a **different**
advantage: it survives kernel updates, where a value-bound policy meets the user
at the one moment they cannot get a shell. That is why it is first in the table.

**The seam the orchestrator asked for is built.** Nothing hardcodes PCR 7: both
`probe_signed_pcr11` and `probe_pcr7` test Secure Boot for themselves, and the
`secure-boot-off` refusal is what the table saying no reduces to when Secure
Boot is the reason every binding said no. A binding added later that genuinely
does not need Secure Boot is selected without that branch being touched, and
overruling this judgement is one clause in one probe. For a machine that will
not enable Secure Boot, `--with-pin` is the honest route: it puts a secret in
front of the unseal that an attacker does not have.

**If the judgement is overruled, the counter-argument has to explain how the
attacker is stopped from replaying the extends.** One could not be constructed
here.

## 9. What this does NOT prove

- **The in-BOOT half of the PCR 7 binding.** The scenarios prove what the header
  holds and that the slot unseals and stops unsealing when PCR 7 moves, all
  host-side. `luks-tpm` boots a real guest, but against the lab's signed PCR 11
  policy and a UKI, which is not what a shipped machine gets today. A guest
  scenario that boots a PCR-7-bound volume needs a staged APEX root and belongs
  in `STAGED`. **This is the largest remaining hole.**
- **`probe_signed_pcr11` has never been exercised.** Nothing in the lab runs the
  shipped script from inside a UKI guest, so the branch is reachable, asserted
  structurally, and never taken. When sd-stub ships, a fifth scenario runs it
  under one.
- **The installer.** L-002's, and not this unit's. Nothing here was called by an
  installer.
- **No image build was run.** The `Containerfile.base` stanza is checked by
  `check-containerfile-assertions.sh` (which classes `test -x` on an image path
  as UNRESOLVED, not as a pass) and by hand against mutants.
- **Nothing on silicon.** Every TPM in this record is swtpm. L-001 has the
  silicon work.

## 10. Status

**L-003 stays `blocked`.** Its acceptance is "Measured boot + TPM unlock +
recovery path validated", and it depends on L-002. The recovery path is
validated in all three cases with mutated-key controls; TPM unlock is validated
host-side including the refusal when PCR 7 moves; measured boot for the binding
a shipped machine actually gets is **not** validated, and the installer that
would call this is somebody else's item.
