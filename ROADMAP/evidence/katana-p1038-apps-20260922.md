# katana: P1-038's applications are installed, 2026-09-22

P1-038 has read "18 matrix rows needing real applications on a real session"
since round 13, with the note that it "cannot be done headless and cannot be
done on the L16 while Andre is using it". Andre gave standing permission to use
katana, so the applications are now there.

## What is on katana now

| | |
|---|---|
| RPM, in the system extension | `obs`, `libreoffice`, `blender`, `wine64`, `chromium-browser` |
| already present | `firefox`, `steam`, `gamescope` |
| Flatpak | `com.discordapp.Discord`, `com.visualstudio.code` |
| not installed | JetBrains (proprietary toolbox, not worth the disk for one row) |

The extension went from 535,928,832 bytes to **3.8 GB across 692 packages**. It
was backed up to `/var/lib/apex-user.raw.bak-20260922` first and the SHA
compared, because that file is what holds Steam's 219 packages and this engine
has a history.

## Two findings, one of them a real defect

**`wine` and `chromium` are not binary names on Fedora.** The install looked
like it had failed until the check was done properly: `/usr/bin/wine64`,
`wineboot`, `winedbg` and `/usr/bin/chromium-browser` are all present. A
`command -v wine` that answers ABSENT is a wrong question, not a failed
install — worth writing down because the matrix rows will ask the same question.

**A Flatpak-only name failed the whole dnf transaction.** `apex install
obs-studio discord code libreoffice blender wine chromium` installed Discord as
a Flatpak and then died: `code` has no RPM in any enabled repository, the
routing kept it for dnf, and dnf refused the entire set — so the other five did
not install either. `apex resolve code` had already said "APEX would use:
flatpak", so the tool disagreed with itself. Fixed in the same session; see the
`bare_name_route` commit and its four assertions.

## What this does and does not close

It removes the **prerequisite**, not the measurement. The 18 rows still need a
real session to run in, and the rows about screen sharing, portals and
XWayland need a compositor with a user at it or a harness that can stand in.
Nothing here claims a row passed.

The rows that were blocked on hardware rather than software are unchanged:
VRR cannot be tested on katana at all (no connector exposes `vrr_capable`),
physical output hotplug needs somebody at the machine, and a second display is
still a second display.
