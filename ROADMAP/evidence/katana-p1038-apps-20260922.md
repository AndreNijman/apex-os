# katana: P1-038's applications are installed, 2026-09-22

P1-038 has read "18 matrix rows needing real applications on a real session"
since round 13, with the note that it "cannot be done headless and cannot be
done on the L16 while Andre is using it". Andre gave standing permission to use
katana, so the applications are now there.

## What is on katana now

| | |
|---|---|
| RPM, in the system extension | `obs`, `libreoffice`, `blender`, `chromium-browser` |
| RPM, installed but **NON-FUNCTIONAL** | `wine` — see the correction below |
| already present | `firefox`, `steam`, `gamescope` |
| Flatpak | `com.discordapp.Discord`, `com.visualstudio.code` |

The extension went from 535,928,832 bytes to **3.8 GB across 692 packages**. It
was backed up to `/var/lib/apex-user.raw.bak-20260922` first and the SHA
compared, because that file is what holds Steam's 219 packages and this engine
has a history.

## Two findings, one of them a real defect

**`wine` and `chromium` are not binary names on Fedora.** The install looked
like it had failed until the check was done properly: `/usr/bin/wine64`,
`wineboot`, `winedbg` and `/usr/bin/chromium-browser` are all present. A
`command -v wine` that answers ABSENT is a wrong question, not a failed
install — worth writing down because the matrix rows will ask the same question.

**A Flatpak-only name failed the whole dnf transaction.** `apex install
obs-studio discord code libreoffice blender wine chromium` installed Discord as
a Flatpak and then died: `code` has no RPM in any enabled repository, the
routing kept it for dnf, and dnf refused the entire set — so the other five did
not install either. `apex resolve code` had already said "APEX would use:
flatpak", so the tool disagreed with itself. Fixed in the same session; see the
`bare_name_route` commit and its four assertions.

## What this does and does not close

It removes the **prerequisite**, not the measurement. The 18 rows still need a
real session to run in, and the rows about screen sharing, portals and
XWayland need a compositor with a user at it or a harness that can stand in.
Nothing here claims a row passed.

The rows that were blocked on hardware rather than software are unchanged:
VRR cannot be tested on katana at all (no connector exposes `vrr_capable`),
physical output hotplug needs somebody at the machine, and a second display is
still a second display.

# CORRECTION 2026-09-22 — wine is installed and does not work, and the cause is general

A peer session measured `wine64` dying with `could not exec wineserver` and was
right. This file said wine was installed; it is, and it cannot run. Worse, the
first two explanations — mine and the peer's — were both wrong, so the sequence
is worth keeping.

## What is actually on the machine

```
/usr/bin/wine32, wine64, wineserver32, wineserver64   real files
/usr/bin/wine, /usr/bin/wineserver                     DO NOT EXIST
/usr/bin/wineboot, winecfg, wineconsole, winefile,
  winemine, winepath, winedbg, msidb, msiexec,
  notepad, regedit, regsvr32                           SYMLINKS -> wine  (dangling)
```

Twelve dangling symlinks in `/usr/bin`, every one of them pointing at a file
that was never created.

## Why three checks disagreed, which is the methodological half

- `ls /usr/bin | grep ^wine` listed `wineboot` — **`ls` does not follow symlinks**.
- `test -e /usr/bin/wineboot` said missing — **`test -e` does follow**, and the
  link dangles.
- `stat -c %s` said **4 bytes** — the length of the string `wine`, because
  `stat` on a symlink measures the link, not the target.

All three were right about different questions. The 4-byte answer is what gave
it away.

## The cause, checked against the package rather than guessed

Fedora's `wine-core` **owns** `/usr/bin/wine` and `/usr/bin/wineserver`, and its
scriptlets drive them through `alternatives` (`/usr/bin/alternatives --remove
wine /usr/bin/wine32`, and the matching `--install` on the way in).

`apex-pkg` builds the system extension by **extracting RPMs**. Extraction does
not run `%post`. So `alternatives` never runs, the two real targets are never
created, and every symlink that depends on them dangles.

**This is not a wine defect. It is a defect in how the extension is built, and
it applies to every package that publishes its binaries through
`alternatives`** — java, editors, `iptables`/`nftables` compatibility wrappers,
and anything else that uses the mechanism. Those packages install "successfully"
and then do not work.

It is also invisible to the obvious test: `command -v wine64` answers, `wine64
--version` prints `wine-11.0 (Staging)`, and only actually *running* something
fails.

## What this does to the P1-038 claim above

The Wine matrix row is **not** unblocked. The rest stand — `obs`,
`libreoffice`, `blender`, `chromium-browser` are real files that execute, and
Discord and VS Code are Flatpaks, which do not go through this path at all.
