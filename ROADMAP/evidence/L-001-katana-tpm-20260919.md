### 2.1 FINDING — the default enrolment on systemd 258.10 binds to NO PCRs

`systemd-cryptenroll --tpm2-device=auto` with no `--tpm2-pcrs=` produced a token
with:

```
tpm2-hash-pcrs:                     (empty)
tpm2-pcr-bank:    n/a
tpm2-policy-hash: 00 00 … 00        (32 zero bytes)
tpm2-pcrs (json): []
```

There is no PCR policy at all — the object is sealed to the SRK and nothing
else. Anything that can talk to the TPM can unseal it, including a different OS
booted on the same hardware. `--help` documents `--tpm2-pcrs=PCR1+PCR2+…` with
**no stated default**, so a reader cannot tell from the tool either.

**Checked rather than left as a universal: nothing in this tree relies on that
default.** `grep -rn "tpm2-device" files/ installer/ docs/ bootlab/ tests/`
finds twelve mentions and **four** actual enrolment call sites, and every one of
them names its PCRs explicitly — `files/scripts/boot-v2/apex-luks-enroll:160`
and `files/scripts/boot-v2/run-scenarios:1127` pass
`--tpm2-public-key-pcrs=11`; `run-scenarios:1276` and `:1510` pass
`--tpm2-pcrs=7:sha256=…` and `--tpm2-pcrs=0:sha256=…` for the by-value control
volumes. So this is a **guardrail for L-002, not a live defect**: the moment
something turns encryption on by default it must keep that property, and a test
must assert the enrolled token carries a policy rather than that the command
exited 0.

### 2.2 FINDING — enrolment did not touch Windows' TPM objects

`handles-persistent` before and after enrolment is the same five handles.
systemd stored the SRK **in the LUKS token** (`tpm2-srk: true`, a 328-byte
`tpm2_srk` field) rather than persisting one. It is **not** Windows' SRK: the
token's object and `0x81000001` are not byte-identical (328 vs 284 bytes) and

`0x81000001`'s published name exactly. So APEX's enrolment coexists with a
Windows-provisioned TPM without disturbing it. **PASS**, and a genuinely new
interop result.

## 4. The signed PCR 11 policy works on Intel PTT — PASS, and this is the headline

APEX chose a `PolicyAuthorize`-over-PCR-11 keyslot precisely so that a kernel
update does not break unlock. **That mechanism had only ever run against
`swtpm`.** It now runs on real Intel PTT silicon. Volume `vol5.img`,
`/dev/loop7`, enrolled with

```
sudo systemd-cryptenroll --tpm2-device=auto \
     --tpm2-public-key=/tmp/sig/pub.pem --tpm2-public-key-pcrs=11 /dev/loop7
→ New TPM2 token enrolled as key slot 1.   (tpm2-pubkey-pcrs: 11, tpm2-hash-pcrs: empty)
```

Signatures produced with `systemd-measure sign --current --bank=sha256
--phase= --private-key=… --public-key=…`.

| # | what was presented | observed | verdict |
|---|---|---|---|
| 4.1 | no signature at all | `Failed to load PCR signature`; mapper ABSENT | PASS (refusal) |
| 4.2 | correct key, signature over the **current** PCR 11 | mapper **present** | **PASS** |
| 4.3 | a **different** RSA key's signature (same policy digest) | `No signature for current PCR policy in TPM2 signature JSON`; mapper ABSENT — refused by systemd on the fingerprint | PASS |
| 4.4 | correct key's fingerprint + correct policy digest + **forged signature bytes** | `Esys_VerifySignature … ErrorCode (0x000002db)` → `Failed to unseal secret using TPM2`; mapper ABSENT | **PASS — refused by the TPM itself** |
| 4.5 | PCR 11 moved, old (valid) signature re-presented | `No signature for current PCR policy…`; mapper ABSENT | PASS |
| 4.6 | re-signed for the new PCR 11 value | mapper **present** | **PASS — this is the kernel-update property** |
| 4.7 | recovery key, throughout, regardless of PCR 11 | mapper present | PASS |

Row 4.4 is the one that needed hardware. `0x2db` is `TPM_RC_SIGNATURE`: Intel
PTT executed `TPM2_VerifySignature`, rejected a forged RSA signature and
therefore never produced the ticket `TPM2_PolicyAuthorize` needs. The refusal is
in the part, not in systemd's C. Rows 4.5/4.6 are the same pair of facts the lab
showed across two edk2 revisions, now shown on silicon: a signed policy survives
a state change **when the new state is signed**, and refuses when it is not.

The policy digest was cross-checked independently: `tpm2_startauthsession` +
`tpm2_policypcr -l sha256:11` computed `6d73bb9de6c56800d5022d30cdcb7515…`, and
`systemd-measure policy-digest --current --phase=` computed the same value for
the same PCR 11. Two implementations, one number.

## 5. FINDING — on a GRUB machine `systemd-pcrextend` refuses, silently, exit 0

This is the most consequential defect found on hardware, and it is not visible
in a lab guest that boots `sd-stub`.

```
$ sudo /usr/lib/systemd/systemd-pcrextend --bank=sha256 enter-initrd
Kernel stub did not measure kernel image into PCR 11, skipping userspace
measurement, too.
$ echo $?
0
```

PCR 11 before: `90F4B395…`. PCR 11 after: `90F4B395…`. **Nothing happened, and
the exit status says everything is fine.** Repeated for `leave-initrd` and
`sysinit` with the same result. There is no `/run/systemd/tpm2-pcr-signature.json`
and no `StubPcrKernelImage` EFI variable on this machine — only
`LoaderDevicePartUUID`, `LoaderInfo` and `LoaderSystemToken`, which shim/GRUB
set.

Consequences, in order of how much they matter:

1. **A boot-phase policy can never be satisfied on a GRUB machine.**
   `systemd-measure sign --current` (no `--phase=`) signs four policies, one per
   phase of the standard `enter-initrd → leave-initrd → sysinit → ready` chain.
   None of them can ever be reached, because the tool that would reach them
   declines to run. A machine enrolled that way is a machine whose TPM unlock
   never works — and the failure is at *boot*, not at enrolment.
2. **The silence is the defect.** Exit 0 with a message on stderr is a shape
   this repository has been bitten by repeatedly. Anything APEX builds on
   `systemd-pcrextend` must check that PCR 11 actually moved, not that the
   command exited 0.
3. **`systemd-pcrextend`'s refusal is policy, not capability.** The TPM itself
   accepts a PCR 11 extend from plain root:
   `sudo tpm2_pcrextend 11:sha256=…0002` took PCR 11 from `90F4B395…` to
   `9DEA5804…`, `rc=0`.

### 5.1 FINDING — a zero PCR 11 is a local denial-of-service, on silicon

`tpm2_pcrextend 11:…` from root moves PCR 11, and **PCR 11 cannot be reset**:

```
$ sudo tpm2_pcrreset 11
ERROR: Esys_PCR_Reset(0x907) - tpm:warn(2.0): bad locality
ERROR: Could not reset PCR index: 11
```

So on a machine where the boot path leaves PCR 11 at zero, any root process can
extend it to an arbitrary value, every PCR-11-bound keyslot stops unlocking, and
the only way back is a reboot. Measured, not reasoned: after the extend, the
`--tpm2-pcrs=11` volume refused with `TPM policy does not match current system
state` and the mapper was absent. On a machine that boots `sd-stub` this is far
less interesting, because PCR 11 is already extended past a value an attacker
can predict — which is one more argument for the UKI path in
`docs/boot-v2.md`, made from hardware rather than from first principles.

## 6. The dictionary-attack counter, on real silicon — PASS

A sealed object with an auth value, created and destroyed inside this run
(`tpm2_createprimary -C o` → `tpm2_create -p goodpin` → `tpm2_load`). **Capped
at two wrong attempts of a 32-attempt budget, deliberately.**

| # | command | observed | verdict |
|---|---|---|---|
| 6.1 | `tpm2_unseal -p goodpin` | `l001-da-secret` | PASS |
| 6.2 | `tpm2_unseal -p WRONG1` | `Esys_Unseal(0x98E) … the authorization HMAC check failed and DA counter incremented`; `LOCKOUT_COUNTER 0x0 → 0x1` | PASS |
| 6.3 | `tpm2_unseal -p WRONG2` | same error; `LOCKOUT_COUNTER 0x1 → 0x2` | PASS |
| 6.4 | `tpm2_unseal -p goodpin` again | secret returned, `LOCKOUT_COUNTER` **stays 0x2** | PASS |

**A successful authorisation does not clear the counter on this part.** Only the
2-hour `LOCKOUT_INTERVAL` decay or `TPM2_DictionaryAttackLockReset` does, and
the latter needs `lockoutAuth`, which Windows holds (§7). So on this hardware a
user who mistypes a TPM PIN 32 times — across days, with successful unlocks in
between — puts the TPM into lockout for up to 24 hours, and **APEX would have no
way to reset it**. That is a product fact about `--tpm2-with-pin` that swtpm's
defaults do not surface.

Counter left at `0x2` of `0x20`, `inLockout: 0`, decaying to `0x0` within 4
hours. Recorded rather than hidden because it is shared state with Windows.

### 7.1 What it would take, so the decision is one word

**The clear can be done entirely over SSH. Nobody needs to be at the machine.**
That was not known before this run:

```
$ cat /sys/class/tpm/tpm0/ppi/version        → 1.3
$ cat /sys/class/tpm/tpm0/ppi/tcg_operations → …
   5  4: User not required          ← operation 5 is Clear
$ cat /sys/class/tpm/tpm0/ppi/transition_action → 2: Reboot
```

MSI's firmware answers `GetUserConfirmationStatusForRequest(5)` with **4 —
allowed, physically present user not required**. So:

```bash
echo 5 | sudo tee /sys/class/tpm/tpm0/ppi/request   # ask firmware to clear
sudo systemctl reboot                               # firmware performs TPM2_Clear during POST
```

and after the reboot: `lockoutAuthSet` back to `0`, the five persistent handles
gone, the eight OS NV indices gone, the manufacturer `0x1C000xx` certificates
still there, and `vol1.img`'s TPM unlock refused while its recovery key still
opens it. That is Run 2 of `docs/boot-v2.md`, complete, in two commands.

**Two things follow that are findings in their own right, independent of whether
anyone ever runs it:**

- `tpm2_clear` over the resource manager is **not** available on this machine.
  `lockoutAuthSet` is 1, so the lockout hierarchy is password-protected and the
  OS-side clear the documentation warns against cannot be reached anyway. Not
  attempted: a failed `lockoutAuth` disables that hierarchy for
  `LOCKOUT_RECOVERY` = **24 hours**, which would be a real side effect on
  Windows for zero information.

### 15.3 FINDING — one "OS" NV index survived, and it is platform-created

§7 listed nine indices outside the manufacturer `0x1C000xx` set and called them
"eight OS-created NV indices". The clear settles the arithmetic: **eight were
destroyed and one survived.**

Destroyed: `0x1410001`, `0x1410002`, `0x1410003`, `0x1800100`, `0x1810008`,
`0x1820002`, `0x1880001`, `0x1880011`.

Survived: `0x1802006`, and the four manufacturer certificates
`0x1C00002`, `0x1C0000A`, `0x1C00016`, `0x1C00100`.

Read out of the part rather than reasoned:

```
0x1802006:
  hash algorithm: sha256      size: 16
  attributes: ppwrite|authwrite|ppread|authread|no_da|written|platformcreate
  value: 0x62050005
```

`platformcreate` is exactly the bit `TPM2_Clear` honours — platform-created
indices survive. So `0x1802006` is firmware's, not an OS's, despite sitting in
the owner range where every other survivor is a `0x1C000xx` SHA-384
certificate. `TPM2_PT_HR_NV_INDEX` agrees and is the cheap check: `0x9` → `0x1`. It is not
counting by attribute — `0x1802006` is itself `platformcreate` and is the one it
still counts — but by range: the nine it counted before and the one it counts
now all sit outside the `0x1C000xx` block the four SHA-384 manufacturer
certificates occupy.

### 16.1 FINDING — the TPM returns two different codes, and systemd prints one string

`0x18b` and `0x1df` both surface to the user as the identical line
`Failed to unseal secret using TPM2: State not recoverable`. Decoded on the
machine with `tpm2_rc_decode`, they are different diagnoses:

```
0x18b → tpm:handle(1):the handle is not correct for the use     (TPM_RC_HANDLE)
0x1df → tpm:parameter(1):integrity check failed                 (TPM_RC_INTEGRITY)
```

Which one you get says **what is wrong**, and §17 shows both deliberately:

- **`0x18b` — the SRK handle `0x81000001` does not exist.** `Esys_Load` has no
  parent to load under. Recoverable without re-enrolment: recreate the SRK.
- **`0x1df` — the handle exists but the key under it is different**, because the
  storage primary seed was rolled. This is what a TPM clear actually does to a
  sealed object, and it is **not** recoverable without re-enrolment.

Both hide in an `ERROR:esys:` line that a script reading systemd's message alone
never sees. Anything APEX builds to explain a failed TPM unlock should read the
esys code, not the sentence.

   again (17.1e). That is why `0x18b` is recoverable and `0x1df` is not: a clear

   **not** Windows's — `000b38e620f17c92…` against the `000b4d8e76b8…` §2.2
   recorded before the clear.

the clear left it.

cheap extra it had not done; it is done now.

### 18.1 FINDING — a TPM clear permanently changes PCR 1 on this board

PCR 1 is the Host Platform Configuration register, and the firmware's own log
says what changed — the log grew:

| | before | after the clear | control boot |
|---|---|---|---|
| `binary_bios_measurements` | 42 328 B | **42 805 B** | **42 805 B** |
| events | 80 | **83** | **83** |
| events on PCR 1 | 8 | **11** | **11** |

Three events were added to PCR 1 and they stayed for the next boot, so this is a
new steady state rather than a one-off of the clear boot. PCR 1's eleven events
on both post-clear boots are `EV_CPU_MICROCODE`, `EV_EFI_HANDOFF_TABLES2`, seven
`EV_EFI_VARIABLE_BOOT` (`BootOrder` and `Boot0000`–`Boot0005`), `EV_SEPARATOR`
and `EV_PLATFORM_CONFIG_FLAGS` (`FeatureTME=0`).

Why it matters: **a keyslot sealed by value to PCR 1 would be destroyed by a TPM
clear twice over** — once because the seed changed, and again because the
register did. Nothing in APEX binds to PCR 1, and nothing should.

## 19. THE BOUNDARY CORRECTION — `nvme0n1` is not a stable name on this machine

This is the most important operational finding in this section and it is a
**correction to §0.1**, which is the safety argument the whole hardware
programme rests on.

§0.1 asserts the Windows disk was never written by quoting
`/sys/block/nvme0n1/stat`, and the standing instruction to every unit is *"never
write to `nvme0n1` — that is the Windows disk."* **The kernel's NVMe enumeration
order changed across the reboot**, and after it, `nvme0n1` is the **APEX** disk.

| identified by serial and PCI function, neither of which moves | boot `96c7fbc3` 08:43 (pre-clear) | boot `c93168d6` 10:28 (the clear) | boot `9dad77b0` 10:34 (**control**) |
|---|---|---|---|
| **Micron_2450_MTFDKBA1T0TFK**, SN `220534D1CB81`, 953.9 GB, PCI `0000:03:00.0` — **APEX**: `BIOS-BOOT` 1 M, `EFI-SYSTEM` 512 M vfat (PARTUUID `99af3362-a7ab-4317-b608-5330058f74b6`), `apex-root` btrfs (PARTUUID `e76ee78f-bf9c-4714-80c6-98cb1beb13c9`) | `nvme1n1` | `nvme1n1` | **`nvme0n1`** |
| **SPCC M.2 PCIe SSD**, SN `240023925111005`, 1.8 TB, PCI `0000:02:00.0` — **WINDOWS**: 200 M vfat ESP (PARTUUID `2ba9a2ea-4865-4d02-bdee-e52a8bf8b037`), MSR 16 M, 500 G NTFS, 845 M NTFS WinRE, 1.3 T ext4 `games` | `nvme0n1` | `nvme0n1` | **`nvme1n1`** |

Read out of the kernel log for all three boots rather than from the one that
looked wrong:

```
boot -2 08:43  nvme0: 0000:02:00.0   nvme1: 0000:03:00.0   apex-root on nvme1n1p3, games on nvme0n1p5
boot -1 10:28  nvme0: 0000:02:00.0   nvme1: 0000:03:00.0   apex-root on nvme1n1p3, games on nvme0n1p5
boot  0 10:34  nvme1: 0000:02:00.0   nvme0: 0000:03:00.0   apex-root on nvme0n1p3, games on nvme1n1p5
```

**The swap happened on the third boot — the control reboot — not on the clear.**
The clear reboot produced the same mapping as the boot before it, and the
perfectly ordinary reboot five minutes later produced the other one. That is
worth more than the version where the clear did it: **the names are not merely
changeable, they are changeable by nothing at all.** The two controllers are
probed asynchronously and the index falls out of the race; `0000:02:00.0` and
`0000:03:00.0` are what actually identify the parts.

**Consequences, in order:**

1. **"Never write to `nvme0n1`" is unsafe guidance on katana.** On the boot this
   section ran in, obeying it literally would have protected Windows's disk by
   accident and named APEX's. The durable identifiers are the serials above, the
   PARTUUIDs above, and the filesystem labels `apex-root` / `EFI-SYSTEM` /
   `games`. Future units: resolve the disk, do not name it.
2. **§0.1's conclusion is still true; its method is not reusable.** Everything
   in this section lived in a loopback file under `/var/lib/apex-tpm-qual2` on
   `apex-root`, wherever the kernel happened to call it. Resolved by serial
   rather than by name, the **Windows disk recorded exactly 7 writes /
   24 sectors on each of the two post-clear boots** — as `nvme0n1` on the clear
   boot and as `nvme1n1` on the control boot, the same disk both times. That is
   the baseline for a boot that mounts nothing on it but `games`, which
   `/etc/fstab` mounts rw by `UUID=a41fee21-…` as Andre's normal setup. Neither
   ESP was mounted in this run; no NTFS volume was mounted in this run at all.
3. **APEX's default boot entry lives on the Windows disk.** `Boot0000* APEX-OS
   Primary` is `HD(1,GPT,2ba9a2ea-…)/\EFI\APEX\SHIMX64.EFI`, and that PARTUUID
   is the **SPCC** disk's 200 MB ESP — the same partition `Boot0002* Windows
   Boot Manager` boots from. `BootCurrent` was `0000` on all three boots.
   `Boot0001* APEX-OS` is the APEX disk's own `EFI-SYSTEM`. So repairing or
   wiping the Windows ESP takes APEX's default boot entry with it, and
   `apex-boot-windows` is even more load-bearing than it looked.

### 21.1 Secure Boot — the same three rows, plus nothing from this section

§11 named exactly three rows to redo with Secure Boot on: the `--tpm2-pcrs=7`
volume, the PCR 7 value, and the event-log replay. **This section adds a fourth
only in the trivial sense** — §18.2's replay is the same replay, now against the
83-event log, so it is the §11 row and not a new one. Everything in §15–§20 is
PCR-7-independent by construction: the Run 2 volume was bound to **no PCRs at
all**, precisely so that a Secure Boot change could not be confused with a TPM
clear.

Carried forward because it keeps surprising people: **enabling Secure Boot will
not make `systemd-pcrextend` work.** It is a silent no-op on a GRUB machine
(§5) — exit 0, PCR 11 unchanged — and the fix is the `sd-stub`/UKI boot path,
not a firmware setting. PCR 11 read all zeros on both post-clear boots, which is
that same fact measured twice more.
