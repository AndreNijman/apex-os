# L-002 — the installer can encrypt a disk now

Unit `luks-installer`, 2026-09-20. apex-os branch `task/luks-installer`, from
`roadmap/v2.2` @ `303221d5`. Not landed.

L-002's acceptance is *"encryption default does not strand users across
qualified hardware and recovery cases"*. Everything below is organised around
that sentence; the design write-up is `docs/disk-encryption.md`.

---

## 1. The load-bearing gap, closed

Before this round, `installer/apex-install` mentioned `crypto_LUKS` exactly
once — at line 925, in a list of things it refuses to overwrite — and the tree
contained no `luksFormat` at all. "LUKS2 by default" had no mechanism.

It now has one. `encrypt=yes` in the answers file makes the engine build the
disk itself:

```
p1  1 GiB  ef00  EFI System Partition  FAT32                 -> /boot/efi
p2  1 GiB  8300  apex-boot             ext4, NOT encrypted   -> /boot
p4  1 MiB  ef02  BIOS boot partition   none                  -> nothing
p3  rest   8309  apex-luks             LUKS2 -> btrfs        -> /
```

p4 is out of numerical order because sgdisk allocates in option order, and the
numbers 1, 2 and 3 are written into the engine's discovery, its tests and the
recovery instructions. It is empty and unused on a UEFI machine; it exists
because a loopback install passes `bootc --generic-image` (see §5), and that
flag makes bootupd install the i386-pc GRUB component, which refuses to embed
`core.img` without it.

and install with `bootc install to-filesystem`.

**`bootc install to-disk --block-setup tpm2-luks` was rejected deliberately.**
It exists on this bootc (checked: `--block-setup <direct|tpm2-luks>`), and its
own help says it binds unlock to *"presence of the default tpm2 device"* — no
passphrase slot, no recovery slot. Combined with round 31's measurement that
`--tpm2-device=auto` binds to **no PCRs at all** on systemd 258, that is the
stranding case spelled as a flag. The reason is recorded in the code, not only
here.

## 2. The recovery key is created, PROVEN, and put in front of the user

Sequence, in this order, all before the ten-minute `bootc install`:

1. `cryptsetup luksFormat --type luks2 --pbkdf argon2id`, passphrase on stdin.
2. `/usr/libexec/apex-luks-enroll --device <dev> --recovery-out <file>`, run out
   of the **image being installed** via `podman run`, with the existing
   passphrase offered as `$PASSWORD` and on stdin.
3. `cryptsetup open --test-passphrase` with the **passphrase** and again with
   the **recovery key**. Either failing is a refusal, with the volume holding
   no data.
4. `cryptsetup luksDump` is read to see whether a `systemd-tpm2` token actually
   exists. Only then is `rd.luks.options=<uuid>=tpm2-device=auto` added — the
   installer never asserts a TPM keyslot it has not observed.

Delivery: a stdout protocol line the GUI shows on its last page behind a
checkbox that gates the **Reboot now** button, plus a 0600 file on the **live
USB's** ESP. Never the target's ESP or `/boot`; never through `note()` or
`log()`, because the install log is copied onto the stick in the clear on
failure.

## 3. The keyboard, measured

Two defects, both of which end at a prompt with no way back.

**(a) `/etc/vconsole.conf` was given an XKB layout name.** `loadkeys` does not
speak XKB. Measured against the keymap tree the shipped image carries
(`i18n_install_all="yes"`, so all 370 xkb-converted maps plus 336 legacy ones
are in the initramfs):

| | |
|---|---|
| XKB layouts offered by `xkeyboard-config` | **99** |
| whose raw name is **not** a loadable console keymap | **36** |
| unloadable after the new conversion | **0** |

The conversion prefers a keymap file of the layout's own name when one exists
(systemd's own order), falls back to `/usr/share/systemd/kbd-model-map`,
handles that table's multi-layout rows (`bg,us`, `gr,us`, `ge,us`) which a
plain equality test silently misses, and **validates the table's answer against
the keymap tree** — the table names a `ge` keymap Fedora 43's kbd does not
ship.

**(b) Nothing put the choice where the initramfs could read it.** The
initramfs is built in the image, `--no-hostonly`, and is identical on every
machine, so it cannot carry this machine's `/etc/vconsole.conf`. The one
per-machine channel that exists today is the kernel command line:
`systemd-vconsole-setup` parses `vconsole.keymap=` (read out of the binary the
image ships), and dracut's `i18n` module delegates to it rather than installing
its own cmdline hook (its `parse-i18n.sh` is absent from the built initramfs's
`hooks/cmdline`, confirmed by `lsinitrd`). An encrypted install now adds
`vconsole.keymap=` and `rd.vconsole.keymap=`, **and only when the resolved
console keymap is not exactly `us`**. The guard is on the console keymap, not
the XKB layout, so `us`+`dvorak` (which resolves to `us-dvorak`) does get the
argument; only a machine that lands on the kernel's built-in `us` gains no
argument that could later override `localectl set-keymap`.

**This mechanism dies with the sd-boot/UKI pivot** — a UKI's command line is
inside the signed PE. The replacement is a `vconsole.keymap` **systemd
credential** on the ESP (which `systemd-vconsole-setup` reads) or a UKI addon
contributing `.cmdline`. The seam is one function; see
`docs/disk-encryption.md`.

## 4. The supporting dependency, pinned

`rpm -q --whatrequires cryptsetup` on the shipped image returned exactly one
package: `clevis-luks`, which is itself only present because the bootc base
brings it. Two links of other people's decisions under the one binary that
opens an encrypted root. `cryptsetup` and `kbd` are now explicit in
`Containerfile.core` with **file-level** assertions, because `dnf5 -y install`
of an already-present package exits 0 and proves nothing.

`Containerfile.apex`'s final dracut run (the last one in the build) now asserts
inside the shipped initramfs: `systemd-cryptsetup`, dracut's `crypt` module,
`libcryptsetup-token-systemd-tpm2.so`, a non-`us` console keymap, and the new
hint module plus the symlink that pulls it in. All were derived by inspecting a
real initramfs first.

Plymouth's `message()` was `fun message (text) { }` in **both** themes —
accepted and dropped. It now draws, and `files/dracut/apex-unlock-hint` calls
it just before the passphrase prompt.

## 5. What was actually run

### Fast suite — `installer/test-installer-luks.sh`, in CI

**36 passed, 0 failed.** Every refusal; the conversion over all 99 layouts;
character-level checks read out of the shipped keymap data (the key right of T
types `y` on a US keymap and `z` on a German one; where US has Q, a French one
types `a`); six mutants, each a one-line inversion of the guard under test, all
of which flip the result.

`tests/check-suites-run-in-ci.sh` discovered `tests/test-*.sh` only — the
installer's suites are named by hand in `pr-validation.yml`, so a new one was
invisible to the gate that exists to catch exactly that. It now discovers
`installer/test-*.sh` too, mutation-tested both ways on a synthetic tree (a
suite in no workflow fails it; an exempt suite CI starts running fails it the
other way).

### A defect the live suite found that has nothing to do with encryption

Three complete installs reached *"Installation complete!"* and then died at

```
useradd: failure while writing changes to /etc/passwd
```

The message names the wrong thing twice. strace against the failed deployment:
the filesystem is rw, the deployment takes writes, `/etc/passwd-` is written in
full, and `/etc/passwd+` is never opened. Between those two steps `useradd`
calls `setfscreatecon()`, which writes `/proc/thread-self/attr/fscreate` —
because it asks `is_selinux_enabled()` **before** it chroots, and on Fedora that
answers yes. There is no `/proc` in the chroot, the open returns `ENOENT`,
shadow-utils turns it into `EACCES`, and the generic message above is all the
user sees.

`create_user_in()` now mounts `/proc` inside the deployment. It is shared with
the unencrypted path, so this was never an encryption bug — and installs from
the shipped ISO were never broken either, because `installer/build-live-iso.sh`
line 185 sets `selinux=0` on the live kernel command line, which makes
libselinux answer "disabled" before the chroot. The installer had an
undocumented dependency on a kernel argument in a different file; the day
anyone drops `selinux=0`, every install fails at the last step with a message
about `/etc/passwd`. That dependency is gone.

### Live suite — `installer/test-installer-luks-live.sh`, not in CI

A **real** `bootc install to-filesystem` of `localhost/apex-os:daily` onto a
**real LUKS2 volume** on a loopback file. It refuses any target that is not a
`/dev/loop*` node it created itself, and it snapshots this machine's UEFI boot
entries before and after and fails if they moved.

### Live suite — `installer/test-installer-luks-live.sh`, run 5, 2026-09-20 21:53

**The install itself failed at the NVRAM guard, and that failure is the most
valuable thing this unit produced.**

`engine exit=3 after 1129s`, which is `tests/lab/nvram-guard`'s
`nvram-changed`. The partitioning, LUKS2 format, enrolment, both-key
verification, btrfs and the whole `bootc install to-filesystem` ran; the
firmware step then did this to the machine running the test:

```
Installing bootloader via bootupd
Executing: "efibootmgr" "-b" "0000" "-B"
Executing: "efibootmgr" "--create" "--disk" "/dev/loop1" "--part" "1" ...
```

`Boot0000 APEX-OS` was moved from PARTUUID `1c417de2-…` (the real 600 MiB ESP,
`0x12c000` sectors) to `44577dfd-…`, `0x200000` sectors — the 1 GiB ESP inside
the loopback image. That is the 2026-09-20 incident, reproduced, four hours
after its guard landed.

**It happened with the efivars mask applied and logged.** The engine's own log
line, 19 minutes before the write:

```
21:53:35 nvram: /dev/loop1 is loop-backed (…/target.img) — masking
                /sys/firmware/efi/efivars in the install container
```

So the mask is not the guard, and this is the correction that matters:

* `bootc install` requires `--pid=host` and **re-enters the host's mount
  namespace** for the bootloader step. The container's own mounts are not
  where bootupd is looking.
* Checked rather than deduced, twice. A privileged container on this machine
  with **no** mask at all shows **zero** entries under
  `/sys/firmware/efi/efivars`, so the write cannot have gone through the
  container's namespace, masked or not. And `strings /usr/bin/bootc` in the
  shipped image carries `nsenter`, `/proc/1/ns/mnt`, `/proc/1/root` and
  `/proc/1/root/sys/fs/selinux/enforce` — bootc reaches PID 1's mount namespace
  by name, which is what `--pid=host` is there to allow.
* `tests/lab/bootc-install-lab` builds its argv with `--pid=host` and relies on
  the same mask. **Its first layer has the same hole.** Its second layer —
  nvram-guard — is what works, and it worked here.

The prevention is a bootc flag, not a mount: `bootc install --generic-image`,
whose own help says *"All bootloader types will be installed - Changes to the
system firmware will be skipped."* The ESP still gets a complete bootloader
including the removable-media path, so the image boots on the machine it is
built for. `apex-install` now passes it on all four `bootc install` call sites
whenever the target is loop-backed, and keeps the mask as a second layer that
is no longer mistaken for the first.

**The host was repaired in the same session**, from the guard's own `before`
snapshot: `efibootmgr -b 0000 -B` then `--create --disk /dev/nvme0n1 --part 1
--loader '\EFI\fedora\shimx64.efi' --label 'APEX-OS'`. `efibootmgr -v` is now
byte-identical to the pre-run snapshot, and the sha256 of `Boot0000`,
`Boot0004` and `BootOrder` in efivarfs match the before-snapshot exactly. The
machine was never rebooted in the broken state.

### Run 6 — the prevention works, and exposes a second thing the flag does

`nvram-guard` verdict: **`verified` — boot variables identical before and
after**. The prevention is proven. `bootupctl backend install` ran with
`--write-uuid --filesystem /sysroot /` and no `--update-firmware`, and no
`efibootmgr` line appears anywhere in the log.

The install then failed for a different reason the same flag causes. "All
bootloader types will be installed" includes i386-pc, and the encrypted layout
had no BIOS boot partition:

```
grub2-install: error: will not proceed with blocklists.
error: boot data installation failed: installing component BIOS to device /dev/loop2
```

with the volume already encrypted. The layout now carries a 1 MiB `ef02`
partition (§1), which is what `bootc install to-disk` builds for itself.

### Run 7 — the first encrypted install to complete end to end

`engine exit=0 after 328s`. 39 passed, 2 failed, and **both failures were in
the suite, not the engine**:

* `final protocol line is APEX-INSTALL-OK` read `tail -1` of a capture that now
  also holds nvram-guard's stderr, so it saw the guard's verdict line.
* `mutant: kernel argument 'vconsole.keymap'` passed when it should have
  failed. The engine writes **both** `rd.vconsole.keymap=X` and
  `vconsole.keymap=X`, and the first contains the second as a substring, so a
  `sed` without `/g` removed only the occurrence inside `rd.vconsole.keymap=`
  and the assertion still found the plain one. A mutant that passes is this
  suite's word for "the case proves nothing", and it took a live run to find.

Both fixed. **Run 8, with those two fixes and nothing else changed: `engine
exit=0 after 334s`, 41 passed, 0 failed, nvram-guard `verified`, and this
machine's `Boot0000` still names PARTUUID `1c417de2-…`.**

What runs 7 and 8 established, against a real LUKS2 volume on a loopback file:

* four partitions with the right types, `/boot` mountable with no key, a kernel
  and BLS entries on it;
* both the passphrase and the recovery key open the volume, a wrong passphrase
  is refused, and the volume opens for real rather than only under
  `--test-passphrase`;
* btrfs inside, with an ostree deployment on it and the user account created
  inside the encrypted root — the `/proc` fix for `useradd` holds;
* the recovery key on screen and in a 0600 file, the same key in both, and
  neither it nor the passphrase in the install log;
* `/etc/crypttab` and `/etc/vconsole.conf` correct, the BLS entry carrying
  `rd.luks.uuid`, `rd.luks.name`, `vconsole.keymap=bg_bds-utf8` and `root=`;
* `loader/credentials/vconsole.keymap.cred` on the ESP reading `bg_bds-utf8`;
* and this machine's UEFI boot entries unchanged, by two independent readers.

## 5b. A stranding case the passphrase rule was built on top of

`apex-install` restricts the disk passphrase to printable ASCII, and the
comment justifying that said: *"Every printable ASCII character is reachable on
every kbd keymap."* Measured across all 562 keymaps in the tree the image
ships, that is false for **15** of them, and every one is a machine whose owner
cannot type their own passphrase at the one prompt with no way back:

| keymaps | what they cannot produce, anywhere in the table |
| --- | --- |
| `hr-unicode` `rs-latinunicode` `ba-unicode` `me-latinunicode` `epo-legacy` | `q` `w` `x` `y` — e.g. Croatian keycode 16 is U+01C9, the ǉ digraph |
| `vn` `kz-latin` `cm-azerty` | the digit `1` — Vietnamese keycode 2 is ă |
| `it-geo` `ge-ergonomic` | Georgian; `z w r t s j c` and more |
| `fa` | Persian; almost no Latin at all |

`ru` is **not** among them, and the first version of this measurement said it
was. Its Cyrillic is on AltGr and `keycode 30 = +a` sits in the base plane; the
analysis that condemned it used a regular expression anchored to column 0 and
never saw the indented lines. The same anchoring bug made `fi` look like a
keyboard with no `1`, no `7` and no `e`. Both are mutants in the suite now, so
neither can come back silently.

The engine now resolves an **unlock keymap** separately from the console
keymap, before anything is erased. `keymap_can_type` reads the shipped keymap
file — following `include` up to three levels, because `jp106` gets every Latin
letter from `include "qwerty-layout"` and a parser that stopped at the top file
would condemn every Japanese keyboard — and answers `yes`, `unknown`, or
`no:<the characters it has no key for>`. On `no` the unlock prompt uses `us`,
the operator is told which characters forced it, and **only that prompt
changes**: the karg is omitted entirely when the unlock keymap is `us`, so the
initramfs falls back to the kernel's built-in table and the installed system
still reads its own `/etc/vconsole.conf`, which names the owner's layout.

`unknown` is a third answer and not a polite `no`: a keymap the parser did not
understand leaves the existing behaviour alone. Condemning a layout on a parse
failure would move a working machine to `us` silently, which is the same
stranding case pointed the other way.

Fourteen assertions in `installer/keymap-checks.sh`, including a sweep of the
whole tree (547 typeable / 15 not / 11 unreadable — the 11 are include
fragments like `keypad` and `windowkeys`, not layouts), the precondition that
`us` itself can type all 95 printable ASCII characters, and the two mutants
above.

## 6. What is NOT proven

* **No disk this engine produced has ever been booted.** Not once. Bootloader →
  initramfs → unlock prompt → ostree pivot → login has not been exercised, on a
  loopback file or anywhere else. Every claim below about the unlock prompt is a
  property of that unrun boot.
* **No keypress has been typed at a real unlock prompt.** The kernel-argument
  mechanism is verified by binary inspection and by reading the installed
  bootloader entry. The end-to-end property — a passphrase containing a
  character only a non-`us` layout produces unlocks the volume at boot — needs
  a VM with QMP `sendkey` and belongs to `files/scripts/boot-v2/run-scenarios`.
  It is requested from the `luks-enroll` unit and **has not been run**.
* **No TPM keyslot was enrolled by these runs.** A loopback file has no TPM,
  and TPM policy is `apex-luks-enroll`'s subject. The installer's side — observe
  the token, then and only then add `tpm2-device=auto` — is exercised only in
  its negative form here.
* **Nothing was encrypted on any real machine.** Every run was a loopback file
  under `/var/lab-scratch`.
