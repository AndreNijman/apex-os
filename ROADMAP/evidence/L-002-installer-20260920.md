# L-002 — the installer can encrypt a disk now

Unit `luks-installer`, 2026-09-20. apex-os branch `task/luks-installer`, from
`roadmap/v2.2` @ `303221d5`. Not landed.

L-002's acceptance is *"encryption default does not strand users across
qualified hardware and recovery cases"*. Everything below is organised around
that sentence; the design write-up is `docs/disk-encryption.md`.

---

## 1. The load-bearing gap, closed

Before this round, `installer/apex-install` mentioned `crypto_LUKS` exactly
once — at line 925, in a list of things it refuses to overwrite — and the tree
contained no `luksFormat` at all. "LUKS2 by default" had no mechanism.

It now has one. `encrypt=yes` in the answers file makes the engine build the
disk itself:

```
p1  1 GiB  ef00  EFI System Partition  FAT32                 -> /boot/efi
p2  1 GiB  8300  apex-boot             ext4, NOT encrypted   -> /boot
p3  rest   8309  apex-luks             LUKS2 -> btrfs        -> /
```

and install with `bootc install to-filesystem`.

**`bootc install to-disk --block-setup tpm2-luks` was rejected deliberately.**
It exists on this bootc (checked: `--block-setup <direct|tpm2-luks>`), and its
own help says it binds unlock to *"presence of the default tpm2 device"* — no
passphrase slot, no recovery slot. Combined with round 31's measurement that
`--tpm2-device=auto` binds to **no PCRs at all** on systemd 258, that is the
stranding case spelled as a flag. The reason is recorded in the code, not only
here.

## 2. The recovery key is created, PROVEN, and put in front of the user

Sequence, in this order, all before the ten-minute `bootc install`:

1. `cryptsetup luksFormat --type luks2 --pbkdf argon2id`, passphrase on stdin.
2. `/usr/libexec/apex-luks-enroll --device <dev> --recovery-out <file>`, run out
   of the **image being installed** via `podman run`, with the existing
   passphrase offered as `$PASSWORD` and on stdin.
3. `cryptsetup open --test-passphrase` with the **passphrase** and again with
   the **recovery key**. Either failing is a refusal, with the volume holding
   no data.
4. `cryptsetup luksDump` is read to see whether a `systemd-tpm2` token actually
   exists. Only then is `rd.luks.options=<uuid>=tpm2-device=auto` added — the
   installer never asserts a TPM keyslot it has not observed.

Delivery: a stdout protocol line the GUI shows on its last page behind a
checkbox that gates the **Reboot now** button, plus a 0600 file on the **live
USB's** ESP. Never the target's ESP or `/boot`; never through `note()` or
`log()`, because the install log is copied onto the stick in the clear on
failure.

## 3. The keyboard, measured

Two defects, both of which end at a prompt with no way back.

**(a) `/etc/vconsole.conf` was given an XKB layout name.** `loadkeys` does not
speak XKB. Measured against the keymap tree the shipped image carries
(`i18n_install_all="yes"`, so all 370 xkb-converted maps plus 336 legacy ones
are in the initramfs):

| | |
|---|---|
| XKB layouts offered by `xkeyboard-config` | **99** |
| whose raw name is **not** a loadable console keymap | **36** |
| unloadable after the new conversion | **0** |

The conversion prefers a keymap file of the layout's own name when one exists
(systemd's own order), falls back to `/usr/share/systemd/kbd-model-map`,
handles that table's multi-layout rows (`bg,us`, `gr,us`, `ge,us`) which a
plain equality test silently misses, and **validates the table's answer against
the keymap tree** — the table names a `ge` keymap Fedora 43's kbd does not
ship.

**(b) Nothing put the choice where the initramfs could read it.** The
initramfs is built in the image, `--no-hostonly`, and is identical on every
machine, so it cannot carry this machine's `/etc/vconsole.conf`. The one
per-machine channel that exists today is the kernel command line:
`systemd-vconsole-setup` parses `vconsole.keymap=` (read out of the binary the
image ships), and dracut's `i18n` module delegates to it rather than installing
its own cmdline hook (its `parse-i18n.sh` is absent from the built initramfs's
`hooks/cmdline`, confirmed by `lsinitrd`). An encrypted install now adds
`vconsole.keymap=` and `rd.vconsole.keymap=`, **and only when the resolved
console keymap is not exactly `us`**. The guard is on the console keymap, not
the XKB layout, so `us`+`dvorak` (which resolves to `us-dvorak`) does get the
argument; only a machine that lands on the kernel's built-in `us` gains no
argument that could later override `localectl set-keymap`.

**This mechanism dies with the sd-boot/UKI pivot** — a UKI's command line is
inside the signed PE. The replacement is a `vconsole.keymap` **systemd
credential** on the ESP (which `systemd-vconsole-setup` reads) or a UKI addon
contributing `.cmdline`. The seam is one function; see
`docs/disk-encryption.md`.

## 4. The supporting dependency, pinned

`rpm -q --whatrequires cryptsetup` on the shipped image returned exactly one
package: `clevis-luks`, which is itself only present because the bootc base
brings it. Two links of other people's decisions under the one binary that
opens an encrypted root. `cryptsetup` and `kbd` are now explicit in
`Containerfile.core` with **file-level** assertions, because `dnf5 -y install`
of an already-present package exits 0 and proves nothing.

`Containerfile.apex`'s final dracut run (the last one in the build) now asserts
inside the shipped initramfs: `systemd-cryptsetup`, dracut's `crypt` module,
`libcryptsetup-token-systemd-tpm2.so`, a non-`us` console keymap, and the new
hint module plus the symlink that pulls it in. All were derived by inspecting a
real initramfs first.

Plymouth's `message()` was `fun message (text) { }` in **both** themes —
accepted and dropped. It now draws, and `files/dracut/apex-unlock-hint` calls
it just before the passphrase prompt.

## 5. What was actually run

### Fast suite — `installer/test-installer-luks.sh`, in CI

**36 passed, 0 failed.** Every refusal; the conversion over all 99 layouts;
character-level checks read out of the shipped keymap data (the key right of T
types `y` on a US keymap and `z` on a German one; where US has Q, a French one
types `a`); six mutants, each a one-line inversion of the guard under test, all
of which flip the result.

`tests/check-suites-run-in-ci.sh` discovered `tests/test-*.sh` only — the
installer's suites are named by hand in `pr-validation.yml`, so a new one was
invisible to the gate that exists to catch exactly that. It now discovers
`installer/test-*.sh` too, mutation-tested both ways on a synthetic tree (a
suite in no workflow fails it; an exempt suite CI starts running fails it the
other way).

### Live suite — `installer/test-installer-luks-live.sh`, not in CI

A **real** `bootc install to-filesystem` of `localhost/apex-os:daily` onto a
**real LUKS2 volume** on a loopback file. It refuses any target that is not a
`/dev/loop*` node it created itself, and it snapshots this machine's UEFI boot
entries before and after and fails if they moved.

## 6. What is NOT proven

* **No keypress has been typed at a real unlock prompt.** The kernel-argument
  mechanism is verified by binary inspection and by reading the installed
  bootloader entry. The end-to-end property — a passphrase containing a
  character only a non-`us` layout produces unlocks the volume at boot — needs
  a VM with QMP `sendkey` and belongs to `files/scripts/boot-v2/run-scenarios`.
  It is requested from the `luks-enroll` unit and **has not been run**.
* **No TPM keyslot was enrolled by these runs.** A loopback file has no TPM,
  and TPM policy is `apex-luks-enroll`'s subject. The installer's side — observe
  the token, then and only then add `tpm2-device=auto` — is exercised only in
  its negative form here.
* **Nothing was encrypted on any real machine.** Every run was a loopback file
  under `/var/lab-scratch`.
