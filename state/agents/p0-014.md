## Decision (round 12) — `renew` still ignores its proof, deliberately

`GrantAuthority::renew` takes `_proof: Authenticated` and drops it, as it
always has. Commit 5 wired `issue` and not `renew`, and that is kept:

- `authenticated_by` describes **how the grant was authorised**, and a
  renewal does not create a grant. Mutating it on renew would make the
  `ended-at-reboot` line for that grant report the renewing key rather than
  the issuing password — strictly worse.
- The real gap is that **a renewal does not record its own authentication at
  all**, and never did. Before P0-014 the "renewed" audit line happened to be
  right because a renewal also required polkit; now a remote key-authorised
  renewal of a locally-issued grant produces a "renewed" line carrying
  `org.apexos.agent.system-access`. Closing it needs a new field in the audit
  record, which `system_grants.rs` asserts on exactly — so it is a follow-up,
  named here rather than smuggled into the last P0 commit.

## The harness fix, measured (2026-09-08)

`tests/in-login-session.sh` is new: it runs a command inside a **real logind
session**, so the daemon observes a local origin and §7's first column becomes
reachable from a test runner that systemd started.

Mechanism, all of it measured on the L16 rather than argued:

```
sudo -n env TERM=dumb systemd-run --quiet --wait --pty --collect \
     --uid=$(id -u) --gid=$(id -g) --property=PAMName=login \
     --working-directory="$PWD" --setenv=… \
     -- /bin/bash -c 'stty -onlcr; …; exec "$@"' in-login-session "$@" </dev/null
```

produces `0::/user.slice/user-1000.slice/session-N.scope`, `Class=user`,
`Type=tty`, uid 1000 — logind's own record, created through PAM the way
`login(1)` and `sshd` do it, **not** a chosen unit name. Nine things that had
to be measured to get there:

- **`--pty`, not `--pipe`.** `--pipe` leaves a logind session record stuck in
  `State=closing` after every run (ten piled up while developing this, and
  `loginctl terminate-session` cannot remove a record whose scope is already
  gone — they clear at reboot), gives `Class=background`, and flaked once in
  seven tries with "Connection timed out". `--pty` gave `Class=user` + a real
  tty, and **10 consecutive mints left the session count unchanged**.
- **`--pty` does NOT forward a piped stdin — the child blocks forever.**
  Measured: `printf 'y\n' | systemd-run --pty … read` hangs. So the wrapper
  closes stdin (`</dev/null`) and says so. Neither suite reads its own stdin;
  they pipe into the client binaries they invoke, which is unaffected.
- **The stdin redirect has to be applied INSIDE the session too, and finding
  that out cost a workspace run.** `--pty` otherwise hands the command a
  terminal on fd 0, and `apex/src/dispatch.rs`'s
  `a_terminal_is_requested_only_when_there_is_one_to_forward` asserts
  `tty_for_stdin() == Tty::None` — `isatty(STDIN_FILENO)`, with the test's own
  comment saying "under `cargo test` stdin is not a terminal". Inside the
  minted session it is, so the first wrapped workspace run came back
  **1881 passed, 1 failed** instead of 1882/0. `exec "$@" </dev/null` inside
  the session fixes it, and does **not** give up the controlling terminal:
  `tty_nr` in `/proc/self/stat` stays set (34819, measured), so the peer is
  still observed as `local-terminal` — which is the whole reason for asking
  for a pty rather than a pipe.
- **A failed mint must not be silent.** `systemd-run --wait` returns the
  COMMAND's exit status, so "the unit would not start" and "the command exited
  1" are the same number — and starting one did fail once in seven tries
  during development. So the inner shell writes a marker file before it
  `exec`s, and an empty marker means the command never ran and it is run in
  place instead. Verified by forcing a mint failure with a nonexistent PAM
  service: exit 224, marker empty, command ran exactly once, its status
  propagated.
- **systemd cannot exec a `#!` script as `ExecStart` here — exit 203**, from
  `/var/tmp`, from `$HOME` and from the worktree alike. `exec` of the same
  path from a shell *inside* the session works, so the command always goes
  through `bash -c`, which is needed for `stty -onlcr` anyway (without it a
  pty turns every line ending into `\r\n`).
- **`TERM` is forced to `dumb`, not forwarded.** systemd 257+ writes an
  OSC 3008 session sequence to the pty, glued to the front of the command's
  first line of output. Measured: it is the **unit's** TERM that decides, not
  systemd-run's own, so `env TERM=dumb` before `sudo` is not enough.
- **Detection asks logind, not the cgroup string.**
  `busctl --system call … login1.Manager GetSessionByPID u $$` answers with a
  session object inside a real login session and "PID … does not belong to any
  known session" both under a `user@` scope **and under a
  `--unit=session-9999.scope` fake**. It is therefore the one test the FOUND
  spoof cannot talk into the wrong answer. The cgroup shape is checked as
  well, because that is what `classify` actually reads.
- **It degrades, never skips.** No sudo, no logind, no systemd-run: it names
  which one is missing, says that every assertion needing a human at this
  machine will now fail for that reason and not the one it is testing, and
  runs the command in place. Every path runs the command exactly once.
  Verified with a fake `sudo` that exits 1.
- `sudo -n` works on the L16 with no prompt of any kind, and root is
  unavoidable: logind reserves `CreateSession` for PAM.
- `XDG_RUNTIME_DIR` is deliberately not forwarded — pam_systemd sets the
  correct one for the session it just created.
- In this environment `cat` is `bat` and `ls` is `eza`; `cat -v` fails with a

## FOUND (third session, 2026-09-07) — a local origin can be claimed after all, by picking a unit name

**`origin::classify` is spoofable, and the card's own recommended workaround is
the exploit.** Measured on this machine, not argued:

```
$ systemd-run --user --scope --quiet --unit=session-9999.scope -- cat /proc/self/cgroup
0::/user.slice/user-1000.slice/user@1000.service/app.slice/session-9999.scope
$ cat /proc/self/cgroup          # a real logind session, for comparison
0::/user.slice/user-1000.slice/session-4.scope
```

`classify` is `if cgroup.contains("/session-") && cgroup.contains(".scope")`
**first**, and the `/user@` + `.service` test second. The faked path satisfies
the first, so any unprivileged process can run itself under
`systemd-run --user --scope --unit=session-<anything>.scope` and be observed as
`local-terminal` — the origin §7 reserves root and break-glass for.

That defeats the module's headline property, which its own doc comment states:
"The two local origins are **observed only**. Nothing a client sends can
produce one." `may_be_declared()` guards the *declaration* path correctly; the
*observation* path was never guarded. A real logind session scope is a direct
child of `user-<uid>.slice`; the fake is nested under `user@<uid>.service`,
which the module already documents as meaning "nobody is present". So the fix
is ordering, not new policy: a cgroup containing `/user@<n>.service` is a user
service whatever a deeper scope is called. The existing test at
`origin.rs` ("A user service called `session-manager.service` is still a user
service") shows the name collision was considered for `.service` and missed for
`.scope`.

Identical `classify` on this branch (`apex-agentd/src/origin.rs:112`) and on
the tip (`apex-agent-core/src/origin.rs`, moved by p1-050) — byte-identical
logic, so one fix serves both.

Consequence for the harness fix: it must **not** be built on
`--unit=session-4242.scope`, because closing this hole breaks that trick.

## FOUND (successor, 2026-09-07) — the challenge cannot name the session it is for

`Challenge.session` is a bare `u32`, and on the path that matters there is no
`u32` to put in it. Measured, both in `apexd/apex-agentd/src/session.rs`:

- `crate::privilege::authorise_grant(...)` is called at **line 145**.
- `let id = reservation.id();` is at **line 207**.

So the primary remote-elevation path — `apex agent run --origin-policy remote
--system-access session`, i.e. a session *being started* with remote elevation
— reaches the gate **before its session id exists**. The ordering is
deliberate and documented in place ("before the worktree, the checkpoint, the
reserved id and the PTY, so a refused password leaves nothing behind"), so the
fix is not to reserve the id earlier.

There are two callers of `authorise_grant`, and the governing policy comes
from a different place in each:

| caller | session | governing `OriginPolicy` |
|---|---|---|
| `session.rs:145`, session start | **does not exist yet** | the `policy` local — the request's own `--origin-policy` |
| `privilege.rs:462`, grant renew | exists, named on the grant | that session's recorded `info.policy` via `daemon.registry` |

`GrantAuthority::issue` does take `session: u32`, so a grant names a session
once issued — but not at the moment it is authorised.

Consequences:

- `authorise_grant` must **take** the governing `OriginPolicy` as an argument;
  it must not look it up, because the two callers look it up differently. Two
  call sites, both present unchanged on `1ab542c`.
- `Challenge.session` becomes `Option<u32>`: `None` = "the session this
  connection is asking to start". Rendered in `binding()` as `session=none`
  or `session=N`, which keeps that function's injectivity argument intact
  (neither form can contain a newline). A `None`-scoped factor may authorise
  only a session start; an `Existing(N)` factor only session N. Deliberately
  **not** `Starting { agent, project }`: agent and project are free strings
  and putting them in a newline-separated binding would break the "no two
  different challenges produce the same bytes" property that `binding()`'s
  doc comment claims.

## Ordering, corrected (2026-09-07, successor)

The card's original 3-commit order landed **the permission before the
enforcement**, which `validate`'s own comment calls "a mode that lies":
relaxing `validate` first would make `apex agent status` print
`origin: remote_elevation_allowed` while `may_be_granted` still hard-refuses
on `is_local()`. Enforcement first, relaxation last.

**The policy instance the gate must read is NOT a session's, and not
`Origin::policy`.** Measured, not assumed:

- `may_be_granted` returns early for `who.session.is_some()`.
- `fn origin()` assigns `policy` **only** on its two sessioned branches; every
  unsessioned branch is `..Origin::default()`.
- Therefore `who.policy.origin` inside `may_be_granted` is *provably always*
  `OriginPolicy::LocalElevationOnly`. Wiring
  `who.policy.origin.allows_elevation_from(..)` there would be a gate that
  **can never open** — the dead-gate pattern inverted, and it would pass a
  naive test.
- **`Config.origin` is NOT the right policy either** — corrected before any
  code was written. `Config::policy()` just assembles the *default*
  `AgentPolicy` for sessions started without the flags, and `config.rs:202`
  repairs that default. A session started with `--origin-policy remote`
  overrides it. Reading `Config.origin` at the gate would mean the per-session
  dimension P0-014 is named after governs nothing — and a naive test would
  pass. The governing policy is per-caller; see the table in FOUND above.
- The gate call still belongs in `authorise_grant` — it has `&Arc<Daemon>`
  and both callers — so `may_be_granted` needs no signature change and no
  rebase risk. `authorise_grant` gains one `OriginPolicy` argument.
- Consequence for commit 5: `config.rs:202`'s self-repair calls
  `self.policy().validate()` and **resets the entire policy to default** when
  it errors. That is the mechanism that currently makes a stored
  `origin = remote_elevation_allowed` unreachable. Relaxing `validate` stops
  that erasure — another reason the relaxation lands last.

**The protocol cannot come after the enforcement.** The gate consumes a
`SecondFactor`; the challenge-issue / assertion-submit round trip and the
`ChallengeStore` on `Daemon` are its inputs. Landing the gate first would give
a gate no production caller could ever satisfy — the same dead-gate trap from
the other side.

## FOUND (round 10, 2026-09-11) — commit 4's gate is DEAD IN PRODUCTION, because polkit still runs after it, and polkit's own policy file says `no` to exactly this caller

**The most important thing found this round.** `authorise_grant` is
"`decide_origin`, then the password" — the polkit check is unconditional and
runs *after* the security key has been verified. For the non-local column that
is not a second lock, it is a wall: a perfect touch on an enrolled key is
followed by a check that is hard-coded to refuse.

Proved from the repository's own files, not by running anything (running it
would raise a prompt, which is out of bounds):

- `files/system/polkit-1/actions/org.apexos.agent.policy` gives **both**
  actions (`org.apexos.agent.system-access`, `org.apexos.agent.break-glass`)
  the defaults `allow_any: no`, `allow_inactive: no`,
  `allow_active: auth_admin`.
- The same file's comment states the intent in so many words:
  *"A switched-away session and a remote one are both 'nobody is at this
  keyboard'. Section 7 reserves elevation for a local origin, and **there is no
  password that makes a remote caller local**, so they are refused outright
  rather than challenged."*
- The subject passed to `pkcheck` is **the peer of the control connection**,
  by deliberate design (same file: "why the subject is the caller and not the
  daemon"). `auth.rs::pkcheck_argv` passes `--process <subject>
  --allow-user-interaction`; `verdict_from_status` maps exit 1 to
  `Verdict::Refused`.

So a non-local peer is refused **two independent ways**, and both are fatal:

1. A remote-control bridge running under `user@1000.service` has no logind
   session at all, so polkit resolves it under `allow_any` → `no`.
2. Even if the owner also happened to be logged in locally, `allow_active`
   is `auth_admin` — the dialog would appear **on the machine's own desktop**,
   which the remote human by definition cannot reach.

This is the dead-gate pattern from a third side, and it is the same class of
defect this unit has now found five times: a check whose only caller can never
pass it. The difference is that this one would have passed every unit test —
`decide_origin` returns `Ok(origin)` correctly, and the death happens one line
later in a function commit 4 does not touch.

**Is this "the touch replaces polkit" or "the touch adds to polkit"?** The
repository's own words point at *replaces* for the non-local column, and the
local column is untouched. `webauthn::may_elevate`'s doc comment, written in
commit 2, says: *"§7 already gives root 'local auth' locally, and that path is
`may_be_granted` plus polkit. Returning `Ok` for it is not a hole; it is this
function declining to be a second, weaker copy of a check that already
exists."* That sentence only parses if the remote path is **the other path** —
the key is the authentication there, not an extra hurdle in front of a password
dialog that cannot appear. `docs/agent-runtime.md` agrees: §7 "allows remote
elevation only behind a security key", which names the key as the condition,
and nothing anywhere names a second one.

**Deliberately NOT fixed in commit 4, and this is not deferral by accident.**
Until commit 5 relaxes `validate_for`, `OriginPolicy::RemoteElevationAllowed`
cannot be stored or set at all (`config.rs:202` resets the whole policy to
default when `validate` errors), so the remote path is unreachable whatever
polkit does. Commit 5 is the commit that makes it live, so commit 5 is where
this has to be settled — **relaxing `validate_for` without it would ship a
setting that reads as enabled in `apex agent status` and cannot work**, which
is precisely the "mode that lies" the ordering note above was written to
prevent.

**What commit 5 must therefore do, beyond the `validate_for` one-liner:**

1. `authorise_grant` gains a branch: for a **non-local** origin whose
   `decide_origin` returned `Ok`, mint `Authenticated` from the receipt instead
   of calling `authenticate(daemon.auth, ..)`. The local column keeps polkit
   exactly as it is.
2. `Authenticated`'s "a token only this function and its sibling can produce"
   doc comment becomes wrong and must be rewritten — there would then be two
   ways to mint it, and the second one is a verified `SecondFactor`.
3. `org.apexos.agent.policy`'s "allow_inactive and allow_any are no" comment
   becomes half-wrong and must be amended: the sentence "there is no password
   that makes a remote caller local" stays **true** (a security key is a
   possession factor, not a password) but it stops being the whole story, and
   an administrator reading that file must be told that apex-agentd has a
   second authentication path that does not go through polkit at all. The XML
   `<defaults>` themselves should NOT change — polkit continuing to refuse a
   remote caller is correct; what changes is that apex-agentd no longer asks it
   about one.
4. The audit record has to distinguish the two: a grant authorised by a touch
   is not a grant authorised by a password, and `apex agent grants` should say
   which.

## FOUND (round 10, 2026-09-11) — the success branch of the gate cannot be tested from apex-agentd, and the fix is to expose the Signer, not a constructor

`decide_origin`'s branch that matters — non-local origin + permissive policy +
a **valid** receipt → `Ok(origin)` — cannot be written as a test in
`apex-agentd`. `webauthn::SecondFactor` has no public constructor and no public
field (deliberately, commit 2), so the redeem closure's `Ok` arm is
unreachable from outside `apex-agent-core`. Every test writable today asserts a
refusal, which is the trap this card names five times.

Consequence: three mutants are **uncatchable** without it —
`.and_then(|a| a.as_ref().ok())` → `None` (the receipt dropped before the
gate), renew's `scope: Some(session)` → `None` (would need `WrongSession`), and
a `ttl_ms` transposition (would need `WrongTtl`).

**The fix is to expose the `Signer`, not to add a `SecondFactor` constructor.**
`Signer` already exists in `webauthn.rs`'s `#[cfg(test)]` child with
`Signer::new(label)` and `.receipt(&challenge, flags, counter)`; it is an
openssl-backed EC key. Exposing it weakens nothing, because the receipt is
**still** minted only by `redeem_and_verify` checking a real signature — a
signer is the ability to hold a key, which any attacker with their own key
already has. A `SecondFactor` constructor would be the actual hole.

Route, in preference order: `pub mod test_support` behind
`#[cfg(any(test, feature = "test-support"))]` in apex-agent-core, enabled in
apex-agentd's `[dev-dependencies]` (resolver 2 keeps dev-dep features out of
non-test builds — **verify the resolver version before relying on this**).
Fallback: replicate the openssl signing in the test file.

Note that `OriginPolicy::RemoteElevationAllowed` **is** constructible directly
in a unit test at commit 4 — `validate` is not in `decide_origin`'s path — so
the success branch is testable as soon as a receipt can be had.
