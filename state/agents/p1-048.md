## P1-049 — IN PROGRESS. My first read was wrong: it is NOT blocked

There is still no `GamingPage.qml`, but the CLI is rich and read-only probes
exist. Corrected findings from `apex ... --help` on this machine:

- **`apex gaming --json`** — the whole readiness probe, already written:
  `{ready, boots_to_game, preselected_session, checks{session_desktop,
  session_launcher, switch_helper, switch_sudoers, rtprio_limits, gamescope,
  steam, mangoapp}, gamepads[], blockers[], warnings[], install_hint}`.
  Each check carries `value` + `source` (a path, or `PATH:tool`). On this box
  gamescope/steam/mangoapp are all `false` and
  `install_hint = "sudo apex install gamescope steam"`. That is the
  not-installed state the brief asks for, authoritative, no `command -v` of my
  own needed.
- **`apex mode`** — list / show / set / status. `apex mode status` gives tier,
  auto-switch, game mode, mode. `apex mode show gaming` explains the policy AND
  names what it reports-but-does-not-apply. No `--json` on mode yet.
- **`apex game`** — start/stop/status/attach, and `apex game profile` is §12's
  per-game profiles.

**The design trap, and it is the important one.** `apex mode set --auto` is
documented one-shot: "APEX ships nothing that re-evaluates this on a timer."
So criterion 1's master "Optimize games automatically" must NOT be a switch —
a switch promises a daemon that deliberately does not exist. It has to be an
action ("Use the mode my workload suggests") plus a readout of the mode you are
actually in.

No verb found for VRR or for background-update suppression; those criteria
cannot be built honestly yet.
