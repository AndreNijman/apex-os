# p1-061 — Extend APEX capabilities to normal application permissions

Task: **P1-061** (`partial`), depends on P1-001 (done). Repo: apex-os with an
apex-shell half. Branch `task/p1-061-app-permissions`, from
`origin/roadmap/v2.2`. Worktree `/var/tmp/apex-work/wt-p1-061`, shell worktree
`/var/tmp/apex-work/wt-p1-061-shell`.

## Criteria, quoted from roadmap.yaml

1. A design unifies or brokers filesystem, camera, microphone, screen capture,
   USB/device, network, sensitive-directory and secret access **where
   Linux/portal primitives permit**.
2. Flatpak and native apps can be represented **without pretending they have
   identical enforcement mechanisms**.
3. Settings → Privacy & Permissions shows effective capabilities and origin.
4. Revocation behaviour is explicit and tested.

Measured, not assumed, and the reason the model is shaped the way it is:

- **The enforcer is per capability, not per subject kind.**
  `io.github.cosmic_utils.camera` is a Flatpak carrying `devices=all`; it opens
  `/dev/video0` directly and lands on the same logind ACL a native binary does.
  `com.spotify.Client` has no `devices=all` and is portal-brokered. Both are
  Flatpaks. The tests assert the first two produce the identical sentence and
  the third differs.
- **There is no microphone portal in any version of xdg-desktop-portal.**
- **Which portal interfaces exist is a property of the SESSION.** Usb, Secret
  and RemoteDesktop are absent under `default=hyprland;gtk` and present under
  niri's `default=gtk;gnome`.
- **Hyprland, the default session, had no Secret portal at all.** Fixed here.
  Naming a backend overrides its `UseIn=`; proven on a private bus rather than
  assumed.
- **Hyprland and niri hand `zwlr_screencopy_manager_v1` to any client**, so the
  ScreenCast portal is not what stops a program capturing the screen.

### Criterion 3 — the page has now been drawn

`tests/run-popup-smoke.sh` is headless since the p2-b unit's harness landed, so
the page could simply be run. It was, and in the first second it reported what
three kinds of static verification had missed:

    PrivacyPage.qml[122]: TypeError: Cannot read property 'desktop' of null
    PrivacyPage.qml[176]: TypeError: Cannot read property 'brokered' of null

`parseList` returned `session: null` for a report it could not read; the header
binds `session.desktop` and the session section binds `session.brokered`; and a
binding inside a section whose `visible` is false is still evaluated. It fired
on EVERY load, because `report` is seeded with `parseList("", 0)`. Fixed in the
model — the failure branch now returns `sessionView(null)`, so the report has
one shape on every path — not by a guard in the page.

New: `tests/run-privacy-page-test.sh` + `tests/privacy-page-test.qml`, the page
built through PageRegistry inside a FloatingWindow on a headless labwc with a
stub `apex` answering from the fixture. 73 assertions over three phases:
`fixture` (3 apps, 30 rows, origin AND enforcer counted 30 times each, 15
controls in three labels, zero on the native program, pressing Never runs
exactly `apex permissions revoke com.spotify.Client camera`), `unreadable`
(`apex` fails; the page must say so and must not throw — the phase the defect
went red on), and `pixels` (grabToImage → 980x692 PNG, 14 536 distinct pixel
values, read back by `tests/lib/png-ink.py`). A TypeError in any phase log is a
hard failure, because that is the one defect class that leaves no other trace.

Mutants, each watched red and restored byte-identical with plain `cp`:

* `PrivacyPage.qml` `"from: "` -> `"origin: "` — *every row on screen says where

### Criterion 4 — the unmeasured timing is measured, and the answer is NO

The CLI half re-run on this tip: `tests/test-apex-permissions.sh --with-binary`
is **17/17, 0 skipped** — including the four `apex permissions revoke` refusal
sentences and the two that state a revocation's timing rather than implying it.

A permission-store change does **not** reach an already-running PipeWire client.
`tests/measure-permission-store-reach.sh` (+ `tests/permission-store-client.c`)
reproduces it: private session bus, private PipeWire, private WirePlumber with a
profile that touches no hardware, private `XDG_DATA_HOME` — so the grant taken
away belongs to an application id that does not exist. Round 1 thought measuring
this meant revoking on Andre's live machine; it does not.

Every other link was verified working in the same run: the client is recorded
`pipewire.access = portal`, WirePlumber granted it (`pw-cli get-permissions`
shows `rwxm-`, `access-portal.lua:87` logged it), the store reads back `['no']`,
and `gdbus monitor` caught the `Changed` signal. Six seconds later the client
still held `rwxm-` on every object and `access-portal.lua` logged nothing.
Where the chain breaks is deliberately NOT claimed.

So `Timing::NextRequest` is the correct statement rather than the cautious one,
and `Timing::Immediate` stays unreachable with the test that holds it so now
backed by evidence. `docs/app-permissions.md` §2.4 and §6 and the `Timing` doc
comment all changed from "not verified" to what was found.

A shipped fact that used to be read off a config file is now read off the
running process: `libwireplumber-module-portal-permissionstore.so` is in the
L16 session WirePlumber's mapped modules.

## NEXT

Nothing this round left half-done. Three things a later round could take on:

1. **Diagnose why the store's `Changed` does not reach
   `client/access-portal.lua:123`.** Measured as an outcome, not diagnosed. The
   module answers `lookup` calls, so its connection to the store works; the
   signal is on the bus; the Lua handler never runs. That is an upstream
   question (wireplumber 0.5.14 / xdg-desktop-portal 1.20.4) and the harness to
   investigate it already exists.
2. **Decide whether Hyprland should reach `gnome.portal` for Usb and
   RemoteDesktop.** Unchanged from round 1, and deliberately not done — see the
   tail of `hyprland-portals.conf`. It would start
   `xdg-desktop-portal-gnome` in a session with no GNOME shell, for backends
   that talk to Mutter, and an interface that exists and cannot answer is worse
   than one honestly absent. Needs a VM and a real USB request.
3. **A second look at the rendered page with real theme colours.** The PNG the
   render test grabs is washed out because the private HOME has no
   `colors.json`, so `ColorLoader` falls back. The structure is correct and the
   assertions are on the object tree, but nobody has yet seen this page in the
   palette a user gets. `PRIVACY_PAGE_PNG=/tmp/p.png ./tests/run-privacy-page-test.sh`
   is where to start.
