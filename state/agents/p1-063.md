## SETTLED 2026-09-12 — the polkit question, answered three ways

**An unprivileged active session CAN take a `handle-lid-switch` block inhibitor
with no prompt. No polkit rule is needed and none was added.**

1. `/usr/share/polkit-1/actions/org.freedesktop.login1.policy` line 106:
   `org.freedesktop.login1.inhibit-handle-lid-switch` defaults are
   `allow_any=no`, `allow_inactive=yes`, **`allow_active=yes`**.
   `/etc/polkit-1/rules.d/` holds only `49-polkit-pkla-compat.rules` — no local
   override touches the action.
2. `pkcheck --action-id org.freedesktop.login1.inhibit-handle-lid-switch
   --process $$` exits **0** (no `--allow-user-interaction`, so it could not
   have prompted). Andre's session is `Type=wayland Class=user Active=yes
   Remote=no`.
3. Held for real, as uid 1000, nothing on screen:
   `systemd-inhibit --what=handle-lid-switch --mode=block …` appeared in
   `systemd-inhibit --list` as `WHAT=handle-lid-switch MODE=block UID=1000`.
   Root can take it too (probed with `sudo -n`).

So the driver may run as either uid. It runs as **root** for a different
reason: the power-down half (`rfkill`, keyboard-backlight sysfs, DPMS) and the
guards' `Suspend()` would otherwise hit `org.freedesktop.login1.suspend`, whose
`allow_active=yes` degrades to `auth_admin_keep` the moment the caller is not
the active session — a prompt waiting to happen.

- evdev `event1`, name `Lid Switch`, `capabilities/sw` = `1` (SW_LID). This is
  what logind watches.
- `/dev/uinput` exists, `crw------- root root` — **uinput injection needs
  root**. `sudo -n` works here, so the live suite can run; without it the suite
  must report could-not-run, never skip.
- `logind.conf(5)`: *"Only input devices with the `power-switch` udev tag will
  be watched for key/lid switch events."* A uinput device without that tag is
  invisible to logind, so an injection against an untagged device proves
  **nothing**. The live suite asserts the tag (via `udevadm info`) and asserts
  logind's own "Lid closed" journal line before it believes its own result.
- **Nothing else on this machine reacts to the lid.** `bindl = …switch:` appears
  in neither `files/desktop/hypr/hyprland.conf` nor the live
  `~/.config/hypr/hyprland.conf`; apex-shell reads no `LidIsClosed`; hypridle's
  config has no lid listener. So an SW_LID injection under a held inhibitor
  cannot blank Andre's screen or lock his session.
- `apex-agentd` is a **user** service (`files/system/units/apex-agentd.service`,
  `WantedBy=default.target`). A root watcher reads the work signal through
  `paths::control_socket_in("/run/user/<uid>")`, per logged-in user.

## The design, decided by the orchestrator — build this, do not re-litigate it

- **The primitive is a `handle-lid-switch` block inhibitor**, not an edit to
  `HandleLidSwitch=`. Dynamic, reverts when its holder dies, and leaves a
  machine with no live work suspending exactly as it does today. Static
  `HandleLidSwitch=ignore` turns every laptop bag into an oven.
- **"Live work" is measured, not a mode the user must remember.** A live agent
  session is the obvious signal and `apex-agentd` already knows about sessions;
  `apexd/apex-agent-core/src/lock.rs` is P0-015's lock-state policy and is the
  nearest existing thing. A manual pin covers everything else.
- **Guards are mandatory and must name themselves.** Lid closed is lid closed:
  no airflow. A thermal guard suspends anyway; a battery floor checkpoints and
  suspends rather than dying mid-task. Whichever guard fires must be recorded
  and reportable.
- **The VPN is the load-bearing half of the request.** ASSERTED, not assumed.
- **After reopening, the machine says what happened**: how long it stayed up,
  what ran, whether the VPN held, what it cost in battery.

## How to test it without a lid and without a window

The decision function for the matrix; one real `SW_LID` event, under an
inhibitor whose lifetime strictly encloses the uinput device's, for the
end-to-end. The injector emits `SW_LID=0` and destroys the device in a trap
*before* the enclosing inhibitor can drop, so a crashed injector cannot leave a
closed lid behind an unheld inhibitor.

**"Permission denied is not absence" applies with force here.**

### Measured live on the L16, 2026-09-12 — do not re-derive

- A uinput `SW_LID` device is tagged `power-switch` by udev
  (`TAGS=:power-switch:`), and logind says which node it opened: *"Watching
  system buttons on /dev/input/event21"*. It then logs `Lid closed.` /
  `Lid opened.` at INFO and flips its own `LidClosed` property.
- **`busctl … Manager BlockInhibited` is the authoritative check**, not
  `systemd-inhibit --list`: it reads `s "idle:handle-lid-switch"` while the
  lock is held and `s "idle"` after. The list says what asked; this says what
  logind believes it must not do.
- **A real WireGuard tunnel (two netns, veth created INSIDE one so neither end
  ever exists in the root namespace) carried 47/47 pings, 0% loss, across a
  real lid close, rx 500 → 6004 bytes DURING the closed window.** NM's nine
  saved connections identical before and after.
- **THE L16 IS DOCKED.** `Docked=b true`, `card1-DP-1 connected`. logind
  consults `HandleLidSwitchDocked` (default `ignore`) **before any inhibitor**,
  so the lid does nothing here with or without the lock, and the non-suspend
  **cannot be attributed to the inhibitor on this machine**. The live suite
  reports that as COULD-NOT-RUN rather than banking the pass.
- `org.freedesktop.LogControl1` **is not implemented by this logind**, so
  logind's debug "Refusing … is inhibited" line cannot be raised to prove
  causation that way. Nothing was changed trying; LogLevel was never set.
- uinput ioctls take the bit NUMBER **by value** (`fcntl.ioctl(fd, UI_SET_EVBIT,
  EV_SW)`); a packed buffer passes its address and answers EINVAL.
- `sudo apex install wireguard-tools` **works on this machine now** (42 pkgs,
  721 MB extension) — the CLAUDE.md note about post-reboot `apex install`
  failing is stale.
- **A unit's sandbox can be measured headless, with no prompt**, and this is how
  the `8e32baba` defects were found rather than argued about:
  `sudo -n systemd-run --wait --pipe --collect -p ProtectHome=… -p PrivateTmp=…
  -p CapabilityBoundingSet='…' sh -c '…'`. Under `ProtectHome=yes`,
  `ls /run/user` returns nothing and `ls /var/tmp | wc -l` gives 0 against 407.
  `runuser -u andre -- true` fails with "cannot open session: Permission
  denied" unless **CAP_SYS_RESOURCE** is in the bounding set — bisected:
  CAP_AUDIT_WRITE, CAP_CHOWN, CAP_FOWNER and CAP_SYS_ADMIN each fail alone.
- **`! grep` cannot fail a build.** bash does not apply errexit to a pipeline
  inverted with `!`: `bash -c 'set -eu; ! grep -q x <<<x; echo REACHED'` prints
  REACHED. Four assertions on this branch had already been found that could
  never pass or never run; this is a fifth species and
  `tests/check-containerfile-assertions.sh` does **not** catch it (it resolves
  paths, not exit semantics). **The pre-existing `! grep -q 'apex-remote'` in
  the firewall stanza at Containerfile.base has the same problem** and is not
  this unit's to fix.
- **Pre-existing flake, not this branch's:**
  `apex/src/provenance.rs`'s `a_git_status_that_could_not_run_is_not_a_clean_
  working_tree` fails roughly **one run in three** under `cargo test -p apex`
  and **never** under `--test-threads=1` (3/3 clean each way). provenance.rs is
  untouched by this branch. The shape is the known write-then-exec race: the
  test writes a fake `git` shell script, chmods it and execs it while sibling
  test threads are forking, so the child inherits a writable fd and exec fails;
  `revision_of_with` then sees no `rev-parse` output and returns `Unmeasured`.
  Re-run alone before believing a regression — as this repo's notes already say
  about its suites.
