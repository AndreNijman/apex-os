## Measured on the L16 on 2026-09-12 — do not re-derive

    HandleLidSwitch              = suspend        (stock; the image ships no
    HandleLidSwitchExternalPower = ""              logind policy at all)
    IdleAction                   = ignore

Live inhibitors include `APEX Shell / systemd-inhibit / idle / "Caffeine is
enabled" / block` — so the shell already has a caffeine concept, and it takes an
**idle** inhibitor, which does nothing about the lid. NetworkManager, UPower,
ModemManager and hypridle all hold `sleep` **delay** inhibitors; claude-desktop
holds one too.

`files/system/system-sleep/apex-wifi-resume` exists — there is already a
resume-side hook for Wi-Fi, and it is evidence that suspend/resume here is not
clean for networking. Read it before designing the network half.

## The design, decided by the orchestrator — build this, do not re-litigate it

- **The primitive is a `handle-lid-switch` block inhibitor**, not an edit to
  `HandleLidSwitch=`. Dynamic, reverts when its holder dies, and leaves a
  machine with no live work suspending exactly as it does today. Static
  `HandleLidSwitch=ignore` turns every laptop bag into an oven. **Check the
  polkit action** (`org.freedesktop.login1.inhibit-handle-lid-switch`) actually
  allows an active session to take it without a prompt — a prompt is forbidden
  here — and if it does not, say so rather than adding a rule that weakens the
  desktop.
- **"Live work" is measured, not a mode the user must remember.** A live agent
  session is the obvious signal and `apex-agentd` already knows about sessions;
  `apexd/apex-agent-core/src/lock.rs` is P0-015's lock-state policy and is the
  nearest existing thing. A manual pin covers everything else.
- **Guards are mandatory and must name themselves.** Lid closed is lid closed:
  no airflow. A thermal guard suspends anyway; a battery floor checkpoints and
  suspends rather than dying mid-task. "It kept working until it died" is worse
  than suspending. Whichever guard fires must be recorded and reportable.
- **The VPN is the load-bearing half of the request.** If nothing suspends, NM
  never gets the sleep signal and the tunnel should simply stay up — but that
  must be ASSERTED, not assumed: Wi-Fi power saving and NM's own reconnect
  logic can drop a long-lived tunnel with no suspend involved at all.
- **After reopening, the machine says what happened**: how long it stayed up,
  what ran, whether the VPN held, what it cost in battery.

## How to test it without a lid and without a window

You cannot close Andre's lid, and you must not try. The lid switch is an input
event: `/proc/acpi/button/lid/*/state` reports it, and logind reacts to an
evdev `SW_LID` event. A test can either drive a **uinput** virtual switch
(create a device advertising `EV_SW`/`SW_LID`, emit the event, observe what
logind and the policy do) or test the policy's decision function directly
against injected conditions and assert the inhibitor is taken and released.
Prefer both: the decision function for the matrix, one real `SW_LID` event for
the end-to-end.

**"Permission denied is not absence" applies with force here.** A test that
cannot create the uinput device, or cannot read the battery/thermal sysfs, must
report could-not-run with the reason. A power test that silently measures
nothing and passes is worse than no test: it is a promise that the machine will
survive a schoolbag.
