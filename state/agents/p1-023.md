## MEASURED, DO NOT RE-DERIVE
Four facts about `producer | grep -q` established by running the shell, not by
reading about it (/tmp/sigp/t2.sh, t3.sh):

- It is NOT a rare flake. It is size-dependent and then certain. Against a
  25 KB producer: 0 spurious failures in 200 runs. Against 183 KB and 915 KB:
  200/200. The pipe buffer is 64 KB — under it the producer finishes writing
  and exits before `grep -q` is even scheduled; over it the producer is still
  writing when grep exits at the first match, takes SIGPIPE, and `pipefail`
  hands 141 to the caller. Test files only grow.
- `bash -c '… | grep -q …'` is SAFE from a pipefail parent. A child bash does
  not inherit pipefail (SHELLOPTS is not exported): measured 0/200 on the
  915 KB file, and 200/200 with `set -o pipefail` added inside the string.
- `grep -q PAT <<<"$var"` — 0/200. `grep -q PAT < <(producer)` — 0/200.
- `producer | grep PAT >/dev/null` — also 0/200 (grep reads to EOF), but the
  repo's established fix is process substitution; that is what is used here.

Added 2026-09-07, also measured, also do not re-derive: the run-*.sh half
inverts rather than flakes. `if echo "$out" | grep -q "FAIL"` on a 1.6 MB log
returns 141, the `if` reads that as "no FAIL found", and a suite that FAILED
reports that it passed. Single deterministic shot above the buffer:
old form MISSED a real FAIL line, new form DETECTED it, and on a clean log
neither invents one. Reproducer kept at /var/tmp/p1023-inversion-proof.sh.

## DESIGN — P1-023 global push-to-talk (measured, not guessed)

THE REAL SPEC is ROADMAP.md §8.2 (line 457), not the 3-line yaml. It adds a
fourth requirement the yaml omits: "no permanent microphone access to all
agents". Full list: compositor-neutral global PTT route to the active project
or focused agent session; clear microphone indicator; explicit routing target;
no permanent mic access to all agents; works in Hyprland, niri and
Floating/labwc. P1-023 is the ONLY `area: voice` item in roadmap.yaml, so it
owns the whole route; nothing else will supply STT later.

### Hold vs toggle — decided: TOGGLE everywhere. Do not re-derive.
Read off the shipped compositors on this machine, not from memory:
- Hyprland 0.56.2 — `bindr` exists, release binds available.
- labwc 0.9.6    — `<keybind key="..." onRelease="yes">`, confirmed in
                   `man 5 labwc-config`. Release binds available.
- niri 26.04     — NO release bind. The complete property set on a bind, from
                   the shipped wiki (/usr/share/doc/niri/wiki/
                   Configuration:-Key-Bindings.md), is exactly: repeat,
                   cooldown-ms, hotkey-overlay-title, allow-when-locked,
                   allow-inhibiting. Nothing fires on release.
ROADMAP.md:122 records "Voice / hold-to-talk is used" as a PROFILE ASSUMPTION,
but the acceptance criterion is "works in Hyprland/niri/Floating". Hold would
work on two of three. So: one semantic, toggle, on all three backends. The
hazard of toggle is a hot mic you forgot about; that is what makes the
indicator load-bearing rather than decorative, and it wants a hard cap too.
NiriBackend.qml:69 independently confirms runtime keybind capture is off on
niri, so PTT must ride the compositor's own config-file binds, not a
shell-side grab.

### Where the bind comes from
KeybindService.qml already generates all three artifacts — `_genLua()` →
~/.config/hypr/apex/shell-keybinds.lua, `_genKdl()` →
~/.config/apex-shell/ApexShellKeybinds.kdl, `_applyLabwc()` splices into a
marked region of ~/.config/labwc/rc.xml (README.md:332). PTT is a new entry in
`_defaults` of type exec dispatching `$qsIpc` (`qs -p <shellDir> ipc call`),
which is how every existing shell-side action already reaches the running
shell. So the "compositor-neutral routing" is a new IpcHandler in
src/state/IpcManager.qml plus one `_defaults` entry — NOT a new input path.

### The privacy contract is already shipped and already asserted
AgentHelpContent.qml:159 tells the user a sandboxed session has "No camera and
no microphone", and check-agent-help.sh asserts on that document (proved by the
todo-block mutant in 89cb520). So the mic MUST stay shell-side: the shell opens
the source only while recording, and only TEXT ever crosses to a session. Any
design that hands an agent the mic contradicts shipped prose and breaks a gate.
Pipewire is already available in-process (Quickshell.Services.Pipewire;
AudioControl.qml:10 holds `Pipewire.defaultAudioSource`), so the indicator and
the capture gate have a real source object to bind to.

### Target resolution — the rule, settled
§8.2 routes "to the active project or focused agent session", so the focused
session is a NAMED target, not a sloppy fallback. Resolve: pinned target →
focused agent session → REFUSE. What "explicit" forbids is the user not knowing
where their words went, so the indicator names the resolved session BEFORE
recording starts, and a refusal says which arm failed ("no session pinned, none
focused"). Refuse-on-no-target stays; refusing merely because the target came
from focus does NOT. "Active project" meaning spawn-a-new-session is OUT OF
SCOPE for v1 — say so in the help prose rather than half-building it.

### THE GAP THAT DECIDES SCOPE — read before planning any commit
There is no way to put text INTO a session today. AgentService.qml's whole
action surface is `apex agent {pause,resume,kill}` + focusTerminal +
reviewRequest; there is no send/prompt/stdin verb. apex-os has none either
(`grep send_input|write_stdin|send_text|"prompt"` over *.rs: one unrelated hit,
main.rs:1289). ROADMAP/design/P1-050-remote-protocol.md confirms the shape:
apex-agentd owns the PTY and every input goes through the daemon's own
protocol; "send prompt" is listed under the REMOTE client's Input and media
(ROADMAP.md:1868), i.e. P1-05x, unbuilt. Screen-scraping/typing into the
focused window is explicitly what that design refuses.
=> Delivering a transcript needs a new apex-agentd verb, but it is NOT a long
   pole — measured, do not re-derive. The full Request enum
   (apex-agent-core/src/protocol.rs:222) is Hello, Run, List, Info, Attach,
   Resize, Signal, Event, Logs, Remove, Prune, PrivilegeRequest, Requests,
   Decide, RequestExecuted, Grants, Revoke, SecretUse, SecretGrant,
   SecretGrants. No Input/Send. BUT `Attach {id, cols, rows, replay}` is
   already a bidirectional PTY byte stream: client.rs:249 forwards stdin
   straight to the socket and the daemon writes those bytes into the PTY
   master. So the write path into a live session EXISTS and is proven; a
   `Request::Input { id, data }` variant reuses it and is on the order of 100
   lines, not a rewrite.
   Do NOT deliver by piping into `apex agent attach`: its reader loop keeps
   running after stdin EOF until the session itself closes, and `replay`
   defaults non-zero so it would dump scrollback. It hangs and it is dirty.
   Session control today is by signal only (apex-agent-core/src/session.rs:386
   maps pause/stop→SIGSTOP), which is why no text path surfaced in the first
   grep.

### STT ownership
No roadmap item anywhere owns speech-to-text and §8.2 says "route". So STT is a
user-configured command hook (audio on stdin, text on stdout), never a bundled
engine. When it is unset, PTT must say it is unconfigured rather than pretend.
