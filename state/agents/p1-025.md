## Traps specific to this unit

- "Runs inside a sandbox" is the criterion that is easiest to assert vacuously.
  The proof is a plugin that tries to reach something outside the sandbox and is
  *observed* to fail — not a grep for a bwrap argument. bubblewrap is installed
  on this machine and in both CI workflows, and
  `kernel.apparmor_restrict_unprivileged_userns=0` is set in CI with a smoke
  check that proves the sandbox actually starts.

## MEASURED, not remembered — claude 2.1.260 on this machine

Probed headlessly with `ANTHROPIC_BASE_URL=http://127.0.0.1:1` so no request left
the machine, and a sentinel script per server that appends its name to a log when
it is started. Fixture HOME under the session scratchpad; nothing real touched.

1. With no flag, **all four** surfaces start a server: `~/.claude.json`
   `mcpServers`, `~/.claude.json` `projects.<dir>.mcpServers`, the working
   directory's own `.mcp.json`, and an enabled plugin's `.mcp.json`.
2. With `--strict-mcp-config --mcp-config <file>`, **only the file's servers
   start** — the plugin-defined one is dropped along with the rest. That is the
   mechanism P1-026's second criterion needs and `sidecar.rs` already named.
3. A server key containing `:` (`plugin:fakeplug:plugsrv`) is accepted verbatim
   in a `--mcp-config` file, so a curated document can keep the agent's existing
   spelling — and therefore the `mcp__<server>__<tool>` names any permission rule
   already refers to.
4. A plugin's live `.mcp.json` is the copy under `installed_plugins.json`'s
   `installPath` (`plugins/cache/<mp>/<plugin>/<version>`), not the marketplace
   checkout. `servers::enabled_plugin_configs` already reads the right one; a
   fixture that points installPath at the checkout measures a stale file.
5. Repo `.mcp.json` servers are approved per directory
   (`enabledMcpjsonServers` / `disabledMcpjsonServers` in the project entry), and
   `-p` skips the trust dialog. A curated document that listed an unapproved one
   would be APEX approving it on the user's behalf.
