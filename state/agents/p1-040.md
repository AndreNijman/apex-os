## WHAT LANDED (apex-shell task/p1-040-per-output-scaling)

### 1. The token table is a component, not a singleton's private contents
`src/theme/ThemeSet.qml` (new) is the geometry token table as a function of ONE
`scale`. `src/theme/Metrics.qml` is now an INSTANCE of it — the instance built at
the reference output's factor — so every one of the 2758 existing call sites
reads exactly what it read before, and a second output can have its own set
without a second copy of the arithmetic. That copy is the defect P1-040 was
opened for.

`src/theme/OutputScale.qml` (new singleton) holds the one policy that turns a
logical height into a factor: the breakpoint table in `scaling.js`, and the
manual override that outranks it. Metrics' own `scale` goes through it, so the
global set and any per-output set cannot be answering two different questions.

`Theme.factorForScreen(screen)` / `Theme.factorForHeight(h)` expose it to files
that import `src/` rather than `src/theme/`. It had to go through Theme: `Theme`
is registered in BOTH `src/qmldir` and `src/theme/qmldir`, so a file importing
both modules gets "Theme is ambiguous". `ThemeSet` is registered in both (a
plain component in two modules is two type registrations of one file, not two
instances — unlike a singleton, which is the hazard `src/qmldir` warns about
twice in its own comments).

Colours are deliberately NOT in ThemeSet. A palette belongs to the shell, not to
an output; two monitors with different accent colours would be a bug. A migrated
file reads SIZES from `theme.` and COLOURS from `Theme.`, visibly, at every call
site.

### 2. Two production surfaces are per-output
`src/windows/DisplayConfirm.qml` and `src/windows/ConfirmDialog.qml`. Each now
carries:

    readonly property ThemeSet theme: ThemeSet {
        scale: Theme.factorForScreen(root.screen)
    }

and reads `theme.px()/fs()/cornerRadius/notchRadius` where it read `Theme.*`.
33 scaled reads moved; 17 colour reads stayed.

They were chosen, not picked at random. Both are built per output by shell.qml,
both are full-screen overlays anchored to nothing but their own screen, both use
only built-in QtQuick types (no shared component pulls the global factor back
in), and nothing outside them reads their size through a singleton.

### 3. The named assertion, delivered and measured
`tests/scaling-test.qml` now builds the real DisplayConfirm and ConfirmDialog per
output, exactly as shell.qml does, and reads the laid-out width and radius off
the actual Rectangles — it does not recompute them.

    HEADLESS-2  1920x1080  factor 1.0   card 400px wide, radius 15

That is the remainder, stated as it was handed over: two outputs at compositor

### check-scale-tokens.sh had to learn the migrated spelling
Its rules matched `Theme\.fs\(` and `font.pixelSize:\s*Theme\.px\(`. A file that
migrates to `theme.` FALLS OUT OF THE GUARD at the moment it is migrated — the
guard this same roadmap item landed would have retired itself one file at a
time. It now matches `(Theme|Metrics|theme)\.`, and the self-test carries a
second mutant in the per-output spelling so the rule cannot be narrowed back
without the self-test noticing.

Two new rules: fs() must be defined exactly once under `src/theme` counting only
definitions that carry the floor (Theme.qml forwards and is not a copy); and a
named per-output surface must still declare its own ThemeSet AND read no size
from the global Theme. The file list there is written out rather than discovered
— discovering it by grepping for `ThemeSet {` would mean deleting the
declaration removes the file from the list and the rule silently stops applying.

## THE REST OF THE TREE IS ITS OWN UNIT — the design, and why

114 of the 116 files still read the global Theme. I did not migrate them, and
the reason is not the call-site count. The count turned out to be the cheap part.

### The mechanism is solved and measured
QtQuick's `Screen` attached property gives any Item the output it is displayed
on, with NO plumbing — no scope object threaded through the tree, no
`required property` on every component, no Loader forwarding. Measured on the
two-output harness: correct per window, corrected 1ms after construction (it
reports the primary output until the item lands on its own), and first paint is
at 39-84ms, so the correction beats the first frame and nothing animates from a
wrong size. A window is better still: `PanelWindow.screen` is exact at t=0, which
is why the two migrated surfaces use `Theme.factorForScreen(root.screen)` and
never touch the attached property.

With that, the migration of a file is: one property declaration, then
`Theme.` -> `theme.` for the SIZE reads only. Mechanical.

### Three costs that the call-site count does not include

**(a) Sizes that cross window boundaries through singletons — the real blocker.**
`TopBar.qml` writes its notch widths into a singleton:

    Binding { target: ShellState; property: "topBarLWidth"; value: root.lWidth }   (x3)

One singleton field, one bar per output, last writer wins. It is harmless today
only because every bar computes the same number. Under per-output sizing the two
bars write different numbers into one field, and `PopupDismiss.qml` reads all
three back (4 reads) to carve out its click-through regions — on the wrong
output's geometry, half the time, non-deterministically. `Popups.dashboardPageWidth`
(3 reads) has the same shape. Seven reads across two files, and every one of them
has to become per-screen state (a map keyed by screen name, or the value moved
onto the per-screen Scope) BEFORE any bar is migrated. This is a design change,
not a rename.

**(b) The bar height is the shell's layout datum, and it is global.**
Nothing that positions itself relative to the bar can be migrated alone.
`Border.qml` sets `margins.top: Theme.notchHeight`; `Osd.qml` sets
`margins.top: Theme.notchHeight + 14`. Migrate the border and leave the bar
global and the strip starts at the wrong row on the non-reference output — a
visible gap. Migrate the bar and its height changes while the notch CONTENT
(LeftContent/CenterContent/RightContent and everything under them) stays at the
global factor: icons the wrong size for the bar they sit in. So the bar and its
whole subtree are one indivisible step, and that subtree is the bulk of the 114
files. This is the honest reason the two surfaces I migrated are modals: they are
the only kind of surface that is anchored to nothing but its own screen.

**(c) Nine files cannot use the mechanism at all.**
`Screen` attaches to Items. These read Theme/Metrics from a QtObject or
Singleton root:

    src/theme/{Theme,Metrics,Colors,ColorLoader}.qml   the theme layer itself
    src/state/DashboardLayout.qml        8 refs, incl. Theme.scale directly
    src/state/Popups.qml                 2 refs
    src/services/plugins/PluginService.qml  10 refs
    src/services/WallpaperService.qml     4 refs
    src/services/SettingsService.qml      3 refs

27 refs across the five real consumers. Each needs a screen passed in by its
caller, or the value it computes has to move to the surface that consumes it.
`DashboardLayout` is the awkward one: it does layout arithmetic for a dashboard
that is drawn inside a per-output bar.

### The design, if someone takes it
1. Make the cross-window singleton sizes per-screen first — `ShellState.topBar*`
   and `Popups.dashboardPageWidth` keyed by screen name, with their readers
   updated. Nothing visible changes while every bar still computes the same
   number, so this lands and is verifiable on its own.
2. Give the five non-Item consumers an explicit screen (or move their arithmetic
   to the consuming surface).
3. Add a shared per-factor ThemeSet registry before migrating in bulk. The two
   surfaces here build one ThemeSet each, which is fine for two; a fully
   migrated tree would build one per component instance. The token set is a pure
   function of the factor and there are at most five distinct factors, so an
   `Instantiator` over the factors DERIVED from `scaling.js` (not a second list
   of them) gives one object per factor for the whole shell.
4. Then migrate by surface, bar-plus-subtree as a single step, with
   check-scale-tokens' per-output list extended each time.

Each of 1-4 is provable on the existing two-output harness. Step 4 is the one
that cannot be verified headlessly beyond "it resolved the right number" — it
changes what the desk looks like, and this agent has no display to look at.

## ALSO LANDED: the scaling suites were never in CI
`.github/workflows/ci.yml` named `check-scale-tokens.sh` and nothing else from
this item. `tests/scaling-test.js` exists BECAUSE the QML suite needs a
compositor and skips without one — "which is every CI runner this project has",
in its own header — and it had never been added to the workflow, so the
breakpoint table it guards has been unguarded in CI since it was written. It is
now a step, and so is `run-scaling-test.sh`, run twice: once on a desk whose
outputs disagree and once with `SCALING_SCALES="2 1"` bringing them into
agreement, because those are different verdicts. The live runner skips cleanly
(status 0) where quickshell or a compositor is absent, so adding it costs
nothing on a runner that cannot host it. ci.yml re-parses clean.
