## Criteria, quoted from roadmap.yaml

1. Standard vs administrator accounts, fast switching, per-user
   agents/secrets/profiles, and session isolation work.
2. Guest sessions can be disposable.
3. Kiosk/shared-device policy is possible without weakening ordinary desktop
   use.
4. Remote agent permissions are bound to the owning user/session.

## What this program already knows that bears on it

- **Origin classification is the heart of criterion 4.** `apex-agentd`
  establishes request origin from the connection's cgroup
  (`apex-agentd/src/origin.rs::classify`), and a per-connection origin latch was
  added for APEX Remote: a non-session connection may declare a narrower origin
  once, monotonically. Criterion 4 is that mechanism seen from the user axis
  rather than the device axis — read it before designing anything.
- `tests/in-login-session.sh` mints a real logind session via PAM so
  `origin::classify` sees a local origin. That is how you test a second user
  without a second human.
- **Per-user secrets already exist**: `apex-secretd` is the protected service
  and capability sets are per-caller. Criterion 1's "per-user secrets" is
  probably an assertion about what is already true, plus the gaps it exposes.
- "Standard vs administrator" on this system is not `wheel` alone: APEX has its
  own privilege decision (`privilege::decide`) with seven request origins, and
  sudo is only one path into it.

## Traps

- Criterion 3 says kiosk policy must be possible **without weakening ordinary
  desktop use**. A change that makes every desktop more locked down to enable
  kiosk has failed the criterion, not met it.
- Creating real users on this machine is a live-system change. Prefer a
  namespaced or fixture user; if you must create one, say so on this card and
  remove it. **Never touch Andre's own account.**
- Do not trigger a polkit or keyring prompt while testing switching.

### Follow-ups, in value order

- **`ensure_private_dir` does not check ownership.** With the per-uid scratch
  root the accident is gone, but a predictable name in sticky `/tmp` can still
  be pre-created by another account, and the chmod then fails. Refusing a
  directory the caller does not own would close it and touches ~40 call sites —
  too broad for this round, and written down in `SCRATCH_ROOT_PREFIX`'s doc.
- **`peer::is_own_user` in `apex-agentd` is a classification branch, not a
  refusal** (`privilege.rs:220`). A foreign uid skips the ancestry walk and the
  request proceeds. That is DELIBERATE — `sudo apex request approve` arrives as
  uid 0 — but the function's own doc comment says "checked anyway ... the
  consequence of being wrong is that another account's process files privilege
  requests attributed to this user", which overclaims. `apex-remoted`
  (`control.rs:175`) and `apex-aid` (`main.rs:310`) DO refuse. Do not "fix" the
  agentd one without handling the sudo path; the doc comment should be
  corrected either way.
- **The guest wipe is not wired to session end.** The unit is
  `After=user-%i.slice`, which orders but does not fire. `BindsTo=` +
  `ExecStop=`, or `pam_exec` at session close, needs a machine with a real
  second account. Untested, and said so in the README.
- **Nothing creates a standard (non-wheel) account.** `installer/apex-install`
  line 570 puts the single account in `wheel` unconditionally and the GUI
  offers no choice. Criterion 1's "standard vs administrator" is ENFORCED
  (polkit `auth_admin`, build-asserted at `Containerfile.base:139-140`) but not
  CREATABLE through any APEX surface.
- **Pairing store is per-user but unasserted.** `$XDG_STATE_HOME/apex/remote/
  {identity.key,devices.json}` — no test says a device paired by one user
  cannot drive another's runtime.

### Do not redo

- The end-to-end shell suite for the classify fix. Live confirmation + unit
  tests + 2 mutations already cover it; a new `pr-validation.yml` step was
  judged conflict risk for redundant coverage.
- A `may_be_granted` fifth condition for guest/kiosk. polkit `auth_admin`
  already refuses one step later, and `apex-agentd` is opt-in so a kiosk
  account would not have it.
