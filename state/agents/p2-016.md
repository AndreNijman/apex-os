## Criteria, quoted from roadmap.yaml

1. Standard vs administrator accounts, fast switching, per-user
   agents/secrets/profiles, and session isolation work.
2. Guest sessions can be disposable.
3. Kiosk/shared-device policy is possible without weakening ordinary desktop
   use.
4. Remote agent permissions are bound to the owning user/session.

## What this program already knows that bears on it

- **Origin classification is the heart of criterion 4.** `apex-agentd`
  establishes request origin from the connection's cgroup
  (`apex-agentd/src/origin.rs::classify`), and a per-connection origin latch was
  added for APEX Remote: a non-session connection may declare a narrower origin
  once, monotonically. Criterion 4 is that mechanism seen from the user axis
  rather than the device axis — read it before designing anything.
- `tests/in-login-session.sh` mints a real logind session via PAM so
  `origin::classify` sees a local origin. That is how you test a second user
  without a second human.
- **Per-user secrets already exist**: `apex-secretd` is the protected service
  and capability sets are per-caller. Criterion 1's "per-user secrets" is
  probably an assertion about what is already true, plus the gaps it exposes.
- "Standard vs administrator" on this system is not `wheel` alone: APEX has its
  own privilege decision (`privilege::decide`) with seven request origins, and
  sudo is only one path into it.

## Traps

- Criterion 3 says kiosk policy must be possible **without weakening ordinary
  desktop use**. A change that makes every desktop more locked down to enable
  kiosk has failed the criterion, not met it.
- Creating real users on this machine is a live-system change. Prefer a
  namespaced or fixture user; if you must create one, say so on this card and
  remove it. **Never touch Andre's own account.**
- Do not trigger a polkit or keyring prompt while testing switching.

### The three findings, in value order

1. **`apex-remoted`'s control socket asked who was asking for exactly one of
   its four verbs.** `Pair` was checked; `Status`, `Devices` and `Revoke` were
   not. With a second account and the directory and socket modes widened by
   hand — so the filesystem was not the thing answering — uid 1042 got the
   owner's machine key, LAN addresses and paired-device list, and reached the
   owner's device STORE through `Revoke`, which answered "no paired device
   'somebody-elses-phone'": it had looked. Fixed; re-measured; the owner is
   unaffected. **Two filesystem fences had to be opened to get there** (the
   `0700` directory AND the socket mode — `connect(2)` needs write), so this
   was defence in depth, not an open door.
2. **The obvious session-end wiring does not work and fails silently.**
   `BindsTo=user-%i.slice` never fires: logind does not stop the user slice,
   and a unit that BindsTo it is a reference that stops the slice being garbage
   collected — so the hook prevents the event it waits for. `user-1042.slice`
   stayed `active` indefinitely after logout; removing the hook, it was
   collected in seconds. `user-runtime-dir@%i.service` is what logind actually
   stops.
3. **A logind record stuck in `State=closing` makes the wipe refuse, for
   ever.** Third live cycle: the guest logged out, the record stayed, fence 4
   refused, the unit went RED, nothing was wiped. That is the correct
   conservative answer — "stuck record" and "somebody is sitting there" look
   identical from inside the engine — and the thing that matters is it was
   VISIBLE. With the boot unit's `SuccessExitStatus=0 2` copied across, as the
   first draft had, it was a green `systemctl status` over an unwiped guest
   home. The boot sweep is the documented backstop.
