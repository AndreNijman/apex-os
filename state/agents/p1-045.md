## FOUND
- `/etc/containers/policy.json` on the L16 is byte-identical to `/usr/etc/containers/policy.json`
  and contains one `insecureAcceptAnything` default. Every APEX image is cosign-signed and
  SBOM-attested in CI, and NOTHING on an installed machine checks any of it. The booted
  deployment's origin records this in its own words:
  `container-image-reference=ostree-unverified-registry:ghcr.io/andrenijman/apex-os:daily`.
- `bootc status` requires root even to READ (it opens the sysroot for write), so it is
  unusable from `apex status`. `rpm-ostree status --json` works unprivileged; so does
  reading `/proc/cmdline` -> `ostree=` symlink -> `<deploy>.origin`, which is world-readable.
- The booted image HAS a cosign signature in the registry
  (`ghcr.io/andrenijman/apex-os:sha256-308127d9....sig`), signed by
  `https://github.com/AndreNijman/apex-os/.github/workflows/build-image.yml@refs/heads/main`,
  source revision 57f593a. It has NO `.att` tag: the SBOM attestation landed on
  roadmap/v2.2 and has never been built, so "attestation absent" is a live, real state.
- `cosign` is not installed in the APEX image; `skopeo` and `openssl` are. So a machine can
  learn that a signature EXISTS and read the identity it claims, but cannot check its
  cryptography. That is a third state, distinct from signed and from unsigned.
- `Blueprint::version` is `Option<u32>` documented as "Absent means SCHEMA_VERSION". That is
  backwards: a file written before the key existed would be read as whatever version the
  CURRENT build is. Harmless while SCHEMA_VERSION is 1; at 2 it silently misreads every
  blueprint on disk. `validate()` also refuses `version != SCHEMA_VERSION`, so an OLDER
  blueprint is refused outright rather than migrated — the forward direction is broken today.
- `AppliedState` (blueprint-state.toml) has a REQUIRED `schema: u32` field and
  `AppliedState::parse` (apexd-core/src/blueprint.rs:1009) never looks at it. It is also
  `deny_unknown_fields`, so a record written by a newer build fails to parse, and
  `load_applied()` swallows that with `.ok()?` — the user is told no apply has ever happened.
- `TaskState` (apexd-core/src/task.rs:607) documents dropping unknown keys because "there is
  no second writer whose fields would be lost". Across a `bootc rollback` the second writer is
  the newer build of the same program: it writes a field, the rollback's build reads and
  rewrites without it, and rolling forward finds it gone. Silent loss, reasoned away in a
  comment.
- `apex recover status` labels the current deployment "ostree 1d98b51dd766", which is the
  BOOTCSUM from the `ostree=` cmdline argument, not the deployment commit (f3f505fc...).
  Both values confirmed live. Wrong label, right data.
- `docs/rollback.md` claims "Promotions to a stable channel get an annotated git tag
  (good-YYYYMMDD)". No channel and no such tag exists. That lands in P1-046.
- NOT a defect, contrary to a survey: `HostCaps` DOES carry `#[serde(flatten)] unknown`
  (apexd-core/src/host.rs:516). Checked directly.
- `apex-agent-core/src/request.rs:665` appends to `privilege-audit.jsonl` with no
  `.mode(0o600)`, unlike `apex-secret-core/src/audit.rs:194` which sets it. Umask-dependent.
- No channel/ring/stream concept exists anywhere in the tree. `Containerfile.base:472` states
  "ONE update channel" as a deliberate product invariant, so P1-046 is a reversal of a stated
  decision, not a gap-fill. `apex`, `daily`, `gaming-mesa`, `gaming-nvidia` are four aliases
  for ONE digest and must stay that way forever (build-image.yml:21-30).
- `clippy` is installed on neither the L16 nor katana. Run it as
  `podman run --rm -v <wt>:/src:z -w /src/apexd docker.io/library/rust:1.97 cargo clippy`.
