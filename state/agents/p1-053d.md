### Four shipped defects the device found

1. **Every pairing code advertised an IPv6 address no phone could dial**, two
   ways stacked. `format!("{ip}:{port}")` on a V6 gives nine colon groups and no
   brackets, so `splitHostPort` takes the whole string as a host and falls back
   to port 7717; and even bracketed, `main.rs` binds `0.0.0.0`, so nothing was
   listening. Invisible on dual-stack because the V4 address is tried first.
   `PairingServiceTest`'s own header asserted the desktop bracketed them. It did
   not, and neither side could see the disagreement because each tested itself
   against its own belief about the other.
2. **The phone could not start the `generic` adapter at all.** The picker is
   `Hello.agents`, which lists it; the wire builder had no `args`, which is
   where its program goes.
3. **The Checkpoint switch had no accessible name** — its words are in a
   sibling Column, so TalkBack announced "off, switch". ATF passes that screen;
   an unnamed switch is not one of its rules.
4. **"Guide" was invisible at font scale 2.0** — four `TextButton`s do not fit
   across a Pixel 7a and a `Row` resolves that by measuring the last child at
   width ZERO. `FlowRow` wraps instead.

Plus **Espresso pinned to 3.7.0**: Compose's test artifacts resolve it at 3.5.0,
every `waitForIdle()` goes through `Espresso.onIdle()`, and on Android 14+ that
throws `NoSuchMethodException: android.hardware.input.InputManager.getInstance`.
Measured on SDK 37: every Compose test died before its first assertion.

### The suite's own false green, and the fix

The first accessibility run **passed while checking nothing**:
`tryPerformAccessibilityChecks()` on an empty node collection is a no-op, so
"no composition at all" and "every screen is fine" were the same result.
Logcat: `isSleeping=true isVisible=false`, the host activity launching and being
DESTROYED a frame later behind a secure keyguard. `wm dismiss-keyguard` cannot
clear a keyguard with a credential on it and no `adb` verb can present a
fingerprint. `ComposeHostActivity` in `src/debug` declares `showWhenLocked` and
`turnScreenOn` (and `MainActivity`'s exact `configChanges`); `ComposeHostTest`
is the floor under everything else, and every walk now asserts the tree is
non-empty **before** checking anything about it.

### P1-051 C6 — observed, and the observation beats a test

On first launch the app raises a `BiometricPrompt` before anything else.
**An agent with full adb access to a debuggable build could not get past it** —
no adb verb presents a fingerprint on real hardware, and "Use PIN" wants the
owner's credential. Consequence: **the live app's UI could not be driven end to
end**, so `LanEndToEndTest` drives `PairingService` — the production class —
with a `PlainBox` in place of `KeystoreSecretBox`, and names that substitution
in the file.

### GrapheneOS refuses this vs the app is broken

Nothing this round was a GrapheneOS refusal. The three device-level obstacles
were **a secure keyguard** (any Android, any phone with a lock), **an ungranted
`POST_NOTIFICATIONS`** (standard since API 33), and **Espresso reflecting on a
platform method removed in Android 14**. GrapheneOS's own hardening never
refused anything: `adb`, `pm install`, `am instrument`, `UiAutomation`
permission grants, `dumpsys`, `settings` and raw TCP to the L16 all worked.
The one GrapheneOS-specific finding is the *opposite* of a restriction —
sandboxed Play services are present, so the no-push claim is a property of the
app rather than of the phone.

### P1-051 C4, recorded rather than chased

A pairing offer **was** minted this round from a bash process inside a Claude
Code session: `may_pair` → `origin::observe_pid` classified that shell as
`local-terminal`. The Rust end-to-end suite relies on the same classification,
so this is the classifier's known scope and not a new hole — but it is the
exact shape "pairing cannot be completed silently by an agent" forbids, and it
belongs in front of somebody.
