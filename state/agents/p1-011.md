## PINNED FACTS (no live account was called; these come from the schema)
`cloudflare/api-schemas` `openapi.json` at **`d5003a19`** (info.version 4.0.0),
the same pin P1-005 used:

- `POST /accounts/{account_id}/tokens` — account-owned API token. Requires
  `name` + `policies`; accepts `expires_on`, `not_before`, `condition.request_ip`.
  Response `result.value` carries the token, `result.id` the handle.
- `DELETE /accounts/{account_id}/tokens/{token_id}` — revoke.
- `GET /accounts/{account_id}/tokens/permission_groups?name=&scope=` — the only
  way to turn a permission-group NAME into the id a policy needs. `name` on a
  permission group is `readOnly`; `id` is required.
- `policies[].resources` is a map, e.g.
  `{"com.cloudflare.api.account.<id>": "*"}` or
  `{"com.cloudflare.api.account.zone.<id>": "*"}`, or one nested level.
- Schema quirk: `policies[].id` is listed `required` **and** `readOnly`, with
  `x-stainless-terraform-always-send`. Creation omits it.

## FOUND
- **`Provider::mint` is already wired.** It is declared at
  `apexd/apex-secretd/src/provider.rs:284` and called at
  `apexd/apex-secretd/src/service.rs:566`, between the host pin and `perform`,
  with the minted value scrubbed alongside the stored one. No shipped provider
  overrides it; the test-only `providers/bearer.rs` does.
  *(An earlier note here said it had no caller. That was wrong — a `grep | head
  -30` cut the list off before `service.rs`. Absence from a truncated list is
  not absence, which is this repository's own recurring defect.)*
- What is actually missing is the **shape**, not the hook:
  `Result<Option<SecretValue>, ProviderError>` cannot distinguish "this
  provider has no narrower form" from "the far side refused to mint" from
  "minting could not run". `Ok(None)` is all three.
- **There is no revoke hook at all.** `service.rs:566-574` uses a minted value
  once and drops it at end of scope, so a minted token would live out its full
  TTL after the operation — including after a failed one.
- `AuditLine` has no field saying which of those outcomes happened.
- **A mutation that did not bite, and what it found.** The first mutation of
  the "refused to mint" arm came back green. Cloudflare gates *reading* the
  permission-group list and *creating* a token on the same permission, so a
  credential that lacks it is turned away at either place — and the test only
  ever reached one of the two. A second double mode (`Mode::ListDenied`) was
  added and both arms are measured now. A mutation that does not bite is worth
  more than one that does.
- **Cloudflare requires Super Administrator on the account to create an
  account-owned token.** So `Denied` is expected to be the *ordinary* live
  answer, not a rare one. That is why three of the four arms fall back to the
  stored credential instead of refusing: §13.4 says *prefer*, and refusing
  would break every operation P1-004 through P1-010 landed for any owner whose
  stored token is not a Super Administrator's. The change is that the trail now
  says which of the three happened. A provider that has been told the project
  will not accept a fallback returns `Err` and nothing runs — the framework
  path exists and is tested
  (`a_provider_that_will_not_run_without_a_narrowed_credential_stops_the_operation`),
  but no project file can say so yet. See BLOCKED ON.
- **Permission-group ids are not knowable offline**, so `POLICY` names the
  groups and the account's own list turns a name into an id. Each slot lists
  the spellings this build will accept (`Edit` for most products, `Write` for
  Access) so a wrong guess degrades to "could not build a policy" — which
  falls back, visibly — rather than to a token that silently cannot do its job.

  choices rather than measurements.** There is no Cloudflare account and no
  token on this machine; everything runs against the loopback double, which
  answers nothing to a request with no `Authorization` header.
  1. **The minimum `expires_on` Cloudflare accepts.** No documentation gives a
     floor. `LIFETIME_SECS = 300` is this build's choice. If Cloudflare refuses
     it the refusal arrives as a 400, which this build answers `CouldNotRun` —
     the operation still runs, on the stored credential, and the trail says
     why. Safe failure, but a live account would settle it in one request.
  2. **The exact permission-group name per product.** Mitigated by the
     candidate list above rather than assumed.
- **The default is to attempt narrowing on every operation.** For an owner
  whose token cannot mint, that costs one wasted request per operation,
  forever. A per-daemon memo of "this credential was denied" would pay it once;
  not built, because it is cross-request state in a service that deliberately
  has almost none.
