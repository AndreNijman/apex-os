## PLAN
Ordered, because P1-012 and P1-013 both sit on P1-011.

1. **P1-011.** `mint` becomes a verdict, not an `Option`. Cloudflare mints a
   short-lived account-owned API token scoped to the operation, spends it in
   the broker's `curl`, and revokes it — including when the operation fails.
2. **P1-012.** Generalise the broker's child-process runner so a credential can
   be presented as an environment variable to a broker-owned `wrangler` /
   `cloudflared` / `terraform`, not only on `curl`'s stdin.

   operations; the flow over them, preview health check and staged rollout.

## PINNED FACTS (no live account was called; these come from the schema)
`cloudflare/api-schemas` `openapi.json` at **`d5003a19`** (info.version 4.0.0),
the same pin P1-005 used:

- `POST /accounts/{account_id}/tokens` — account-owned API token. Requires
  `name` + `policies`; accepts `expires_on`, `not_before`, `condition.request_ip`.
  Response `result.value` carries the token, `result.id` the handle.
- `DELETE /accounts/{account_id}/tokens/{token_id}` — revoke.
- `GET /accounts/{account_id}/tokens/permission_groups?name=&scope=` — the only
  way to turn a permission-group NAME into the id a policy needs. `name` on a
  permission group is `readOnly`; `id` is required.
- `policies[].resources` is a map, e.g.
  `{"com.cloudflare.api.account.<id>": "*"}` or
  `{"com.cloudflare.api.account.zone.<id>": "*"}`, or one nested level.
- Schema quirk: `policies[].id` is listed `required` **and** `readOnly`, with
  `x-stainless-terraform-always-send`. Creation omits it.

**P1-012 — transparent brokered wrangler/terraform. Both criteria closed.**

- `75df89b1`. `broker::run_tool` is `run_git`'s credential branch generalised,
  not a second mechanism: `run_git` has always put `APEX_GIT_TOKEN` in a
  child's environment, because `/proc/<pid>/cmdline` is world-readable and an
  environment is not. The environment is built in the parent and never
  inherited.
- The vocabulary is four subcommands — `wrangler deploy`,
  `wrangler versions upload`, `terraform plan`, `terraform apply` — each with
  an argv this build writes. **There is deliberately no
  `cloudflare.wrangler.run`**: a grant to pass your own argv to wrangler is a
  grant to do everything wrangler can do.
  `nothing_a_caller_sends_can_reach_a_brokered_command_line` asserts no
  brokered operation declares a parameter.
- Transparency is `files/system/libexec/apex-tool-broker`, symlinked under each
  tool's own name. **What puts it on an agent's PATH is `apex-agentd`, not the
  profile.d drop-in** — `/etc/profile.d/*.sh` is read by a *login* shell and an
  agent's tool calls are `bash -c '…'`. `install_session_bin` symlinks the
  shims into the session's scratch `bin`, the directory that already goes first
  on a confined session's PATH next to the `git` shim. The profile.d file is
  for a person who opens a terminal inside a managed session, and now says so
  in its own comment.
  `tests/test-apex-tool-broker.sh`, 18 cases, wired into `pr-validation.yml`.
- The shim understands `--env <name>` (it becomes the worker the daemon
  resolves) and reads `name` out of `wrangler.toml`/`.json`/`.jsonc` the way
  wrangler does, so a skill that has always run a bare `wrangler deploy` sets
  no variable and changes nothing.
- **`cloudflared` is declined, with the reason recorded.** `Performed` carries
  an exit code and a `String`; every useful `cloudflared` subcommand streams or
  is a daemon. And `mod.rs:911-918` already declined its connector token
  because it is presented to the Cloudflare edge over QUIC, not to any HTTPS
  host the store can pin it to. §12's `cloudflared auth -> APEX` is where that
  belongs.

**P1-013 — transactional deploy flow. Three of four criteria closed.**

- `7c29a6b4`. *Version upload separated from traffic deployment*: was already
  true and nothing said so; now
  `uploading_a_version_puts_it_in_front_of_nothing` says it, including that the
  upload grant does not carry the deploy.
- *Staged rollout*: did not exist — `deployment_body` hard-coded
  `percentage: 100`. Cloudflare's payload is the **whole split every time**, so
  "send 30% here" cannot be expressed without saying where the other 70% goes,
  and the only honest answer is the version that has it now. That costs a
  credentialled lookup, so a staged rollout is two requests the way
  `dns.update` is. `deploy::Current` has five values and three are refusals,
  modelled on `dns::Lookup`.
- *Rollback path tested*: `the_rollback_path_puts_an_older_version_back_and_says_it_meant_to`
  — including `?force=true`, without which Cloudflare reads a return to an
  older version as a deployment that lost a race.

**P1-005's open criterion is CLOSED, with one dimension named as not closed.**
`an_operation_spends_a_credential_that_did_not_exist_a_moment_ago_and_does_not_outlive_it`
asserts the operation's own request carried the minted token and not the
stored one, that the stored one was spent on exactly three requests, and that
the revoke names the same id that was issued. What is *not* closed: an R2
token cannot be narrowed to a bucket **and still work here** — R2's
bucket-scoped resource string carries the Object permissions, and Cloudflare
documents those as S3-only, unusable against the REST API this broker speaks.
So an R2 token is narrowed by product and lifetime; the bucket narrowing stays
in `binding.rs` where P1-005 put it. DNS is the surface where the narrowing
does reach the resource: its permission groups are zone-scoped, so a minted
DNS token names the one zone the project bound
(`a_token_minted_for_dns_names_the_one_zone_this_project_bound`).

## FOUND
- **`Provider::mint` is already wired.** It is declared at
  `apexd/apex-secretd/src/provider.rs:284` and called at
  `apexd/apex-secretd/src/service.rs:566`, between the host pin and `perform`,
  with the minted value scrubbed alongside the stored one. No shipped provider
  overrides it; the test-only `providers/bearer.rs` does.
  *(An earlier note here said it had no caller. That was wrong — a `grep | head
  -30` cut the list off before `service.rs`. Absence from a truncated list is
  not absence, which is this repository's own recurring defect.)*
- What is actually missing is the **shape**, not the hook:
  `Result<Option<SecretValue>, ProviderError>` cannot distinguish "this
  provider has no narrower form" from "the far side refused to mint" from
  "minting could not run". `Ok(None)` is all three.
- **There is no revoke hook at all.** `service.rs:566-574` uses a minted value
  once and drops it at end of scope, so a minted token would live out its full
  TTL after the operation — including after a failed one.
- `AuditLine` has no field saying which of those outcomes happened.
- **A mutation that did not bite, and what it found.** The first mutation of
  the "refused to mint" arm came back green. Cloudflare gates *reading* the
  permission-group list and *creating* a token on the same permission, so a
  credential that lacks it is turned away at either place — and the test only
  ever reached one of the two. A second double mode (`Mode::ListDenied`) was
  added and both arms are measured now. A mutation that does not bite is worth
  more than one that does.
- **Cloudflare requires Super Administrator on the account to create an
  account-owned token.** So `Denied` is expected to be the *ordinary* live
  answer, not a rare one. That is why three of the four arms fall back to the
  stored credential instead of refusing: §13.4 says *prefer*, and refusing
  would break every operation P1-004 through P1-010 landed for any owner whose
  stored token is not a Super Administrator's. The change is that the trail now
  says which of the three happened. A provider that has been told the project
  will not accept a fallback returns `Err` and nothing runs — the framework
  path exists and is tested
  (`a_provider_that_will_not_run_without_a_narrowed_credential_stops_the_operation`),
  but no project file can say so yet. See BLOCKED ON.
- **Permission-group ids are not knowable offline**, so `POLICY` names the
  groups and the account's own list turns a name into an id. Each slot lists
  the spellings this build will accept (`Edit` for most products, `Write` for
  Access) so a wrong guess degrades to "could not build a policy" — which
  falls back, visibly — rather than to a token that silently cannot do its job.

## FOUND — not this unit's, but measured rather than assumed
**`apex::provenance::tests::a_git_status_that_could_not_run_is_not_a_clean_working_tree`
is flaky, it is PRE-EXISTING, and the reason is worth someone's attention.**

P1-005's card reported it failing once in six runs and left it there. It is
reproducible: **1 failure in 8 runs** of `cargo test -p apex --bin apex` on
this branch, and **1 in 14 at the branch point `24472b64`**, in a worktree with
none of this unit's changes. This unit touches nothing under `apexd/apex/` —
`git diff --stat origin/roadmap/v2.2...HEAD` lists no file there. So it is not
this unit's, and that is measured rather than claimed.

The failure is not the assertion the test is about. It is:

```
panicked at apex/src/provenance.rs:1596:22:
Unmeasured("/tmp/apex-prov-…-gitfail-… is not a git checkout and carries no revision file")
```

The test writes a `fakegit` shell script, `chmod 0755`s it and runs it. Under
parallel load that exec intermittently fails — the classic `ETXTBSY` window,
where another test thread forks while the writable fd to the new file is still
open, and the fork's child holds it until its own exec. The fixture directory
is unique (pid + nanoseconds), so it is not a collision.

**And the shape of the failure is this repository's own recurring defect, one
level up.** A `git` that could not be *executed* is reported by
`revision_of_with` as *"is not a git checkout"* — a could-not-run collapsed
into an absence, which is exactly what `verify.rs::Verdict`, `dns::Lookup`,
`deploy::Current` and now `Minted` all exist to prevent. The flaky test is the
symptom; the interesting thing is that the production path underneath cannot
say "I could not run git". Worth an item for whoever owns `provenance.rs`. Not
touched here: it is another unit's file and fixing it would widen this diff
into code this unit has no business changing.

## BLOCKED ON
- **Not verified against a live account, and two things therefore stand as
  choices rather than measurements.** There is no Cloudflare account and no
  token on this machine; everything runs against the loopback double, which
  answers nothing to a request with no `Authorization` header.
  1. **The minimum `expires_on` Cloudflare accepts.** No documentation gives a
     floor. `LIFETIME_SECS = 300` is this build's choice. If Cloudflare refuses
     it the refusal arrives as a 400, which this build answers `CouldNotRun` —
     the operation still runs, on the stored credential, and the trail says
     why. Safe failure, but a live account would settle it in one request.
  2. **The exact permission-group name per product.** Mitigated by the
     candidate list above rather than assumed.
- **The default is to attempt narrowing on every operation.** For an owner
  whose token cannot mint, that costs one wasted request per operation,
  forever. A per-daemon memo of "this credential was denied" would pay it once;
  not built, because it is cross-request state in a service that deliberately
  has almost none.
- **P1-013's *"Preview health checks supported"* is OPEN, and not
  approximated.** A health check is an unauthenticated GET against a
  `*.workers.dev` preview URL. The framework's host pin means a credential
  stored for `api.cloudflare.com` may only ever be sent there — which is
  right, and is exactly why this cannot be a brokered operation. It is `apex
  cf` CLI work, alongside the command that sequences upload -> preview ->
  check -> staged -> full. Nothing in the broker blocks it; nothing in the
  broker can do it either.
