## Measured before writing anything

- `sudo -n true` works on the L16 — non-interactive sudo is available.
- **`smartctl -j /dev/nvme0n1` as an unprivileged user exits 2** and returns a
  document with only `json_format_version`, `local_time` and `smartctl`, where
  `smartctl.exit_status` is 2 and `smartctl.messages` holds
  `"Smartctl open device: /dev/nvme0n1 failed: Permission denied"`. A reader
  that keys on the absence of `nvme_smart_health_information_log` reports
  "no SMART data" for a disk that has plenty.
- **`sudo smartctl -j /dev/nvme0n1` exits 0 and also returns no health log.**
  smartctl with no action option does nothing; `-a` (or `-x`/`-H`/`-A`) is
  what asks. Exit 0 plus an empty document is the same trap wearing root.
- `fwupdmgr get-devices --json` answers as `andre` with no session bus at all
  (it uses the system bus). No polkit prompt.
- **`io` is not in the root cgroup's `subtree_control`** (`cpu memory pids`
  are), so no `io.max` file exists anywhere under `user.slice`. I/O budgets
  are not enforceable for a user-service agent on this machine as shipped.
- `apex-agentd.service` has no `Delegate=`, so systemd owns its cgroup and
  sub-cgroups are unsupported until a drop-in adds one.
- **Nothing in any Containerfile installs `fwupd`** and
  `rpm -q --whatrequires fwupd` says no package requires it — it rides in from
  `quay.io/fedora/fedora-bootc:43`. `apex update`'s firmware pass in `ops.rs`
  depends on a package the image does not own.
- `smartmontools`, `nvme-cli`, `udisks2`, `gparted`, `parted`, `gdisk` are
  installed explicitly by `Containerfile.core:1017`.

**Shape note for a successor: this is `Roots` + `$APEX_STORAGE_ROOT` (the
`apex trust` shape), NOT the `detect_from(sys_root, proc_root)` the old NEXT
asked for.** Deliberate: storage needs three roots (sysfs, proc, /run/udev)
plus two subprocess answers (smartctl, systemctl), and a fixture prefix covers
all five where a two-argument signature covers two. Do not "fix" it.

Sources actually used, and why they differ from the card's list: `lsblk -J`
and `findmnt -J` are not spawned — `/sys/block` and `/proc/self/mountinfo` are
the same data with no subprocess and no JSON schema to track. `nvme smart-log`
is not spawned either: `smartctl -j -a` already returns
`nvme_smart_health_information_log`, and `nvme list` prints the serial to any
user. `blkid` is not spawned — see the measurement below.

## Measured, second pass (P2-014)

- **`blkid -o value -s TYPE /dev/nvme0n1p5` unprivileged exits 0 and prints
  nothing.** Same trap family as the two smartctl ones: exit zero, no data, no
  error. A caller trusting it reports an encrypted disk as unencrypted. The
  filesystem type comes from `/run/udev/data/b<major>:<minor>` instead — udev
  wrote it as root at boot and left it world-readable.
- **smartctl's exit status is a bitmask and bits 3-7 mean the read WORKED.**
  Bit 3 is "DISK FAILING". `if status != 0 { unavailable }` turns the one row
  this feature exists for from red to grey. This is not on the card's trap list
  and is the biggest of the three.
- **`/` is `overlay`/`composefs`, 37.8M, 0 available, 100% used** on every
  bootc machine forever, and `/dev/nvme0n1p5` is mounted at five paths. Free
  space is per filesystem-on-a-block-device, one row, or the report is a
  permanent false alarm about a machine with 1.1 TB free.
- **btrfs writes `discard=async`, not `discard`.** A comparison against the
  bare word reads every btrfs filesystem on this OS as untrimmed.
- Two hwmon layouts both live on the L16: `<device>/hwmon4` (nvme) and
  `<device>/hwmon/hwmon6` (platform). Checking one reports "no sensor" for the
  other's hardware.
- **`cargo test --workspace` has ONE pre-existing failure in this environment**
  and it is not a regression: `apex-agentd` `system_grants.rs`
  `renewing_a_grant_that_does_not_exist_is_refused_without_asking_anybody`.
  `origin::classify` reads the caller's cgroup; an agent running under
  `user@1000.service/app.slice/apex-roadmap-resume.service` is a systemd user
  service, so §7 classifies it `ScheduledJob` and refuses elevation before the
  test's assertion is reached. **Verified at `ee30c3b` in a detached worktree:
  identical failure, exit 101.** What I verified is the cgroup rule and that
  the failure predates these commits; I did NOT verify it passes from a login
  terminal, only that `classify` would return `LocalTerminal` there. Do not
  "fix" apex-agentd for this without reproducing it outside a user service.
- `cargo clippy` does not exist on the L16; `tests/run-clippy.sh` (podman) is
  the only real clippy. It caught `items_after_test_module` that
  `cargo build --all-targets` did not.
