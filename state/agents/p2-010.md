## FOUND (ninth, and NOT this unit's files): apex-agentd's unit tests can hang FOREVER, and it is one defect with three symptoms

**This is the finding of round 12.** The predecessor reported three hung
threads as it died; the orchestrator independently hit the same hang days
earlier running `cargo test --workspace` on this machine and abandoned the run.
It is not a flake and it is not three tests. It is **one** defect, and the three
symptoms are evidence of its mechanism.

Not fixed from here. `pty.rs` came from the agent-runtime PR #20 and P1-020,
`egress.rs` from `task/p0-008-network-modes`, `grants.rs` from P1-020/§7 — none
of them is this unit's file, and all three are **byte-identical to the
integration tip `fbf06a4f`** (`git diff --quiet HEAD fbf06a4f --` those paths
is silent). Recorded here for whoever owns them rather than edited from this
worktree, which is the same rule this card applied to `system_grants.rs` and
the 33 grep-blind shell suites.

### What is actually wrong

`pty::spawn` forks, and **the child calls `unsetenv` at `pty.rs:211`** on the
`clear_env` path. `unsetenv` is not async-signal-safe: it takes glibc's
environment lock. `fork()` in a multi-threaded process clones only the calling
thread, so a lock another thread held at that instant is **held forever** in the
child. Caught in the act, with the stack of a real orphan:

```
TID 471015:
#0  __lll_lock_wait_private
#1  unsetenv
...
#11 start_thread
#12 __clone3
```

The concurrent lock-holder is in the same test binary: `grants.rs:512`'s
`unsafe { std::env::set_var("XDG_STATE_HOME", &path) }`. Its own comment reads

> `set_var` is process-global, so the tests that need it run one at a time.
> ... Safe: the lock above serialises every test that touches it.

and that is exactly the gap. The mutex serialises every test that touches **the
environment**. `pty::spawn`'s `fork()` does not touch the environment, so it is
not serialised against — and it is the one that matters.

The file's own comment says the right thing three lines above the bug —
"between fork and exec only async-signal-safe calls are legal" — and the author
avoided `clearenv` *because it allocates*. `unsetenv` was chosen as the safe
alternative. It is not: allocation is only half of the rule, and locking is the
other half.

### Why three different tests hang, and why that is the proof

The child never reaches `execvp`, so **`FD_CLOEXEC` never fires**, so the child
keeps a copy of every descriptor open in a process that will never exit. Read
from `/proc` on the predecessor's run, hung 4 h 03 m, and reproduced live in
this round's own battery:

```
threads of the test binary 470886:
  apex_agentd-2c7   futex_do_wait              (main, in join)
  egress::tests::   unix_stream_read_generic   (syscall 45, recvfrom)
  pty::tests::the   anon_pipe_read             (syscall 0, read)
  pty::tests::the   anon_pipe_read             (syscall 0, read)
the orphan 471015:
  pty::tests::the   futex_do_wait              (1 thread, never exec'd)
```

and the descriptors line up exactly:

| fd on the orphan 471015 | fd on the hung parent 470886 | which thread it hangs |
|---|---|---|
| 17 → `pipe:[572159]` (write) | 12 → `pipe:[572159]` (read) | `pty::tests::the…` #1 in `read_sync` |
| 16 → `pipe:[573752]` (write) | 14 → `pipe:[573752]` (read) | `pty::tests::the…` #2 in `read_sync` |
| 7,8 → `socket:[572757/572758]` | **not held** | `egress::tests::…` in `read_to_string` |

The egress row is the one that closes the argument. That socketpair is
`UnixStream::pair()` from an egress test whose `serve` worker has already
finished and dropped the server end — the parent does not hold those inodes any
more. The **only** remaining reference is the orphan's, so the test's
`read_to_string` never sees EOF. An unrelated test's fork deadlock is what
keeps another unrelated test's socket open.

So: one fork, one env lock, and every descriptor open at that instant becomes a
test that hangs forever. The count of hung threads varies with how many spawns
were in flight — this round's reproduction had one `pty` casualty, the
predecessor's had two.

### It has no deadline anywhere, and that is a second defect

Even with the env bug fixed, nothing here is bounded:

- `read_sync` (`pty.rs`) is a bare `libc::read` loop with **no timeout and no
  `poll`**. It returns on 3 bytes, EOF, or error — and EOF requires every
  duplicate of the write end to be closed, which is not a thing a caller can
  guarantee.
- the egress tests do `(&client).read_to_string(&mut answer).unwrap()` and then
  `worker.join().unwrap()` with **no `set_read_timeout` and no deadline**.
  `serve` itself sets a 30 s `HEAD_TIMEOUT` on the server side; the tests set
  nothing on the client side.

**A hang is not a pass, and a test that waits on a pipe or socket nobody will
close needs a deadline whatever the reason it is waiting.**

### Why it matters beyond this laptop

`pr-validation.yml`'s `Tests` step is a bare `cargo test --locked` under
`tests/in-login-session.sh` — **default test threads**, which is precisely the
condition that creates the race. A hang there is not a red build; it is a job
that burns its whole timeout. This one defect has already cost the
orchestrator's `cargo test --workspace` run, the predecessor's session, and a
600 s timeout in this round's battery.

### The fix, for whoever owns these files

1. **Primary, `pty.rs`:** build the complete `envp` array **before** the fork and
   `execve` with it. The child then calls no libc function that takes a lock —
   no `unsetenv`, no `putenv`. Note that `execvp` must go too: it reads `PATH`
   via `getenv`. `spawn` already resolves the program itself
   (`resolve_program`), so it can pass an absolute path to `execve` and the
   change is small.
2. **Secondary, `pty.rs`:** give `read_sync` a `poll()` deadline. A parent that
   cannot learn whether its child exec'd should fail the spawn, not block the
   process forever.
3. **Secondary, `egress.rs` tests:** `set_read_timeout` on the client end
   before `read_to_string`, and do not `join()` without one.
4. Measured rates and the control experiment are under
   `### Rate, measured three ways` below. Evidence capture:
   `/var/tmp/p2010-agentd-hang-evidence.txt`.

### Rate, measured three ways

`/var/tmp/p2010-hang-rate.sh`, log `/var/tmp/p2010-hang-rate.log`. Bin target
only (`-p apex-agentd --bin apex-agentd`), `timeout 120`, N=10 per arm, tree
verified clean between arms:

| arm | result |
|---|---|
| clean tree, **default** test threads (the CI shape) | **0 hung of 10** |
| clean tree, `--test-threads=1` (the control) | **0 hung of 10** |
| **B5 spliced**, default test threads | **1 hung of 10** |

Read these honestly. A low sampled rate is not a low risk, because **the cost
of one occurrence is unbounded** — the predecessor's instance had been hung for
**4 h 03 m** when it was found, and it was still holding the worktree when this
round started. Two spontaneous occurrences were observed today without trying:
the predecessor's run, and this round's own first battery attempt, which hung

The `--test-threads=1` arm is the **control, not a fix**. Serially there is no
second thread to be holding glibc's environment lock when `pty::spawn` forks,
so the race cannot occur — which is itself the confirmation that concurrency is
the trigger. It is also why round 12's battery ran serialised and completed all
fourteen rows with **zero TIMEOUT cells**, where the parallel attempt did not

**B5 is not causal**, even though it is 1-of-10 here and was where both

sentence to keep is "a race, perturbed by scheduling" — not "B5 hangs".

## FOUND (tenth): from 02:31 the live half could not pass from a login session, and the recipe that works is production placement

Measured this round, because the live column came back **6/2** where the card
records **8/0** and the difference had to be explained before any live row
could be trusted.

`systemd-run --user --scope` has to **migrate the calling process** out of its
current cgroup into the new scope under `user@<uid>.service/app.slice`. cgroup
v2 requires the writer to have write access to the **common ancestor** of
source and destination. Measured on this machine:

```
/sys/fs/cgroup/.../user-1000.slice/cgroup.procs                     root  0644
/sys/fs/cgroup/.../user-1000.slice/session-4.scope/cgroup.procs     root  0644
/sys/fs/cgroup/.../user@1000.service/app.slice/cgroup.procs         andre 0644
```

So from a **login session** (`…/user-1000.slice/session-4.scope`) the common
ancestor is `user-1000.slice`, which is root-owned, and the uid-1000 user
manager cannot do it:

```
systemd-run --user --scope -- cat /proc/self/cgroup     -> rc=1
journal: apex-p2010-probe2-790838.scope: Failed to add PIDs to scope's
         control group: Permission denied
         ... Failed with result 'resources'.
```

From a **systemd user service** (`…/user@1000.service/app.slice/<unit>`) the
common ancestor is `app.slice`, which the user owns, and it works:

```
inner scope -> /user.slice/user-1000.slice/user@1000.service/app.slice/...scope
rc=0
```

The discriminator is migration, not the bus: `systemd-run --user` as a
**service** (which starts a fresh process and migrates nothing) returns rc=0
from the login session at the same moment `--scope` returns rc=1.

Consequences, and none of them is a defect in `budget.rs`:

- **The live half must be run from a user service.** Driven that way it is
  **8 passed / 0 failed in 5.58 s**, reproducing the card's recorded 8/0 in
  5.18 s exactly. Driven from a login session it is 6/2, and the two failures
  are `a_budgeted_session_runs_in_its_own_scope_with_the_limits_really_written`
  ("wanted …/apex-agent-779051-1.scope, got
  /user.slice/user-1000.slice/session-4.scope") and
  `a_wall_clock_budget_really_ends_the_session`. Both are the same fact: no
  scope was ever created.
- The recipe is in `/var/tmp/p2010-live-rows-r12.sh` — wrap the cargo
  invocation in `systemd-run --user --unit=… --collect --wait --pipe`.
- **Production is unaffected.** The shipped `apex-agentd.service` is a systemd
  user unit and already runs under `user@1000.service/app.slice`, which is the
  placement that works.
- This is the **third** time this unit has been bitten by the login-session /
  user-service split — after `system_grants.rs`'s pre-existing failure and
  FOUND (seventh), which flip in opposite directions. Standing lesson:
  **every agentd measurement must state which cgroup produced it.**

## FOUND (fourth): a structural check that was a coin flip, and 96% blind

`producer | grep -q` under `set -o pipefail` **does not reliably report a
match.** `grep -q` exits at its first match and SIGPIPEs whatever is feeding
it, so the PIPELINE's status is 141 rather than grep's 0, and an `if` reads a
match as "no match". Both directions are wrong and **one of them is silent**:

- match means `bad` (a "this must not appear" check) → a SIGPIPE turns a real
  regression into a **pass**, and no mutation can ever be caught by that check
  again.
- match means `ok` → a SIGPIPE is a **spurious red** on an unchanged tree.

Found in `tests/test-apex-firmware.sh`, which had four. Measured under bash:
40 trials of `sed -E 's://.*$::' apexd-core/src/firmware.rs | grep -q
uefi_capsule` returned **0 twenty times and 141 twenty times**, and the suite's
own structural half was **21/0 three times and 20/1 nine times out of twelve
runs over a tree that never changed**. That is the landing lesson from
2026-09-08 in a new form: green in a worktree, red in CI — except here it is
red or green in the *same* worktree.

**Then the same pattern was measured against `tests/test-apex-storage.sh`,
which is this unit's own landed work, and the result is the finding.** Ten of
its checks were this shape and **seven were the silent direction**. A mutation
was spliced into `apex/src/storage.rs` making the CLI look up
`ID_SERIAL_SHORT` — the exact privacy regression the first of those checks
exists to catch, and the reason the read half never spawns `nvme list` — 35
lines into a 1,331-line file:

```
raw pipeline, 40 bash trials      -> 141 in 40 of 40
suite reports the mutation        ->   1 of 25 runs      ** 96% BLIND **
after the fix, same mutation      ->  25 of 25
```

The check guarding the disk serial was 96% blind to the one change it is for,
while printing `40 passed, 0 failed` — fifteen consecutive runs of it on a
clean tree are 40/0, so nothing about the suite's own output ever hinted at
this.

**Why the other three survived, and why that is not a defence.** They use
`awk '/^fn x/,/^}/'`, which emits one small function and finishes writing
before grep can exit. The same class of mutation inside `machine()` was caught
**20/20**. That is luck about a 64 KB pipe buffer, not a property anyone
maintains: a function that grows past it, or a match near its start, flips the
check to blind. The discriminator is **producer size and where in the stream
the match sits** — a whole-file `sed` with an early match is the reliably
broken shape, and it is the shape the two privacy checks had.

Fix, in both suites: two helpers, `absent`/`present`, that take **captured
text** rather than a pipeline — command substitution reads its producer to EOF,
so there is nobody left to signal. `has`/`hasnt` grep a plain file and were
never affected. Also fixed while there: one firmware assertion could
**vanish** — its outer guard was `… | grep -n Error | head -1 | grep -q .`,
and a non-zero pipeline skipped the whole `if`, recording neither a pass nor a
failure — and the `uefi_capsule` check had a **second, independent** bug, in
that it grepped the whole file for a string that legitimately appears eight
times in fixtures and in an assertion message, so it was a false alarm on
correct code whenever it was not a coin flip. It is now scoped to
`SECURE_BOOT_PLUGINS`' own declaration.

**Not fixed, deliberately: `grep -c '| grep -q' tests/*.sh` finds this shape
in 33 more suites under `set -o pipefail`** — 43 in `test-apex-dispatch.sh`,
35 in `test-secret-broker.sh`, 34 in `test-apex-input.sh`, 28 in
`test-apex-task.sh`, 26 in `test-shell-agent.sh`, 25 in `test-apex-ai.sh`, and
so on down. Those are other units' files and touching them from here would be
a merge minefield; the two fixed are the two this unit owns. **Whoever picks
this up: the direction is what decides urgency** — a `found → bad` check is
silently mutation-blind and is the one worth auditing first, and the whole-file
producers among them are the ones that are actually broken today rather than
merely fragile.

## FOUND (second): one unreadable directory turns six refusals into a permit

Measured in the fixture, with `.fixture/euid` 0 and the correct token, against
the CLI enumerator as the predecessor wrote it:

```
chmod 755 <disk sysfs dir>  -> 6 refusals, exit 3   (CarriesTheRunningSystem,
                                IsTheEsp, 4x CouldNotVerify)
chmod 100 <disk sysfs dir>  -> "would erase /dev/nvme0n1", exit 0   ** WRONG **
```

`chmod 100` is readable to nobody and still traversable, so `holders/` and
`dev` keep answering — only the *listing* of the disk's directory fails. The
draft's enumerator had `let Ok(entries) = read_dir(&base) else { continue }`
and `base.join(n).join("partition").exists()`, so all five partitions vanished
from the `Machine`. Then: no mount source is `/dev/nvme0n1` (measured: zero
times), nothing was left carrying `parent == nvme0n1`, and the ESP rule is
only ever asked of partitions. **Only the fixture gate stood between that and
`wipefs --all` on the disk carrying the running system.**

This is a **fifth** way "is the device mounted?" green-lights destroying this
machine, and the first that needs no unusual hardware at all — one directory
with the wrong mode. It is also `Path::exists()` being false on EACCES for the
sixteenth time in this module.

Fix: `machine()` returns `Result<Machine, String>` and **every** enumeration
error is the `Err` arm — a partially-enumerated machine is not a machine to
judge against. Unlike every other reading here it cannot be a `Reading`,
because the guard reasons about a device by looking at its *neighbours*: a
device that was never enumerated is not an unknown the guard can refuse on, it
is a fact the guard never learns. `erase()` reports it as a refusal (exit 3),
not an error — nothing was wrong with the request. `NotFound` and
`NotADirectory` are the only two definite "not a partition" answers, and
`read_dir`'s per-entry `Err` is no longer `.flatten()`ed away.

## FOUND (third): a partition of a loop device has no `loop/` directory

Measured with `sudo -n losetup --find --show --partscan` on a 64 MB GPT image
(on `/dev/loop1`, chosen by `--find`, backing file asserted first — `loop0`
was never touched):

```
/sys/block/loop1/loop1p1/partition  -> exists
/sys/block/loop1/loop1p1/loop/      -> DOES NOT EXIST
```

So read on its own a loop partition answers `Known(None)`, "not an attached
loop device", and the `LoopDeviceInUse` rule lets it through — while `wipefs`
on it writes through the parent into the backing file exactly as it would on
the whole device. `would_destroy` walks downward only, so nothing else relates
a partition back up to its disk: the loop rule was one-directional where the
mount rule is explicitly both, which is the card's own sentence.

own read is `Known(None)` — including the parent's `Unavailable`, because if
nobody could tell whether the disk is an attached loop device then nobody can
tell whether this partition is on one. A partition's own reading, if it ever
has one, still wins.

## Measured, fifth pass (P2-011 surfaces, before writing a line of it)

Three things the third pass had not measured decide whether budgets work at
all. All three are now measured, and **two of them changed the design**.

### The daemon is a systemd USER unit, and there are two of them

```
systemctl --user show apex-agentd.service -p ControlGroup -p Delegate
  ControlGroup=/user.slice/user-1000.slice/user@1000.service/app.slice/apex-agentd.service
  Delegate=no
pgrep apex-agentd -> 1406 (uid 0) and 1472 (uid 1000)
  1406: /user.slice/user-0.slice/user@0.service/app.slice/apex-agentd.service
```

So `--user` from a child targets a real user manager for both, and root's
`/run/user/0/bus` exists (`ls` as andre is EACCES, error 13 not 2 — present,
not absent). `user@0.service/cgroup.controllers` is `cpu memory pids`, the
same as 1000's.

### The child CAN reach the bus — but not for the reason it looks like

`pty::spawn` is called with `clear_env=true`, so the child's whole environment
is `sandbox::resolved_env(&spec)`, and **`ENV_BASE` contains neither
`XDG_RUNTIME_DIR` nor `DBUS_SESSION_BUS_ADDRESS`** (it is TERM, COLORTERM, the
LC_*/LANG set, TZ, TERMINFO, NO_COLOR — nothing else). Reproduced exactly:

```
env -i TERM=… PATH=… systemd-run --user --scope -q -p MemoryMax=64M -- true
  -> rc=1  "Failed to connect to user scope bus via local transport:
            $DBUS_SESSION_BUS_ADDRESS and $XDG_RUNTIME_DIR not defined"
+ XDG_RUNTIME_DIR=/run/user/1000                        -> rc=0
+ DBUS_SESSION_BUS_ADDRESS=unix:path=/run/user/1000/bus -> rc=0   (either alone)
```

What saves it is `session.rs:378`, which already pushes `XDG_RUNTIME_DIR` =
`real_target(&spec.runtime_dir)` into `spec.env_set` for an unrelated reason
(so a session can find its control socket). `env_set` is inside
`resolved_env`, so the wrapper inherits it. **No env injection is needed and
none should be added** — the alternative was putting a bus variable into every
agent's environment, which for an unconfined session is a new leak, and this
feature must not pay for itself that way.

### `--scope` execs in place, so no pid bookkeeping changes

```
systemd-run --user --scope -q -- sleep 4 &   ->  PID 89655 ppid 89653 (the shell)
                                                 pgid 89653, no systemd-run alive
```

One process, not two: systemd-run creates the scope over the bus and then
`execve`s the command in its own process. So the pid `pty::spawn` records is
still the pid of the real program chain, `peer.rs`'s parent-chain session
resolution is unchanged, and `apex agent kill`'s killpg still names the right
group. The wrapper is a pure exec-chain prefix and is invisible to everything
that counts processes. This is the property that makes a one-line hook safe.

`RuntimeMaxSec=5 -- sleep 30` reproduces the card: **rc=143 at exactly 5s.**

### FOUND (fifth): reading `subtree_control` reports `cpu` as unenforceable on a machine where it is enforceable

The third pass read `user@1000.service`, where `cgroup.controllers` and
`cgroup.subtree_control` happened to be the same string. One level down they
are not, and the difference is **transient**:

```
app.slice/cgroup.controllers      -> cpu memory pids
app.slice/cgroup.subtree_control  -> memory pids          ** no cpu **

then, once ONE child scope asked for CPUQuota:
app.slice/cgroup.subtree_control  -> cpu memory pids       ** cpu appeared **
```

systemd enables a controller in `subtree_control` **on demand**, when a child
unit first needs it. So a discovery routine that keys availability on
`subtree_control` answers "cpu budgets are not enforceable here" on a machine
where they are — and answers it differently depending on what else happens to
be running. Measured against the real thing, inside a scope that asked for all
four:

```
scope cgroup.controllers -> cpu memory pids
  cpu.max     50000 100000     (CPUQuota=50%, enforced)
  memory.max  67108864         (MemoryMax=64M, enforced)
  pids.max    64               (TasksMax=64, enforced)
  io.max      No such file or directory
```

So the file to read is the **delegation boundary's `cgroup.controllers`**, and
`subtree_control` must not be consulted as an availability signal at all. Same
family as everything else this unit found: a reading that is not the fact it
looks like. Here it fails in the direction of falsely reporting *absence* —
which under the "never a budget of zero" rule would have silently dropped a
budget the machine could have honoured.

`io` really is absent, and that part holds up: it is in the root cgroup's
`cgroup.controllers` (`cpuset cpu io memory hugetlb pids rdma misc dmem`) but
**not in the root's `subtree_control`**, so it is never delegated to anyone,
and `find /sys/fs/cgroup/user.slice -maxdepth 4 -name io.max` finds **nothing**.
`io` is a `Reading::Unavailable` carrying that reason.

### FOUND (sixth): a transient scope's NAME can widen a request's privilege

`origin::classify` decides §7 origin by substring, over the peer's cgroup path:

```
cgroup.contains("/session-") && cgroup.contains(".scope") -> LocalTerminal / ApexShell
cgroup.contains("/user@")    && cgroup.contains(".service") -> ScheduledJob
```

A transient user scope is placed under the user manager regardless of who asks
for it — measured from a login session at `/user.slice/user-1000.slice/session-4.scope`:

```
systemd-run --user --scope --unit=apex-budget-probe-1 -- cat /proc/self/cgroup
  -> /user.slice/user-1000.slice/user@1000.service/app.slice/apex-budget-probe-1.scope
```

That path still contains `/user@` and `.service` (from the `user@1000.service`
ancestor), so a wrapped agent still classifies **ScheduledJob**, exactly as it
does today inside `apex-agentd.service`. No widening — **as long as the unit
name cannot supply the other rule's substring.** It can:

```
systemd-run --user --scope --unit=session-99-probe -- cat /proc/self/cgroup
  -> …/app.slice/session-99-probe.scope        ** matches "/session-" + ".scope" **
                                               ** classifies LocalTerminal **
```

The scope name is the last path segment, so a name *beginning* `session-`
puts `/session-` into the path and promotes every request from inside that
agent to the origin §7 reserves root and break-glass for. It is not reachable
today (the name is built from a fixed prefix and the daemon's own integer
session id, neither caller-supplied), but it is one refactor — "name the scope
after the session" — away from being reachable, and nothing in `origin.rs`
would notice. So the name is validated at construction, and a test asserts the
produced cgroup path still classifies `ScheduledJob`.

### Consequences for the design

- No `Reading` exists in `apex-agent-core` (grepped: only `*Unavailable`
  error variants in `policy.rs`/`client.rs`), and **no limits/resources stanza
  exists in `adapter.rs` or `config.rs`** — so `budget.rs` declares its own
  two-state reading and owns its own config surface. `apexd-core` is
  deliberately NOT added as a dependency: the daemon must not gain a
  dependency on the CLI's core crate for a 20-line enum, and P1-020's tip
  makes `Cargo.toml` a conflict surface.
- Default is **no budget and therefore no wrapper at all**, so an unbudgeted
  session's argv is byte-identical to today's. That is what keeps the three
  existing integration tests (`hook_bridge.rs`, `request_origin.rs`,
  `system_grants.rs`, which drive a real daemon over a socket) unchanged, and
  it is why `RuntimeMaxSec` defaults to none — a wall-clock kill on a coding
  agent is a regression, not a feature.

### P2-015: fwupd's exit status flips meaning on `--json`

- `fwupdmgr get-updates --json` with nothing to update → **exit 0**, body
  `{"Devices": []}`, empty stderr.
- `fwupdmgr get-updates` **without** `--json`, same machine, same moment →
  **exit 2**, a full device list on stdout and `No updates available` on
  stderr. So the *success* case is a non-zero exit in one form and zero in the
  other. A caller that keeps the exit check but drops `--json` reads a healthy
  machine as a broken firmware subsystem. Same family as the three smartctl and
  blkid traps, and the one direction none of them covered: **exit non-zero
  meaning "nothing to do".** Use `--json` and read `Devices`, not the status.
- `fwupdmgr get-devices --json` → exit 0, 37 KB, **28 devices**, as `andre`,
  no session bus, no prompt.
- **Most of those 28 are not hardware.** `KEK CA` (twice), `UEFI CA`,
  `Windows UEFI CA`, `Option ROM UEFI CA`, `ThinkPad Product CA`, `SBAT` are
  Secure Boot certificate entries, and five separate rows are all named
  `UEFI Device Firmware`. A readout that prints every row is unreadable and has
  duplicate names. Filter on the `Flags` array (`updatable` is present on real
  ones) and expect to disambiguate repeated `Name`s by `DeviceId`.
- **`Name` and `Version` are both optional.** `linux_display` and
  `GPIO controller` rows have no `Name` and no `Version` at all; `Version` is
  sometimes a raw hex string (`0x0006`). A reader that indexes `Name`
  unconditionally breaks on this machine's own output.

### The ESP name rule was wrong, and the disk says so

`ID_PART_ENTRY_TYPE=c12a7328-f81f-11d2-ba4b-00a0c93ec93b` is on `nvme0n1p1`,
and **it is the only partition on the disk with an `ID_PART_ENTRY_NAME` at
all**. p2-p5 carry a type GUID and no name. So:

- Keying the ESP rule on the name `EFI System Partition` (the draft's rule)
  misses any ESP an installer left unnamed — which, on the evidence of this
  disk, is the normal case for a partition here.
- Worse, treating a missing name as unverifiable refuses **four of five**
  ordinary partitions for a reason that is not true, which is exactly the
  "safe refusal that teaches the user the guard is noise" failure.
- Hence `Reading<PartitionEntry>` with `Option` fields inside: the RECORD
  being absent is a check that did not happen; udev writing no NAME is a
  fact. Two different unknowns, and collapsing them breaks one direction or
  the other. `is_esp` answers `Yes` on the type GUID or MBR `0xef` first,
  `Yes` on the name second, `No` only when a partition type was actually
  read, and `Unsure` when there is no type at all — because a `vfat`
  partition with no readable type is the exact shape of an ESP under a table
  the parser failed on.

### `ops::require_root` calls an unreadable `/proc/self/status` "must run as root"

into the root refusal — its own test says so deliberately ("must fail
CLOSED"). Safe, but it tells the user to run `sudo`, which will not help if
the problem is that `/proc/self/status` was unreadable. `storage::guard`
therefore takes `&Reading<u32>` and reports that case as
`CouldNotVerify { what: "which user is running this" }`. **`ops.rs` was not
changed** — this is the storage guard being stricter about its own inputs,
not a fix to `apex update`.

```
                   + Mounted(/sysroot/ostree/deploy/default/var)

/dev/nvme0n1p5  -> CarriesTheRunningSystem + Mounted
/dev/nvme0n1p1  -> IsTheEsp on the type GUID, mounted nowhere
/dev/nvme0n1p3  -> Unconfirmed only  (correct: unmounted, non-ESP)
/dev/loop0      -> Unconfirmed only  ** WRONG **
```

**`/dev/loop0` is attached to `/lib/extensions/apex-user.raw`** — the live,
merged system extension carrying 219 packages including Steam — and:

- `grep loop /proc/self/mountinfo` -> **0**
- `sudo grep loop /proc/1/mountinfo` -> **0**
- `/sys/block/loop0/holders` -> **empty**
- `losetup -a` -> `/dev/loop0: [0037]:9076916 (/lib/extensions/apex-user.raw)`,
  `autoclear=1`

So an attached, in-use loop device appears in **no** mount table anywhere and
has no holders. With the correct token the guard granted a `Permit`, and
`wipefs --all /dev/loop0` writes *through* the loop device into
`/lib/extensions/apex-user.raw` and destroys the extension.

This is a **fourth** independent way "is the device mounted?" green-lights
destroying live state, alongside the composefs `/`, the never-mounted whole
disk, and the unmounted ESP — and it is the one that lands on the exact
device class the destructive test is supposed to be safe on. The card already
warned that a *test* hardcoding loop0 destroys the extension; the finding is
that the *guard itself* permitted it.

Fix: `BlockDevice` gains `loop_backing: Reading<Option<String>>` from
`/sys/block/<dev>/loop/backing_file` (`Known(None)` = not an attached loop
device, which for a device with no `loop/` dir is a definite answer;
`Unavailable` = the node existed and could not be read, which refuses). An
attached loop device refuses with `LoopDeviceInUse` **unless** the caller
asserts which file it backs and is right — `apex storage erase
--expect-backing-file <path>`, wrong path being its own refusal
`BackingFileMismatch`. That promotes the assertion the card demanded of the
*test* into the product, where it protects everyone and not just the suite.
Paths are canonicalized at the CLI edge on both sides, so `guard` stays a
pure string comparison.

### P2-014 destructive half: two facts that decide the design

- **`/dev/loop0` is already in use on the L16**, backing
  `/lib/extensions/apex-user.raw` — a live, merged system extension. A test
  that hardcodes a loop device number, or takes one from argv, destroys a
  mounted extension. `losetup --find --show` plus an assertion that
  `/sys/block/<dev>/loop/backing_file` is the file the test just created is not
  belt-and-braces here; it is the only thing standing between the suite and
  live machine state. `sudo -n losetup` works (util-linux 2.41.5).
- **`wipefs --backup[=<dir>]` defaults to `$HOME`, and under `sudo` `$HOME` is
  `/root`.** So the signature backup a user is told to keep lands in root's home
  where they will not look, not in `/var/home/andre`. Recovery guidance has to
  name the actual path, and the destructive path should pass an explicit
  `--backup=<dir>` rather than inherit it.
- Not `udisksctl` for any of this — it goes through polkit.

### "Is the device mounted?" green-lights destroying this machine, three ways

Measured from `/proc/self/mountinfo`, `/sys/block` and `/run/udev/data` on the
L16. The obvious guard — refuse if the device is a mount source, and protect
`/`, `/var`, `/boot` — **fails on all three of these independently**:

1. **`/`'s source is `overlay`, fstype `composefs`.** It is not a block device
   and never will be on a bootc machine. The device that actually carries this
   operating system, `/dev/nvme0n1p5` (btrfs, label `apex-root`), is the source
   of `/etc`, `/sysroot`, `/boot`, `/var` and
   `/sysroot/ostree/deploy/default/var` — and of `/` **never**. A
   critical-target list that contains `/` protects nothing at all here. This is
   the same bootc trap as the free-space one wearing a knife.
2. **The whole disk is a mount source zero times.** `grep ' /dev/nvme0n1 '
   /proc/self/mountinfo` → 0. Only `p5` appears. So `wipefs /dev/nvme0n1` —
   which takes the partition table and therefore everything, including the
   running OS — passes an "is this device mounted?" test cleanly. The guard has
   to relate a partition to its parent disk **in both directions**: refuse the
   target if it is a critical source, if it is the parent disk of one, or if a
   critical source is a partition of it. Parent is `/sys/block/<disk>/<part>`,
   so the relation is available without parsing names.
3. **The EFI System Partition is mounted nowhere.** `nvme0n1p1` is vfat,
   partname `EFI System Partition`, and this machine has **0** vfat mounts —
   bootc mounts the ESP only when it needs it. Wiping it leaves an unbootable
   machine and passes a mount check. Its type is legible unprivileged from
   `/run/udev/data/b<maj>:<min>` (`ID_PART_ENTRY_NAME`, `ID_FS_TYPE`), the same
   surface the read half already uses for encryption.

Also measured: the disk holds two other installations —
`p3` btrfs `fl_fedora`, `p4` ext4 `apex-newboot`, `p2` ext4 — so "unmounted"
here means "someone else's operating system", not "spare". And **every
`holders` directory on this machine is empty** (no LUKS anywhere), so the
holder rule cannot be exercised live and must be fixtured. Which is the
argument for the refusal logic being pure and fixture-driven in the first
place.

**The inversion that matters most:** for the read half, a read it could not
perform is a grey row. For the destructive half, **a check it could not perform
must refuse**. An unreadable `holders` directory is not an absence of holders;
an unreadable `mountinfo` is not an absence of mounts. Same sentence this whole
unit keeps re-learning, except here getting it backwards destroys data instead
of mislabelling a row. So the guard takes `Reading`s, and
`Refusal::CouldNotVerify` is a refusal and not a pass.
