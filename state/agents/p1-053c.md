## FOUND (round 6)

- **`apex install` SHIPPED A JAVA 21 THAT CANNOT START A JVM, and it is the
  known `install_etc` defect biting a second package.** Every `:core:test` on
  this machine dies before a single test runs with `java.lang.InternalError:
  Error loading java.security file`. Measured, not guessed:
  `/usr/lib/jvm/java-21-openjdk/conf` is a relative symlink to
  `../../../../etc/java/java-21-openjdk/java-21-openjdk/conf` and **that
  target does not exist** — `/etc/java/` holds only `java-27-openjdk` and
  `security`. `rpm -qf` on the symlink answers *"not owned by any package"*,
  so it came from the `apex-user.raw` extension (755 MB, mtime 12 Sep 17:34,
  the same minute as the JDK tree) and not from the image. The image's own
  java-27 works because its `/etc/java/java-27-openjdk` is present in BOTH
  `/etc` and `/usr/etc`.
  This is the `install_etc` failure CLAUDE.md records from katana in its
  other direction: there the removal pass DELETED image-owned `/etc` files;
  here an extension's `/etc` half was never installed at all, leaving a
  package whose `/usr` half is complete and non-functional. A `/usr` tree
  that symlinks into `/etc` is broken by any engine that ships one without
  the other. **Worth a roadmap item for whoever owns `apex-pkg`** — I did not
  file one, and I changed nothing on the live machine.
- **Worked around entirely inside my own scratch; the live system was not
  touched.** `dnf download java-21-openjdk-{headless,devel}` +
  `rpm2cpio | cpio -idm` into
  `/var/tmp/apex-work/scratch-p1-053c/jdk21root`. The rpm is
  `21.0.12.1.1-1.0.fc43`, which is **byte-for-byte the same build** as the
  extension's (`IMPLEMENTOR_VERSION="(Red_Hat-21.0.12.1.1-1)"` in its
  `release`), so this is the missing half restored rather than a different
  JDK substituted. Because the rpm's `conf` symlink is relative, extracting
  the whole rpm under one root makes it resolve inside that root — the JDK is
  self-contained and needs no `/etc`. Pass it with
  `-Porg.gradle.java.installations.paths=...` (see NEXT for the exact line).
- **CI is NOT affected and needs no change.** `.github/workflows/
  pr-validation.yml:3077-3080` uses `actions/setup-java@v4` with
  `distribution: temurin, java-version: '21'`, which never touches Fedora's
  `/etc/java`. This defect is local to the L16, which is why it has never
  shown up in a gate.
- **A background "exit code 0" notification can be `tee`'s status, not the

## FOUND (round 4, all measured on this machine)

- **The daemon has no `WAYLAND_DISPLAY` and the user service manager does.**
  Measured on the live `apex-agentd` (pid 1479): its `/proc/<pid>/environ`
  holds `XDG_RUNTIME_DIR` and `DBUS_SESSION_BUS_ADDRESS` and **no**
  `WAYLAND_DISPLAY`, while `systemctl --user show-environment` reports
  `WAYLAND_DISPLAY=wayland-1`. `apex-agentd.service` deliberately does not
  depend on `graphical-session.target` ("useful in a bare TTY"), so it starts
  before the compositor imports the variable and never gets it. A clipboard
  read that just runs `wl-paste` therefore fails on the daemon with
  "Failed to connect to a Wayland server ... falling back to wayland-0" —
  verified by running wl-paste under exactly the daemon's environment. The
  module must discover the socket itself.
- **This machine has TWO wayland sockets and one of them is dead.**
  `/run/user/1000/wayland-1` (live) and `/run/user/1000/wayland-2` (stale,
  12 Sep 18:36). `wl-paste` against the stale one exits 1 with "Connection
  refused" **promptly** — it does not hang — so probing candidates in order is
  safe. `apex/src/dispatch.rs`'s `session_script` picks the first glob match
  and would have taken a stale socket had the numbers been the other way
  round; not this unit's file, recorded for whoever owns it.
- **`apex-remoted` needs no change for this verb, checked rather than
  assumed.** `proxy::takes_over_the_channel` is `cmd == "attach" || cmd ==
  "receive"`, so `clipboard` round-trips through `serve.rs`'s `control()` like
  `list` does. The Frame::Control reply goes out at `serve.rs:353` as
  `send(&sealer, Frame::Control(reply))?` — a `?` in the connection loop, so
  the doc comment's claim that an oversize reply drops the whole device
  connection is true as written.
- **`CONTROL_TIMEOUT` is 300 seconds** (`proxy.rs:50`), and `control()` is
  called inline in the frame loop. So an unbounded `wl-paste` — which waits on
  the *source application* to serve the selection, and a frozen app never does
  — would freeze the phone's entire connection, terminal included, for five
  minutes. The bounded wait in `clipboard.rs` is load-bearing, not a nicety.
- **Only ONE exhaustive match over `Request` exists in the workspace**
  (`apex-agentd/src/main.rs:662`), and none over `Response`. `cargo check
  --workspace` with the new variants fails in exactly that one place, so no
  file outside this unit's scope needs an arm.
