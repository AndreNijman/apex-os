## The wire vocabulary, read off `protocol.rs` rather than remembered

28 verbs: hello, run, list, info, attach, resize, inject, input, signal, event,

**There is no file-transfer verb and no clipboard verb.** `apex send
--clipboard` (`apexd/apex/src/dispatch.rs:548`) is real, and it is ssh +
`wl-paste`/`wl-copy` between two Linux hosts in the §20 host registry. An
Android phone is not an ssh destination running `wl-copy`, so that mechanism is
unreachable from here — it is a different feature wearing a similar name.

## FINDING: `inject` is reachable from a paired phone and is not origin-gated

`Request::Inject { id, source }` reads `source` — **an absolute path on the
host** — with the daemon's own access, outside every sandbox. That is the point
of the verb for a human at the keyboard: `~/Pictures/Screenshots` is masked by
the tmpfs over `$HOME` and the daemon can see it.

`apexd/apex-agentd/src/inject.rs:48` refuses exactly one caller: one that
resolves to a managed session. It never consults the origin.
`apex-remoted`'s `control()` (`serve.rs:473`) is a **denylist of one verb**
(`attach`). `apex-remoted` is not a managed session.

So a paired device can send `{"cmd":"inject","id":N,"source":"/home/<user>/.ssh/id_ed25519"}`
and the daemon will read that file, copy it into the session's inbox where the
agent can read it, and type the path into the agent's terminal. The module's own
threat model names this exact attack for a *session* ("`apex agent send 4
~/.ssh/id_ed25519` ... would be a complete escape") and gates it there; the
remote caller was not considered, because P1-035 landed before there was a
phone.

Nothing in `android/` builds an `inject` request today, so this is a hole in the
daemon rather than a defect in the app — but P1-059's fourth criterion is about
not reaching past what was explicitly granted, and this is that criterion
inverted.

## Criterion 2 needs a transport that does not exist, and the arithmetic says so

"Photo/screenshot/file upload lands in an explicit permitted project/temp path
and inserts a safe path into the agent session" is exactly what
`apex_agent_core::inject` does — `safe_name`, `destination`, `payload`,
`keystrokes`, the INBOX under the session scratch, nothing submitted. What is
missing is getting the bytes from the phone to the machine.

`apex-remote-core`'s `MAX_PAYLOAD` is 65514 bytes (`wire.rs:67`). A control
frame carries one line of agentd JSON; base64 costs 4/3; so a single-frame
handoff verb tops out near 48 KB of file. A screenshot is 100 KB to 2 MB. A
verb that carries a log tail and refuses the thing the criterion is named after
is the same mistake as building a request nothing can parse.

Doing it properly means chunked transfer — begin/chunk/end, staging state and a
size cap in the daemon, a timeout, cleanup of an abandoned upload, and the
origin gate above applied to the destination. That is a protocol unit, not an
Android round, and it is recorded as one.
