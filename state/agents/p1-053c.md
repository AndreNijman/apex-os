## FINDING: `inject` is reachable from a paired phone and is not origin-gated

`Request::Inject { id, source }` reads `source` — **an absolute path on the
host** — with the daemon's own access, outside every sandbox. That is the point
of the verb for a human at the keyboard: `~/Pictures/Screenshots` is masked by
the tmpfs over `$HOME` and the daemon can see it.

`apexd/apex-agentd/src/inject.rs:48` refuses exactly one caller: one that
resolves to a managed session. It never consults the origin.
`apex-remoted`'s `control()` (`serve.rs:473`) is a **denylist of one verb**
(`attach`). `apex-remoted` is not a managed session.

So a paired device can send `{"cmd":"inject","id":N,"source":"/home/<user>/.ssh/id_ed25519"}`
and the daemon will read that file, copy it into the session's inbox where the
agent can read it, and type the path into the agent's terminal. The module's own
threat model names this exact attack for a *session* ("`apex agent send 4
~/.ssh/id_ed25519` ... would be a complete escape") and gates it there; the
remote caller was not considered, because P1-035 landed before there was a
phone.

Nothing in `android/` builds an `inject` request today, so this is a hole in the
daemon rather than a defect in the app — but P1-059's fourth criterion is about
not reaching past what was explicitly granted, and this is that criterion
inverted.

## Criterion 2 needs a transport that does not exist, and the arithmetic says so

"Photo/screenshot/file upload lands in an explicit permitted project/temp path
and inserts a safe path into the agent session" is exactly what
`apex_agent_core::inject` does — `safe_name`, `destination`, `payload`,
`keystrokes`, the INBOX under the session scratch, nothing submitted. What is
missing is getting the bytes from the phone to the machine.

`apex-remote-core`'s `MAX_PAYLOAD` is 65514 bytes (`wire.rs:67`). A control
frame carries one line of agentd JSON; base64 costs 4/3; so a single-frame
handoff verb tops out near 48 KB of file. A screenshot is 100 KB to 2 MB. A
verb that carries a log tail and refuses the thing the criterion is named after
is the same mistake as building a request nothing can parse.

Doing it properly means chunked transfer — begin/chunk/end, staging state and a
size cap in the daemon, a timeout, cleanup of an abandoned upload, and the
origin gate above applied to the destination. That is a protocol unit, not an
Android round, and it is recorded as one.

## FOUND

- **THE ARITHMETIC WAS ABOUT THE WRONG FRAME TYPE, and the transport already
  chunks.** Round 1 refused P1-059's criterion 2 with `MAX_PAYLOAD = 65514`,
  base64's 4/3, and "a single-frame handoff tops out near 48 KB". Every number
  is right and the conclusion does not follow, because it measures a
  `Frame::Control`. `apex-remote-core/src/wire.rs` has four more variants, and
  `Frame::Open { channel, request }` / `Frame::Data { channel, bytes }` /
  `Frame::Close { channel, reason }` **is** begin/chunk/end. `wire.rs:66` says
  so in its own words: "A `Data` frame is split by the writer and reassembled
  by the reader as an ordinary byte stream, so the limit is invisible above
  this layer" — and `Frame::data_frames` is `bytes.chunks(MAX_PAYLOAD)`, in the
  tree, carrying every PTY byte the phone has ever received. So the missing
  piece was never a chunking protocol. It is ONE daemon verb that turns a
  channel into a byte sink the way `attach` turns one into a PTY.
- **"That is a protocol unit ... and it is recorded as one" is not true.** Both
  items' evidence says the chunked-transfer follow-up was recorded. It is in no
  `ROADMAP/state/queue.json` unit, no `roadmap.yaml` item and no
  `ROADMAP/design/` note — grepped, not assumed. A refusal that points at a
  unit which does not exist is a refusal with nowhere to go.
- **The three seams a streamed verb needs are all clean, checked before
  committing to build it.** (1) `apex-agentd/src/main.rs:618` already has an
  explicit "this verb does not return to the loop" branch for `Attach`, so a
  second takeover verb slots in beside it rather than being threaded through
  the loop. (2) `apex-agentd/src/inject.rs`'s steps 3-6 — session lock,
  sequence, `destination`, `payload`, the write, `keystrokes`, the journal —
  never touch `source`; only step 2 does, so a streamed upload calls the same
  tail rather than a copy of it. (3) `Mux` on the Android side ALREADY takes
  `accepted: (ByteArray) -> Boolean` as a constructor parameter, so a second
  takeover reply needs no new plumbing there.
- **No staging file and no abandoned-upload cleanup are needed, and that is a
  consequence of the cap rather than a shortcut.** `inject` already reads a
  whole file into one `Vec<u8>` bounded by `MAX_BYTES` (32 MiB), so a streamed
  upload bounded the same way is buffered the same way and an upload that dies
  half-way leaves nothing on disk. The remaining guards are the cap — checked
  against the DECLARED length before the takeover reply, so an oversize upload
  is refused before 32 MB crosses the wire, and again with `take()` so a client
  that lies cannot overrun — and a read timeout.
- **P1-060's "no emulator" was "not obtained", not "impossible".** There IS an
  Android SDK on this machine at `/var/tmp/android-sdk` (cmdline-tools,
  platform-tools, build-tools 35+36, platforms/android-36, installed by
  `setup.sh` on 2026-09-12 — that is how round 1 built without a
  `local.properties`). `/dev/kvm` exists and is `crw-rw-rw-`, `/var` has 754 GB
  free, 20 GB RAM available, and `dl.google.com` answers. So `sdkmanager
  --install emulator "system-images;android-36;aosp_atd;x86_64"` is reachable
  and round 1's flat "there is no emulator" was a claim about what was
  installed, read as a claim about what was possible.
