## The protocol, as read out of the crate (round 1)

- Socket opens with ONE plaintext byte: `P` (0x50) pairing or `S` (0x53)
  session. Everything after it is `[u32 big-endian length][Noise message]`,
  length <= 65535, refused before allocating (`apex-remoted/src/net.rs`).
- Pairing is `Noise_NK_25519_ChaChaPoly_BLAKE2s`; session is `Noise_IK_…`.
  Prologue for both is the literal bytes `apex-remote/1`.
- NK msg1 payload = `PairingRequest` JSON (`key`, `name`, `token`,
  `user_verification`). NK msg2 payload = `{"ok":true,"device":…,"machine":…}`
  or `{"ok":false,"error":…}` — a refusal comes back inside the finished
  handshake, so the client must always read msg2.
- IK msg1 payload is empty; IK msg2 payload is the machine name as raw bytes.
  An unpaired or revoked key gets **no msg2 at all** — the connection dies.
  EOF there means "not paired or revoked", and the two are not distinguishable
  by design.
- Frames: `[u8 tag][u32 BE channel][payload]`, MAX_PAYLOAD 65514. Tags
  0 Control, 1 Open, 2 Data, 3 Close, 4 Ping, 5 Pong. Control/Ping/Pong only on
  channel 0; Open/Data/Close never on channel 0. Unknown tag is an error, not a
  skip. A Control payload containing `\n` is refused in both directions.
- base64url **unpadded** everywhere; `key=` with padding must be REJECTED.
- device id = first 16 characters of the key's base64url text.
- rendezvous id = b64url(SHA-256(`apex-remote/rendezvous/v1` || desktop_pub)[..16]);
  relay URL is `{prefix}/r/{id}?role=guest`, WebSocket binary payloads carrying
  the same length-prefixed byte stream.

### Three defects round 4 found, so they are not re-found

* **There is no `worktrees` verb**, and round 3's `Agentd.worktrees()` /
  `readWorktrees` / `WorktreeStatus` built a request `apex-agent-core`'s
  `Request` cannot deserialise. Removed; the test that exercised them is kept,
  inverted. **P1-056 must start from this**: the socket has Hello, Run, List,
  Info, Attach, Resize, Signal, Event, Logs, Remove, Prune and the privilege
  and secret verbs, and nothing else. Browsing projects and worktrees from a
  phone needs a verb somebody adds to the daemon first.
* **`PtyAttachment` silently dropped the terminal's answers to the opening
  frames of a replay.** The listener read the field that means "attached",
  which the attaching thread sets *after* `openChannel` returns — and
  `apex-agentd` starts replaying the instant it answers. So a TUI's `ESC[6n`
  and `ESC[c` were computed and thrown away, and the TUI waited for ever: a
  remote terminal that hangs with nothing in any log. Fixed with a second
  field set before the pump starts. Its regression test FORCES the ordering
  rather than hoping for it — twenty-five attachments went on passing against
  the reverted defect on a quiet box.
* **Six of the sixteen ANSI colours were the same hex as their normal twin.**
  Catppuccin's own terminal mapping, deliberate there, and it meant the app
  rendered ten distinct colours where the criterion says sixteen — `git`'s
  `31` and `91` would have looked identical. Found because deleting the
  bold-brightening rule changed nothing any test could see.

### The hostile half of P1-055's last criterion

A reconnect test that passes because the connection was politely closed has
proved nothing about the case that matters. A phone does not get a FIN: it goes
into a lift, and because `soTimeout` is deliberately zero after the handshake
the socket sits in `read` for hours while every layer above sees exactly what
an idle terminal looks like.

`FrameChannel.lastFrameNanos` is what tells them apart — the desktop pings
every fifteen seconds, and the pings are consumed inside the channel, so the
question is "has any FRAME arrived" and it can only be answered one layer below
the multiplexer. The watchdog closes after three missed pings. It answers
`null` for a transport that cannot report liveness and the attachment emits
`WatchdogUnavailable` rather than arming over nothing, because a watchdog
watching nothing is the exact shape of the failure it exists to prevent.

`FakeMachine` grew a frame size, an inter-frame delay, a silence mode and a
machine-side keepalive. Writing that keepalive found a bug in the test itself:
it pinged from the CLIENT, which proves nothing about the far end, and watched
the attachment reconnect three times while claiming to prove the opposite.

### For whoever takes P1-056 / P1-057

* `MachineLink` is the control connection and is deliberately NOT the PTY's —
  `apex-remoted` answers a control frame from a single-threaded loop that
  blocks while `apex-agentd` thinks, for up to five minutes on a privilege
  request. It retries a question and never an instruction.
* The device key is unwrapped ONCE per session and held in memory by the view
  model, keyed by `deviceId`, cleared on `lock()` and `onCleared()`. Do not
  move that into a `connect` lambda: `PtyAttachment` calls its lambda on every
  backoff retry, and the result would be a biometric prompt per reconnect.
* `:app` still never opens a file. `tools/no-second-write-path.sh` enforces it
  and the accessory row rides on `MachineStore` for that reason.
* The CI test-count floors were moved (87 -> 295, 6 -> 10). They are floors
  only while somebody moves them.
* Toolchain is unchanged from round 1 and is still not in git.
