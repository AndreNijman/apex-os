## FOUND
- **The documented REST paths are confirmed from a pinned source**, not from
  memory: `cloudflare/api-schemas` `openapi.json` at commit `d5003a19`
  (info.version 4.0.0, 2026-09-11), cross-checked against the rendered
  reference pages. Recorded in the mod.rs note. Highlights that matter:
  - R2 object read/write **do** exist on the REST API
    (`…/r2/buckets/{bucket_name}/objects/{object_key}`), contrary to the R2
    token page, which says object permissions are S3-only — that sentence is
    about the *named permission group*, not about the endpoint. Checked both
    ways before building on it.
  - **R2 GET and KV GET answer `application/octet-stream`, not the envelope.**
    Their *failures* are still JSON.
  - **D1 database ids are UUIDs with hyphens**; account, zone, KV namespace,
    queue, Hyperdrive config and DNS record ids are all 32 lowercase hex. One
    validator will not do for both.
  - `wrangler d1 migrations apply` posts to the ordinary `/query` endpoint —
    traced through `packages/wrangler/src/d1/migrations/apply.ts:158` →
    `execute.ts:507`. There is no separate migrations endpoint. `/import` is a
    three-step init/ingest/poll protocol that needs an upload to a temporary
    URL, so it is not a single brokered call.
  - Hyperdrive's PATCH body carries `origin.password`. An `edit` that accepted
    one would be an agent handing a credential *to* the broker — the inverse of
    the model. P1-006 must restrict `hyperdrive.edit` to non-secret fields.
  - **Cloudflare documents no reliable way to tell "not authorized" from "not
    found".** 403 + code 10000 with a `documentation_url` field is the one
    documented denial signal (changelog 2026-08-20); code 7003 "No route for
    the URI" is the schema's canonical failure and carries no documented
    status. 81044 does not appear in the schema at all. So P1-007's lookup must
    key on HTTP status and on `success:true` with an empty result, and must
    call anything else could-not-run rather than absence.
- **Two hard-coded vocabulary lists must move with every operation added**, not
  one: `providers/cloudflare/tests.rs`'s count arithmetic (now 9 / 10 / 23) and
  `providers/mod.rs::the_shipped_registry_builds_and_offers_every_provider_s_vocabulary`,
  which lists every operation id in sorted order across all three providers.
- `every_operation()` in `cloudflare/tests.rs` is a table the surface test
  walks, and it asserts one authenticated call per declared operation. DNS
  update and delete will make two calls each, so that assertion has to learn
  the expected count rather than assume one.
- No `elevated` class exists in `apex-secret-core`: `Effect` is `{Read, Write}`
  only, and `OperationSpec` has 28 literals across 6 files, so adding a field
  is real integration surface. P1-007's third criterion will be fail-closed
  (refuse NS/DS/SOA, never declare registrar/dnssec/custom_ns) and reported
  partial.
- House standard for verdicts is `apexd/apex/src/verify.rs::Verdict` —
  `Verified / Absent / Failed / CouldNotRun`, four values because "the registry
  answered and holds nothing" and "the registry did not answer" are different
  measurements.
