## FOUND
- **Two real defects, both found by the tests rather than by reading.**
  `BindingError::NoRecord` and then `NoResource` each fell through the
  `From<BindingError> for ProviderError` match into `Refused`
  (→ `PermissionDenied`) instead of `NoSuchResource` (→ `BadRequest`) — so "this
  project does not bind that" was being reported as "you may not". Same defect
  twice, one unit apart; the second was caught only because the test asserts the
  **error kind** and not merely that something was refused. Any later unit
  adding a binding variant must add it to that arm.
- **A pre-existing trap disarmed.** `service.rs`'s
  `the_vocabulary_is_closed_at_the_grant_and_at_the_use` used
  `cloudflare.dns.delete` as its example of a name no provider declares — which
  P1-007 then declared. Replaced with `cloudflare.account.delete`, which is not
  a §13.2 name and never will be, with a comment saying why. **Whoever
  implements the remaining ten should not hit this again**, but should grep for
  their names before building.
- **The documented REST paths are confirmed from a pinned source**, not from
  memory: `cloudflare/api-schemas` `openapi.json` at `d5003a19` (info.version
  4.0.0, 2026-09-11), cross-checked against the rendered reference. Recorded in
  the `mod.rs` note. The four that mattered:
  - R2 object read/write **do** exist on the REST API, contrary to the R2 token
    page's "object permissions are S3-only" — that sentence is about the named
    permission group, not the endpoint. Checked both ways before building.
  - **R2 GET and KV GET answer `application/octet-stream`, not the envelope**;
    their failures are still JSON.
  - **D1 database ids are UUIDs**; account, zone, KV namespace, queue,
    Hyperdrive and DNS record ids are 32 lower-case hex.
  - `wrangler d1 migrations apply` posts to the ordinary `/query` endpoint
    (`apply.ts:158` → `execute.ts:507`). `/import` is a three-step
    init/ingest/poll protocol around an upload to a temporary URL — not one
    brokered call.
- **Cloudflare documents no reliable discriminator between "not authorized" and
  "not found."** 403 + code 10000 with a `documentation_url` is the one
  documented denial signal (changelog 2026-08-20); code 7003 "No route for the
  URI" covers both a bad identifier and an out-of-scope one; 81044 does not
  appear in the schema at all. So the DNS lookup keys on **HTTP status** and
  calls what it cannot place `CouldNotRun` rather than guessing — which is why
  `Lookup` has five values (Found / Absent / Denied / Ambiguous / CouldNotRun)
  modelled on `apex/src/verify.rs::Verdict`.
- **A filter that was sent is not a filter that was applied.** The DNS lookup
  re-checks every record it gets back against the name and type it asked for. If
  the query parameter were ever spelled wrongly or stopped being honoured, the
  lookup would come back holding the whole zone and the first record in it would
  be modified; the re-check turns that into a refusal instead. Mutation DNS-M5.
- **Hyperdrive carries the origin database's password.** `edit` declares a name
  and three caching settings and nothing else, so the framework refuses an
  `origin`/`password` option before the provider is asked. `read` strips
  `password` and `access_client_secret` from the reply **anyway**, though the
  documentation says they are write-only and never returned — the double sends
  one so the test measures a removal rather than an absence.
- **Limitations that are in the build rather than in a plan**, all stated in
  the `mod.rs` note: an R2 object and a KV value come back through a `String`
  pipeline (`run_curl` does `from_utf8_lossy`), so a non-UTF-8 value is not
  delivered byte-for-byte; an object key is a `Syntax::Path`, so
  `backups/2026-09-12T10:00.sql` cannot be named (`:` is refused by a grammar
  that is load-bearing); `MAX_PAYLOAD` is 10 MB against the documented
  endpoint's 300.
- **A flaky test that is not mine.**
  `apex::provenance::tests::a_git_status_that_could_not_run_is_not_a_clean_working_tree`
  failed once under a parallel `--workspace` run and passes 5/5 in isolation. My
  diff touches no file in `apexd/apex/`. Pre-existing, worth a look by whoever
  owns provenance.
- `every_operation()` in `cloudflare/tests.rs` now carries an **expected request
  count per row**, because `dns.update` and `dns.delete` are two requests each.
  An operation that quietly starts making an extra call fails there.
- Two hard-coded vocabulary lists must move with every operation added: the

## BLOCKED ON
- Nothing blocking. Two criteria left **partial**, precisely:

  **P1-005, "No broad token when narrower scope is possible".** Half of this is
  done and half is not, and the done half must not be allowed to stand in for
  the other. Done: the agent never holds a token at all — the broker spends it
  inside a `curl` it owns — and every R2 operation is scoped to a bucket the
  project's own file lists. Not done: the token actually spent is the
  account-wide one the owner stored. A narrower per-task credential is §13.4's
  and P1-011's; `Provider::mint` still answers "cannot" rather than pretending.
  R2's own `POST /accounts/{id}/r2/temp-access-credentials` does not close it
  either — it needs a `parentAccessKeyId`, which is an S3 access key this
  broker does not hold, and it yields SigV4 credentials that a REST-only
  `curl` transport cannot spend. Closing it means giving the broker an S3
  credential and a signing implementation, which is a task of its own.

  **P1-007, "Registrar/nameserver/DNSSEC-root changes require elevated class".**
  There is no elevated class in `apex-secret-core` to require — `Effect` is
  `{Read, Write}` and nothing in the crate knows what "elevated" would mean. The
  build takes the only honest reading available to it: **NS, DS, DNSKEY and SOA
  are refused outright on create/update/delete** (reading one is allowed, since
  §13.9 reserves *changes*), and registrar, `/zones/{id}/dnssec` and `custom_ns`
  are never declared, so no grant can reach them. The test grants all four DNS
  verbs and still gets a refusal for every reserved shape **with
  `fake.seen().is_empty()`**, so nothing reaches the API.

  That is fail-closed, not the class §13.9 asks for. A real one needs a field on
  `OperationSpec` (28 literals across 6 files — genuine integration surface,
  which is why this agent did not take it unilaterally) plus a grant path gated
  on §4.5's `ACTION_BREAK_GLASS` in `apex-agent-core`. Worth its own item.
