## The design, settled before the first commit

**The relay carries a byte stream, and nothing above it changes.** The LAN
transport is `[u32 BE length][Noise ciphertext]` over `TcpStream`
(`apex-remoted/src/net.rs`). A relay leg is a WebSocket whose binary payloads
carry that same byte stream, so `read_message`/`write_message`, the Noise
channel and every `Frame` ride over it unaltered. "The relay copies bytes it
cannot read" is then a structural property, not a promise.

**The relay leg terminates on the daemon's own loopback, not in `serve.rs`.**
Checked rather than assumed: `grep -n 'loopback\|127\.0\.0\.1\|is_loopback'`
over `apex-remoted/src/{serve,main}.rs` is empty, so nothing refuses a loopback
peer. The relay thread dials the relay outbound, and when a guest attaches it
connects to this daemon's own listener and splices. `serve::connection` keeps
its `TcpStream` and its whole session path untouched — which matters with
p0-014 in flight on the same tree — and the alternative (making `connection`,
`session`, `frames` and `Sealer` generic over a stream trait) is a six-signature
refactor bought for nothing.

Path labelling is race-free by ordering, not by luck: the splice registers its
own loopback source port in `State` **before** it writes the hello byte, and
`connection` reads the hello byte first, so the lookup cannot run early.

**No TLS crate enters the workspace.** `apex-secretd/src/providers/cloudflare/
api.rs` already settled this question for the tree — it shells out to
`curl -q -K -` and says so: "`api.cloudflare.com` is TLS, and nothing in this
workspace speaks TLS." The WebSocket client is therefore generic over
`Read + Write`; plain TCP is what the double and every test use.

**Relay defaults to off, and that is already true.** `apex-remoted --relay
<url>` is optional, `State.relay` and `PairingOffer.relay` are
`Option<String>`, and `files/system/units/apex-remoted.service` passes no
`--relay`. The image therefore ships pointing at no relay and LAN keeps
working. Pinned with a test rather than left as an observation.

**Protocol decisions taken before the double was written**, so the double and
the Worker cannot drift:

- **Roles are explicit.** The desktop dials `?role=host`, a device
  `?role=guest`. A relay that paired "the first two arrivals" would join two
  phones to each other and let them discover that only when Noise failed.
- **The host re-arms.** The moment a guest attaches, the desktop opens a fresh
  waiting connection, so one desktop serves more than one session at a time.
- **An impostor host is a denial of service, not an impersonation.** Anyone who
  has seen the QR knows the rendezvous id and can dial as host for it. They do
  not have the static private key, so `Noise_IK` fails for them. Written into
  the threat model as a decision rather than left to be discovered.

### What the OS side actually offers, checked rather than assumed

- `apex remote pair --text` prints **only** the `apex-remote:` payload on
  stdout; the human sentences go to stderr. Without `--text` it prints
  `qr_block`'s prose as well, so the page wants `--text`.
- `apex remote devices --json` → the `Device` array: `id`, `name`,
  `public_key`, `paired_ms`, `last_seen_ms`, `revoked_ms`,
  `requires_user_verification`, `last_path`. `state()` is `revoked` or
  `paired`, derived from `revoked_ms` alone.
- `apex remote revoke <id>`, `apex remote status --json`. There is **no**
  `pair --json`.

### Criteria, quoted from roadmap.yaml rather than paraphrased

1. "Desktop can display a QR code / short pairing flow from APEX Shell."
3. "Lost devices can be revoked from APEX Settings."
5. "Paired-device list shows name, last seen, permissions, and revocation
   state." — not named in the dispatch, but it is what a paired-device page
   *is*, and the fields are all in `Device`. `requires_user_verification` is
   the "permissions" one, and it is the device's own claim: the CLI says so in
   a sentence rather than a column, "a tick in a table would read as a fact
   this machine had verified". The page must not turn it into a tick.

## Deploying, when Andre wants it

Full version with commands and cost: `ROADMAP/design/P1-052-relay.md` §5.
The short form:

**One blocker first.** `apex-remoted` refuses a `wss://` relay by name, because
nothing in the apexd workspace speaks TLS and `*.workers.dev` is HTTPS-only.
Deploying the Worker today gives a relay that works and a desktop that will not
dial it. Three ways out, and the choice is Andre's because it is a dependency
decision: add `rustls` + `webpki-roots` (~15 crates in a workspace that has
deliberately had none); tunnel through an `openssl s_client` child (zero
crates, same shape as the `curl` child `apex-secretd` already uses); or a
custom domain with "Always Use HTTPS" off so `ws://` on port 80 reaches it
(zero code, and it gives up TLS's cover of the rendezvous id from an on-path
observer — a different party from the relay operator the disclosure already
names).

**Then:** `cd relay && npm install --save-dev wrangler && npx wrangler login &&
npx wrangler deploy`, then `--relay <the printed URL>` on
`apex-remoted.service` per machine.

**Cost:** Durable Objects are on the free plan when SQLite-backed, which the
migration declares; this Worker stores nothing so no row is ever read or
written. Free plan is 100,000 requests/day and 13,000 GB-s/day; paid is $5/mo
with 1 M requests and 400,000 GB-s included. Hibernation means an idle waiting
connection is not billed for duration at all, and incoming WebSocket messages
bill 20:1. One laptop and one phone sit inside the free plan.

**The step I would take before deploying:** `npx wrangler dev --local` with
`cargo test -p apex-remoted --test relay` pointed at it instead of its double.
That is what turns `index.js` from reviewed code into run code.

  **The fixtures caught a real defect before CI ever saw it.**
  `alignmentPositions` used `Math.ceil` where the specification truncates,
  so every version from 7 up put its alignment patterns in the wrong
  columns — 21 of 36 cases, including both pairing offers. Versions 2–6
  have two alignment centres and never use the step, which is why it looked
  right on small symbols. Annex E's table is now transcribed into the test.

  **The oracle is patched, and that is the part worth reading.** segno
  1.6.6 deviates from §7.4.10: `write_padding_bits` quotes the clause in a
  comment and the code drops the condition in it, so it appends 8 zero bits
  when the stream already ends on a codeword boundary — a spurious `0x00`
  where the `0xec`/`0x11` pad codewords belong. In byte mode that is the
  only case, never an edge one: 4 mode bits plus an 8- or 16-bit count means
  the 4-bit terminator always lands exactly on a boundary. Invisible to a
  scanner, which stops at the terminator; not invisible to a byte-for-byte
  comparison. Without the correction this encoder would have to reproduce a
  bug to pass. Three things keep that honest, all checked rather than
  claimed: the generator builds every case twice and **derives**
  `_iso_corrected` by diffing; the test pins that list at exactly the four
  padded cases, so a spreading correction *or* an upstream fix reds it; and
  §7.4.10 is asserted directly off the codewords, so those assertions hold
  with every fixture deleted. The other 32 fill their symbol to capacity and
  provably cannot be reached — asserted, not stated.

  Five mutations, all red: alignment rounds up 21/60; the first pad
  codeword is `0x00` as segno emits 8/73; `FORMAT_BITS` has L and M the
  usual way round 31/50; version 32's special case dropped 2/79; the
  fixtures regenerated with stock segno 6/75. The fourth is why the Annex E
  table earns its place — no fixture is at version 32, so nothing else
  catches it.
