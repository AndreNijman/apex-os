## What this unit is, and is not

Successor to p1-050 (landed as apex-os `1ab542c`, P1-050 done). Five things
were left:

1. No Cloudflare Worker / Durable Object relay — `apex_remote_core::rendezvous`
   derives the id, nothing dials a server; the server side does not exist.
2. No reconnect across network changes.
3. No mDNS discovery (`_apex-remote._tcp`).
4. Connection quality is measured nowhere and rendered nowhere.
5. apex-shell owes a QR pairing page and a paired-device page.

**Not this unit, and P1-051 does not close from here:** `--origin-policy remote`
stays refused until the device key lives in Android Keystore with
`setUserAuthenticationRequired`, a per-approval challenge and attestation. That
is p1-053a; `p0-014`'s CTAP2 verifier is its desktop half.

## The deployment constraint

**Nothing is deployed to Andre's Cloudflare account.** No `wrangler deploy`, no
real Worker, no real Durable Object, no live account auth. The relay's server
side is written as code and proven against a **local double**, the pattern
already in this tree (the P1-005 Cloudflare capability sets run entirely against
a loopback transport that 401s unauthenticated requests; the trust gate was
proven against a minted CA, not production sigstore).

A correct outcome for this unit is "the relay is written, tested against a
double, and ready to deploy". What deploying would actually require is recorded
under **Deploying, when Andre wants it** below.
