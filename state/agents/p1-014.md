## The plan, decided

**P1-014.** The environment is the provider's knowledge and the approval is the
framework's, so the two halves are split at `Bound`:

1. `Bound` gains `approval: Approval` — `Standing` (the grant is the whole
   decision) or `Required(why)`. This closes half of the "Bound carries no
   provider payload" gap **generally**, not for Cloudflare.
2. A store table of **one-shot owner approvals**, a protocol verb, and
   consumption inside `use_capability` *after* the pin and the `creates` check
   and *before* the value is read. Spent on commit, not on success — refunding
   a failed perform would let an agent probe. Guarded by a mutex on `Service`,
   because of the threading note above.
3. `binding.rs` reads `unattended = true` under `[cloudflare.<env>]`. Default
   polarity, §13.8: `preview` and `staging` unattended, **everything else
   protected** — not "production is special-cased by name", so `prod`, `live`
   and `production-eu` do not get a free pass by being spelled differently.
4. Gated: the operations that change what a protected worker **serves** —
   `worker.deploy`, `worker.rollback`, `wrangler.deploy`. NOT
   `worker.upload-version`: §13.7 puts the upload *before* the approval point,
   and gating it would force approval at step one of a five-step flow.
5. `approval_policy` gains two distinct words: `approval-required` on the
   refusal, `owner` when one is spent.

**P1-017 is DONE and pushed** — `8d0439c1` and `dbcdc216`. 2906 -> 2910
passing, 0 failed, clippy clean. Both criteria met. The plan below was
decided after reading `end_to_end.rs` ~880–1150 and
`apexd/apex/src/mcp/servers.rs`, and all three parts were carried out:

1. **The gap is `Credential::None` on an `Endpoint` transport.** A remote
   MCP server whose definition carries no credential header is NOT a server
   with no credential: either it needs none, or the agent authenticates it
   itself by OAuth — and a token the agent's own runtime obtains is
   agent-readable by construction, because the agent uses it. That is
   §13.12 word for word: *"do not hand provider credentials directly to the
   model just because the MCP server supports OAuth."* Today
   `agent_readable()` answers **false** for exactly that case, which is an
   absence reported as a fact. A new variant for remote-with-no-header,
   `agent_readable() == true`, and the way out printed is `apex mcp connect
   <name>`. Nothing Cloudflare-specific is hardcoded — the rule is about
   remote servers; Cloudflare's are the instance §13.12 names.
2. **The hostile test for criterion 2** is a fake MCP server that echoes
   the `Authorization` header it received back inside its JSON-RPC
   `result`. That proves the model cannot see the credential even when the
   far side tries to hand it over, rather than that nobody handed it over
   today. It must assert three things or it can pass vacuously: the server
   really received `Bearer <sentinel>`, the output does not contain it, and
   the scrub marker IS present.
3. Criterion 1 is strengthened rather than inherited: `mcp.request` now
   passes the grant check, the §13.14 budget and the reservation.

**The open question was settled, by fetching Cloudflare's own docs rather
than inferring:** their remote MCP servers **do** accept a Cloudflare API
token as `Authorization: Bearer` — stated there for CI and automation, user
and account tokens both — so `apex mcp connect` can route them and P1-017's
Cloudflare instance is `done` rather than `partial`. They are a different
HOST from `api.cloudflare.com`, so such a server needs its own stored
credential with its own pin; the existing `cloudflare` credential cannot be
reused.

Deliberately not done: no live `apex mcp connect` was run against a real

## NEXT (for whoever picks this up)

Nothing in this unit is outstanding. Two things it *found* and left alone,
each its own task rather than scope creep here:

1. **§13.13's D1 and KV preview resources** need six new operations plus
   the binding question of how an id that does not exist yet reaches
   `apex.toml`. That is what keeps P1-015 `partial`.
2. **The framework's endpoint pin compares scheme and host and not port.**
   Nothing shipped exploits it — the MCP provider builds its request from
   the stored record and never from `bound.endpoint`, which is what M18
   measured — but a provider written later that trusted `bound.endpoint`
   would be able to reach a different service on the same host. On loopback
   that is every other daemon on the machine. Worth a decision: either pin
   the port, or state in `provider.rs` that a provider must never resolve a
   destination from caller input.
