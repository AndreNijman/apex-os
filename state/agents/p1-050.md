## The finding that shapes everything

`apex-agentd` establishes request origin from the *connection's* cgroup
(`apex-agentd/src/origin.rs::classify`). A proxy is not a managed session, so
`Request::DeclareOrigin` refuses it outright ("only a managed session can narrow
its own origin"). Consequence: whatever origin a remote proxy is observed to
have is the origin every request it forwards is recorded under — and if the
proxy is started from a login session rather than a user unit, that origin is
`local-terminal`, which `privilege::decide` accepts as a human at the keyboard
and will let approve a root operation.

That is exactly "laundering a remote request into a local one", and it happens
by default if you start the service the obvious way. So commit 1 is a
**per-connection origin latch** in agentd: a non-session connection may declare
a narrower origin once, monotonically (`origin::may_declare` already refuses any
move towards local), and it sticks for the life of the connection.

## Decisions taken

- Reuse `RequestOrigin::RemoteControl` (`claude-remote-control` on the wire)
  rather than adding an 8th §7 origin. An 8th is a `PROTOCOL_VERSION` bump, a
  change to `Capability::ruling` and the 7×7 declaration test, and a conflict
  with the open P1-020 branch. Device identity travels in a separate `actor`
  field, which answers "which device" better than an origin name would.
- The remote protocol is the **existing agentd control protocol carried inside
  an encrypted channel**, not a second protocol. Provider neutrality then comes
  from the adapter layer that already exists.
- No inbound port for the relay; LAN listener needs one firewall exception.
