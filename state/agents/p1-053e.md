## How to run the on-device suite

```
cd /var/tmp/apex-work/wt-p1-053e
export ANDROID_HOME=/var/tmp/android-sdk
export JAVA_HOME=/var/tmp/apex-work/scratch-p1-053c/jdk21root/usr/lib/jvm/java-21-openjdk
android/tools/run-device-suite.sh -s 192.168.1.98:35915
```

It builds both APKs, stands up `apex-agentd` + `apex-remoted` from the worktree
in their own XDG root, brokers the control socket to the phone, turns TalkBack
on, runs the instrumentation and restores TalkBack. **It never touches the live
runtime and stops its daemons by pid.** Round 1's result on the tip: **OK (24
tests)**, TalkBack bound.

**The system JDK 21 on the L16 is broken in a specific way** —
`/usr/lib/jvm/java-21-openjdk/conf/security/java.security` does not exist, so
every `MessageDigest.getInstance` throws `InternalError` and kills the Gradle
*wrapper* before a build starts. Use the unpacked root above. This is why
`JAVA_HOME` is not optional.

## NEXT

Round 1's own card ordered the remaining work by value. Take them in this order
and stop when the round is full rather than starting a fifth:

1. **The terminal on a real screen.** `TerminalScreen`/`TerminalController` were
   deliberately excluded from the on-device suite (`Screens.kt` says so): they
   own a PTY attachment, and half a controller asserts something no user sees.
   **A terminal in landscape at font scale 2.0 is the screen that matters most
   and the one with no device evidence at all.**
2. **PTY output read back over an attach from the phone**, and the relay leg.
   Those are the two named parts of **P1-060 C1** still missing — this is the
   only item here that closes a criterion.
3. **The dual-stack bind — a real regression, and it needs its own measurement.**
   `main.rs` still binds `0.0.0.0`. Binding `::` moves every peer to
   `::ffff:a.b.c.d`, and `State::path_of` decides LAN-or-relay on
   `is_loopback()`, which is **false** for a v4-mapped loopback. `State::bound`
   is already in place so the advertisement follows the bind automatically.
   Measure the wrong answer before you change anything, then measure it again.
4. `createAndroidComposeRule` is deprecated in Compose 1.11 in favour of
   `…junit4.v2.createAndroidComposeRule`, which swaps `UnconfinedTestDispatcher`
   for `StandardTestDispatcher`. Round 1 left it alone **deliberately** — it
   changes when coroutines run inside every test here, and migrating it in the
   round that first got these tests running would make a failure impossible to
   attribute. That reason has now expired, so it is takeable; but it is last,
   and it must be its own commit.

## FOUND

- **There is NO relay client on Android at all.** `PairingService.handshake`
  says it in its own error text — "(and no relay client has been written yet)"
  — `:core` has no WebSocket code, and `Help.kt` tells the user the relay has no
  deployment. So "the relay leg on the device" is not a test to write against
  existing code: it is an RFC 6455 client in `:core`, a relay double the phone
  can dial on the L16, and `apex-remoted --relay` pointed at it.
- C1 names **approvals** too, and `p1-053d`'s evidence lists "no approve/deny
  round trip" as a third gap the dispatch does not mention. **A phone can never
  approve or deny** — `privilege.rs:1176` refuses `decide` from any non-local
  origin before the pending check — and `Approvals.kt` records that as a thing
  that deliberately does not exist. What a phone CAN do is list requests/grants
  and revoke, so that is the shape the device test must take.
- Round 1's findings are on `p1-053d.md` under CORRECTIONS, and two of them
  invert a criterion in our favour.
