## Defects found, proven in a namespace, and fixed

All five were found by loading the policy; none is visible to a grep.

1. **Not idempotent.** `nft -f` merges a `table` block into an existing table.
   Measured: a second load turned 14 accepts into 28, and a doubled
   `limit rate` is silently twice the rate it says. Fixed with a
   `table inet apex` / `delete table inet apex` preamble.
2. **One typo closed every other port.** `apply_sets` built one
   `nft add element` per protocol, so a single bad `.conf` failed the whole
   command — silently, because the unit runs the reload as `ExecStart=-` and it
   printed "exceptions reapplied" either way. Now applied one at a time, with a
   non-zero exit and a `status` that says which file was rejected.
3. **`deny` was an `rm -f` on an unvalidated path, as root.**
   `apex firewall deny ../../../etc/issue` reached outside
   `/etc/apex/firewall.d`. Now the name is checked before it becomes a path.
4. **The forward chain killed every rootful container's network.** Its comment
   claimed podman was unaffected because it hooks "at its own priority in its
   own table". Measured false: nftables evaluates every base chain at a hook,
   an accept in one does not end the others, and a drop in any one is final.
   A stub table accepting everything did not rescue the traffic. Chain removed
   — `ip_forward` is 0 until something turns it on, and the thing that turns it
   on brings its own policy.
5. **`established,related` does not rescue a pre-existing connection.**
   conntrack is not loaded on an APEX box until this ruleset loads, so it has
   no entry for a connection that was already open; the first packet creates a
   `new` entry and `new` is dropped. Measured, per kind: outbound survives
   (our next packet out makes the entry), inbound on an open port survives on
   that port's rule — which is why ssh is safe — and inbound on a closed port
   dies. Documented in the policy header rather than "fixed": the unit loads
   before the network, so at boot there is nothing to strand.

Two more in the ssh driver itself, found by trying to run it at katana:

6. **`--target` was an ssh destination and a TCP address at once.** Every
   probe was `</dev/tcp/$TARGET/...`, so the script could only ever run against
   a target whose ssh name also resolves. `katana` is an alias with a key
   attached and resolves nowhere; the IP has no key. Now the probe address
   comes from `SSH_CONNECTION` on the target, which is the far end of the path
   already under test and needs no resolver.
7. **"must not resolve to a local address" was a string comparison.** It
   caught `localhost` and this host's own name, not an alias pointing back
   here — which would have loaded a default-drop policy on the driver. Now the
   probe address is checked against `ip -o addr show`.

Still open as scope questions, not defects: LLMNR (5355 tcp+udp) is accepted on
every interface, and mDNS accepts a unicast query from any source rather than
only link-local.

## Three more defects, found by running it at a real machine

8. **The policy staged under `/run` is unreadable to the `nft` that loads it.**
   `/usr/sbin/nft` is `iptables_exec_t`, so systemd starting it transitions to
   `iptables_t`, and `iptables_t` may not read `var_run_t`. Measured twice from
   a transient unit: `avc denied { getattr } scontext=iptables_t
   tcontext=var_run_t`, exit 1; the same bytes relabelled `usr_t` load. The
   staged copies now carry the labels their shipped originals do (`usr_t` for
   the policy, `bin_t` for the helper), which incidentally settles that the
   shipped `/usr/share` path works for the same reason.
9. **The driver got itself banned by the target's sshd.** `Match exec` in
   `~/.ssh/config` runs `~/.ssh/lan-up` on every ssh *invocation* —
   multiplexing does not skip it — and `lan-up` is a bare TCP connect to port
   22 that never authenticates. Fifteen calls in ten seconds tripped OpenSSH's
   `PerSourcePenalties`; the driver was locked out for about fifty seconds
   while the policy was loaded, which reads exactly like the firewall
   stranding its operator. One connection now goes through the config and
   everything else rides its socket with `-F /dev/null`. Measured: six calls
   through the config open seven such connections, six over the socket open
   none.
10. **A call that never arrived was being read as a fact about the target.**
   With the master socket mismatched (`%h` expands to the resolved address
   with the config and to the alias without it), every `-F /dev/null` call
   failed — and "no apex table is loaded" and "the firewall is not shipped
   here" are both *non-zero exits*. A remote `exit 7` must now come back as 7
   before anything else is believed.

Also fixed: the same alias falls back to a tunnel when the direct path stops
answering, so "a brand-new ssh connection still gets in" could have passed as
a fact about the tunnel. It must now arrive on the same address, and a
completed handshake on port 22 when ssh fails is reported as sshd refusing
rather than the policy dropping.

## Mutation proof of the live suite, on katana

Mutating `files/system/nftables/apex.nft` in the worktree; the driver stages
from `$ROOT`, so editing it there is the mutant, and every count below is
against a live enforcing ruleset on real hardware.

| mutant | passed | failed |
|---|---|---|
| baseline | 27 | 0 |
| input chain `policy drop` → `policy accept` | 22 | **5** |
| `tcp dport @allowed_tcp accept` deleted | 24 | **3** |
| restored | 27 | 0 |

(1 skip throughout: katana has no IPv6 route.)

The five and the three are the right five and the right three: `policy accept`
loses "the policy really is enforcing", "a new connection to that port is now
dropped", "a listener on 22000 is unreachable until it is allowed", "a
malformed exception leaves the base policy standing" and "deny really closes
it again"; deleting the exception set's rule loses "allow really opens it",
"the exception survives a real systemctl restart" and "and does not close the
exception next to it".

Two more mutants ran by accident and were caught: the first live run had the
staged files mislabelled and the unit refused to start (7/1); the second had
the ControlPath broken and the suite stopped at the first thing it could not
learn (2/1). Neither reported a green machine.

**A mutant touching `tcp dport 22 accept` or `ct state established,related
accept` was deliberately NOT run against katana** — that one is an outage on
Andre's machine. The namespace suite measured that half.

- The parsers were replayed against output the CLI really produced —
  `apex firewall list`, `status` unprivileged on the L16, `status` as root on
  katana over a policy loaded in the kernel with one working and one rejected
  exception, and `systemctl show` on the real `apex-firewall.service` in all

The design decision, so nobody relitigates it: **privileged verbs are shown,
not run.** The shell raises no authentication prompt of its own; `RecoveryService.qml`
lines 50–63 is the precedent and the reasoning, and there is no polkit action
for the firewall — `org.apexos.apexd.policy` covers apexd's power and battery
D-Bus methods and nothing else. The page shows `sudo apex firewall allow <name>`
the way RecoveryPage shows the rollback command.

One defect found and fixed (`e51412b`): an empty exception list was rendered
with a single reassuring sentence, "every port ... is reachable only from this
machine itself". Three machines produce that empty list and it is true of one.
Measured on katana, whose image predates `apex firewall`: the verb exits
non-zero with "unrecognized subcommand", the parser correctly reports a read
that did not answer, and the page then printed the reassuring sentence three
lines under its own headline saying nothing was filtering anything. The
sentence is now chosen in `firewall.js` from what is known; two node mutants
(2 and 1 failures) and two static mutants prove it.
