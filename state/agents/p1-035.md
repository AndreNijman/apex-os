## FOUND
- `File::open` on a FIFO BLOCKS until a writer arrives. The first version of
  the daemon handler opened first and checked the type second, so a path to a
  FIFO would have parked a daemon thread indefinitely, from any caller, with no
  privilege. Found because the unit test hung. Now: stat the path, refuse a
  non-regular file before opening, open with O_NONBLOCK, re-check on the fd.
- A grep pattern containing a newline is TWO patterns to grep, the second empty,
  and an empty pattern matches every line. `grep -q $'\n'` therefore always
  succeeds. The first run of the suite reported "nothing that arrived can submit
  the line" as FAILED on bytes that were correct.
- `Request::Signal`, `Remove` and `Prune` take no peer credentials at all, so a
  confined session (which has the control socket bound in, so it can publish
  events) can SIGKILL any other session, delete its transcript, or prune every
  exited session. Read from apex-agentd/src/main.rs's dispatch; not exploited.
  Reported, not fixed — outside these three items.
- The `apex agent send` verb has no shell-side surface. apex-shell's
  AgentHelpContent.qml already tells the user per-worktree test status and
  merge-conflict state are "on the roadmap" (that text is P1-036's to correct).

- **`cargo test --workspace` CANNOT be green when run by the autoresume
  timer, and the cause is the timer itself.** `apex-agentd`'s
  `renewing_a_grant_that_does_not_exist_is_refused_without_asking_anybody`
  expects the message "no active system-access grant" and instead gets
  `grants.rs:98`'s origin refusal, "a scheduled-job request cannot renew a
  system-access grant: §7 reserves elevation for a human at this machine".
  Why: `origin::classify` (apex-agentd/src/origin.rs:112) returns
  `ScheduledJob` for any cgroup containing both `/user@` and `.service`, and a
  session started by `apex-roadmap-resume.service` has the cgroup
  `/user.slice/user-1000.slice/user@1000.service/app.slice/apex-roadmap-resume.service`.
  So the origin check, which runs BEFORE the grant-existence check, fires
  first. Any agent dispatched by the unattended timer will see this 1/982
  failure and may burn time chasing it — it is not a regression and not the
  agent's own code. Run that suite from a login terminal to see it pass.
  MEASURED, not assumed: real tty processes on this L16 are in
  `/user.slice/user-1000.slice/session-4.scope`, which matches classify's
  FIRST branch and is correctly labelled `LocalTerminal`. So this is
  specifically about systemd *user services*, and ordinary terminals and
  APEX Shell are unaffected. Not fixed — outside these three items, and the
  fix is a judgement call about whether the test should pin its origin.

## FOR THE INTEGRATOR — a rebase conflict that will NOT show up as a build error
`apex-agent-core/src/paths.rs` `scratch_root()` was invented TWICE, on both
sides of the fork, for the same bug, with **different environment variable
names**:
- `origin/roadmap/v2.2` calls it `APEX_AGENT_SCRATCH` (inline `var_os`, guards
  the empty string).
- this branch (`1bb5db4`) calls it `APEX_AGENT_SCRATCH_ROOT`
  (`paths::SCRATCH_ROOT_ENV`, plus `SCRATCH_ROOT = "/tmp/apex-agent"`, guards
  with `is_absolute()`).

Both sides rewrote the same hunk (`@@ -199,11` on each), so it conflicts
loudly — but whichever name loses, **the suites that export the other name
keep compiling and silently stop isolating**. The symptom is not a type error,
it is `bwrap: Can't open source /tmp/apex-agent/1` at runtime, or worse, a test
run reaping a live session's scratch (which is the exact bug `1bb5db4` fixed).
Whoever resolves it must also fix the `export` line in
`tests/test-agent-inject.sh` and in v2.2's own integration suite. Recommend
keeping `APEX_AGENT_SCRATCH_ROOT` + `is_absolute()`: the absolute-path guard is
the part that carries the trust argument, and an empty-string guard is a subset
of it.

Also on the rebase, all minor: `apex-agent-core/src/lib.rs` conflicts trivially
(v2.2 inserts `pub mod graph;`/`pub mod statusline;`, this branch inserts
