## P1-037 DESIGN (2026-09-08, agent #4)
Acceptance (`roadmap.yaml:1807`): "Agent task can run in disposable capsule and
discard state." Gates: tests, stop_slop.

**MEASURED first, because the card's groundwork note was only half right.**
`apex disposable` exists and is good (`apex/src/disposable.rs` is an argv
builder over `files/system/libexec/apex-disposable`, 707 lines, with the
isolation caveat already written honestly in its own header). But **the agent
runtime has NO capsule awareness at all** — grepped: `project::Project.capsule`
is the only mention in `apex-agent-core`/`apex-agentd`, and it is a name nobody
reads at run time. `RunRequest` has no capsule field, and `session.rs` spawns
the adapter directly through `sandbox::build_argv`. So the connection IS the
work; it is not a wiring job onto something half-connected.

Also measured: **`apex task` has no run verb** (`TaskCmd` is
new/set/list/show/resume/checkpoint/forget — `resume` prints commands and
attaches). So the acceptance line is satisfied by `apex agent run
--disposable`, and `task.rs` is not touched. Do not widen into it.

### Why the CLI cannot compose this, which rules out the obvious design
`apex disposable run -- apex agent run ...` already works by hand and is the
WRONG answer: the daemon spawns the PTY on the host, and `/run/user/<uid>` is
shared into every capsule, so `apex agent run` from inside a capsule reaches
the host daemon and the session starts OUTSIDE the environment. The capsule
would be an empty gesture. The wrap has to happen where the process is
spawned, i.e. in the daemon.

### The design
`RunRequest` gains two OPTIONAL `#[serde(default)]` fields — `disposable: bool`
and `copy_out: Option<String>` — the ToolCheck precedent, not a protocol bump.
When `disposable` is set the daemon makes the session's PTY child the ENGINE,
not the adapter:

    <apex-disposable> run --name disp-agent<id> --copy-in <workdir> \
        [--copy-out <dir>] \
        -- sh -c 'cd -- "$HOME/in/$1" || exit 1; shift; exec "$@"' \
           sh <basename of workdir> <adapter program> <adapter args...>

Three things that design buys, each of which would otherwise be new code:
- **Teardown is the engine's, already tested.** Its `trap ... EXIT` plus INT
  and TERM traps mean the environment is removed on every exit path, including
  the daemon sending SIGTERM (the trap exits 143, then EXIT fires). The daemon
  needs no SIGCHLD teardown hook, and a daemon that dies mid-session leaves an
  entry `apex disposable list`/`purge` already handles — say that in the docs
  rather than pretending it is perfect.
- **The `sh -c` script is a FIXED string.** The directory and the whole
  adapter argv arrive as POSITIONAL PARAMETERS, so nothing the user typed —
  and the prompt is user text — is ever interpolated into a shell string.
- **`--copy-in`, so the worktree is COPIED, not bound.** That is the "discard
  state" half of the acceptance line: the agent's changes live in the
  capsule's throwaway home (`--home` is mandatory in the engine's
  `create_argv`) and go with it. Nothing leaves unless `--copy-out` says so.
  A worktree reached through `/run/host` instead would write to the host and
  discard nothing.

### Refused, not composed
A confining `policy.sandbox` together with `--disposable` is REFUSED at the
daemon with the reason. bwrap wrapping `apex-env exec` confines the podman
client, not the agent, so the pair reads as "confined AND disposable" and
delivers neither. The engine's header says the two "compose" — that means
starting a sandboxed session from INSIDE a capsule, which is the direction
ruled out above.

### The honesty this feature must carry, in three places
The `disposable` field doc, the `--disposable` help text, and the docs section:
a throwaway ENVIRONMENT, not a security boundary. distrobox mounts the host
root at `/run/host` in every capsule and there is no flag that removes it, and
the process runs as the user's own uid — so code in there can read and write
the real HOME. For confinement the mechanism is the sandbox policy, and the two
are refused together rather than pretended to combine.

### Testable with NO podman and no image pull
`APEX_DISPOSABLE_ENV_ENGINE` already overrides the capsule engine the
disposable engine calls, and `APEX_DISPOSABLE_ROOT` overrides the root it
deletes. So the suite runs the REAL disposable engine — real name validation,
real copy-in, real teardown, real traps — against a FAKE `apex-env` that LOGS
every invocation and, for `exec`, runs the command on the host. The log is the
point: a fake that only exits 0 makes every assertion vacuous (the lesson from
P1-036's decoy repository). The daemon needs one new override to find the
engine at all, since `ops::DISPOSABLE_ENGINE` is a hardcoded const in the
`apex` crate that `apex-agentd` cannot use.

## P1-036 DESIGN
**RECONSTRUCTED 2026-09-07 by agent #3.** The section the dispatch called

Acceptance (roadmap.yaml): "Tests/conflicts/diff/PR readiness visible per
worktree." Four quarters, and each one needs a source of truth that does not
touch a worktree someone is sitting in.

- **conflicts** — `git merge-tree --write-tree --name-only <base> <branch>`,
  run from the PROJECT ROOT against ref names, never from inside the agent
  worktree, so nothing depends on that tree's HEAD or index. NEVER a real
  merge. MEASURED on git 2.55.0 (the four cases, in the scratchpad): exit 0 =
  clean, stdout is the tree OID alone; exit 1 = conflicted, stdout is OID,
  then one conflicted path per line, then a blank line, then human messages
  ("Auto-merging", "CONFLICT (content): ..."); exit 128 = refusing to merge
  unrelated histories, and also a ref that does not resolve. So exit 0/1 are
  the only answers to trust and anything else degrades to `Unknown` rather
  than failing the whole status. Caveat to keep honest in the docs:
  `--write-tree` DOES write unreferenced tree objects into the common object
  store. That is not a worktree touch and cannot disturb an index, a stash or
  a branch, but it is not literally zero — say so, do not claim "reads only".
- **base** is the MAIN tree's current branch read at query time.
  `ensure_worktree` bases a new worktree on `git::current_branch(root)` and
  records that nowhere, so there is no stored base to recover; the struct doc
  must say the base is observed now, not remembered.
- **diff** — `git diff --numstat <base>...<branch>` for the committed delta,
  plus the uncommitted dirt from the existing `git::is_dirty`.
- **PR readiness** is a DERIVED LOCAL boolean with reasons — has an upstream,
  in sync with it, ahead of base, clean tree, no conflicts. Named
  `ready_to_propose`, deliberately not `pr_status`: nothing here asks GitHub.
  See NOT MINE #1.
- **tests** — the scope decision. The constraint "no side effects in a
  worktree someone is sitting in" means test state can only be OBSERVED,
  never produced: the runtime must not run anybody's suite to answer a status
  query. The only observation channel that exists is the hook stream the
  daemon already receives. MEASURED: `hook::Payload` (hook.rs:241) carries NO
  exit code, so a tool's outcome is knowable only from WHICH event fired —
  `post_tool_use` vs `post_tool_use_failure`, both already in `HookEvent::ALL`
  and already subscribed. So: detect a test command in `hook.rs` where the
  payload is already parsed and unit-testable, carry it as a new OPTIONAL
  field on `Request::Event` (`#[serde(default)]`, the precedent the protocol
  already documents at protocol.rs:509 — NOT a protocol bump), record it on
  the session, and join it to the worktree. States: `Unobserved` (the honest
  default), `Running`, `Passed`, `Failed`.
  **The upstream caveat that must NOT be overclaimed:** whether Claude really
  emits `PostToolUseFailure` for a non-zero Bash exit is an UPSTREAM fact this
  branch cannot verify headlessly. What is verifiable, and what the suite
  actually tests, is APEX's own chain end to end once such an event arrives.
  Document it as "the last test run APEX OBSERVED", never as "the tests pass".

## FOUND (earlier rounds)
- `File::open` on a FIFO BLOCKS until a writer arrives. The first version of
  the daemon handler opened first and checked the type second, so a path to a
  FIFO would have parked a daemon thread indefinitely, from any caller, with no
  privilege. Found because the unit test hung. Now: stat the path, refuse a
  non-regular file before opening, open with O_NONBLOCK, re-check on the fd.
- A grep pattern containing a newline is TWO patterns to grep, the second empty,
  and an empty pattern matches every line. `grep -q $'\n'` therefore always
  succeeds. The first run of the suite reported "nothing that arrived can submit
  the line" as FAILED on bytes that were correct.
- `Request::Signal`, `Remove` and `Prune` take no peer credentials at all, so a
  confined session (which has the control socket bound in, so it can publish
  events) can SIGKILL any other session, delete its transcript, or prune every
  exited session. Read from apex-agentd/src/main.rs's dispatch; not exploited.
  Reported, not fixed — outside these three items.
- The `apex agent send` verb has no shell-side surface. apex-shell's
  AgentHelpContent.qml already tells the user per-worktree test status and
  merge-conflict state are "on the roadmap" (that text is P1-036's to correct).

- **`cargo test --workspace` CANNOT be green when run by the autoresume
  timer, and the cause is the timer itself.** `apex-agentd`'s
  `renewing_a_grant_that_does_not_exist_is_refused_without_asking_anybody`
  expects the message "no active system-access grant" and instead gets
  `grants.rs:98`'s origin refusal, "a scheduled-job request cannot renew a
  system-access grant: §7 reserves elevation for a human at this machine".
  Why: `origin::classify` (apex-agentd/src/origin.rs:112) returns
  `ScheduledJob` for any cgroup containing both `/user@` and `.service`, and a
  session started by `apex-roadmap-resume.service` has the cgroup
  `/user.slice/user-1000.slice/user@1000.service/app.slice/apex-roadmap-resume.service`.
  So the origin check, which runs BEFORE the grant-existence check, fires
  first. Any agent dispatched by the unattended timer will see this 1/982
  failure and may burn time chasing it — it is not a regression and not the
  agent's own code. Run that suite from a login terminal to see it pass.
  MEASURED, not assumed: real tty processes on this L16 are in
  `/user.slice/user-1000.slice/session-4.scope`, which matches classify's
  FIRST branch and is correctly labelled `LocalTerminal`. So this is
  specifically about systemd *user services*, and ordinary terminals and
  APEX Shell are unaffected. Not fixed — outside these three items, and the
  fix is a judgement call about whether the test should pin its origin.
- The mutation runner `.mutate.sh` the predecessor left had two defects, both
  of which would have manufactured FALSE SURVIVORS, i.e. the single most
  misleading result this exercise can produce. Both fixed before any mutation
  was trusted (the file stays untracked; do not commit it):
  1. No `set -e` and no `&&` between the python splice and the test run, so a
     splice whose `assert s.count(old)==1` tripped would have run the suite
     against UNMUTATED source and reported "48 passed, 0 failed" — identical
     to a surviving mutant. `run()` now refuses to run unless
     `git diff --name-only -- apexd/` is non-empty, and prints what it mutated.
  2. Mutation 1's splice called `other.lock()` while the handler still holds
     the addressed session's mutex through `s` (inject.rs:95). A std `Mutex`
     re-locked on the same thread DEADLOCKS rather than returning `Err`, so
     mutation 1 would have HUNG on the addressed session instead of mutating.
     Changed to `try_lock()`, which skips the already-held addressed session

## FOR THE INTEGRATOR — a rebase conflict that will NOT show up as a build error
`apex-agent-core/src/paths.rs` `scratch_root()` was invented TWICE, on both
sides of the fork, for the same bug, with **different environment variable
names**:
- `origin/roadmap/v2.2` calls it `APEX_AGENT_SCRATCH` (inline `var_os`, guards
  the empty string).
- this branch (`1bb5db4`) calls it `APEX_AGENT_SCRATCH_ROOT`
  (`paths::SCRATCH_ROOT_ENV`, plus `SCRATCH_ROOT = "/tmp/apex-agent"`, guards
  with `is_absolute()`).

Both sides rewrote the same hunk (`@@ -199,11` on each), so it conflicts
loudly — but whichever name loses, **the suites that export the other name
keep compiling and silently stop isolating**. The symptom is not a type error,
it is `bwrap: Can't open source /tmp/apex-agent/1` at runtime, or worse, a test
run reaping a live session's scratch (which is the exact bug `1bb5db4` fixed).
Whoever resolves it must also fix the `export` line in
`tests/test-agent-inject.sh` and in v2.2's own integration suite. Recommend
keeping `APEX_AGENT_SCRATCH_ROOT` + `is_absolute()`: the absolute-path guard is
the part that carries the trust argument, and an empty-string guard is a subset
of it.
